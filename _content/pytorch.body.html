What PyTorch Is & Why It Matters

PyTorch is an open-source tensor and automatic-differentiation library that has become the dominant framework for deep-learning research and, increasingly, production. It feels like NumPy with GPU acceleration and a built-in gradient engine — you write ordinary Python, and PyTorch records what you do so it can differentiate it.

Its killer feature is the define-by-run (dynamic) computation graph: the graph is built on the fly as your code executes, so control flow, loops, and conditionals are just normal Python. This is why nearly every modern model — Transformers, diffusion models, LLMs — ships a PyTorch reference implementation first.

Tensors

N-dimensional arrays with GPU support and a NumPy-like API.

Autograd

Automatic reverse-mode differentiation over any tensor computation.

nn & optim

Composable layers, loss functions, and gradient-based optimizers.

Tensors: The Core Data Structure

Everything in PyTorch is a torch.Tensor. The API deliberately mirrors NumPy, so most intuition transfers directly.

import torch

# Creation
a = torch.tensor([[1., 2.], [3., 4.]])   # from data
z = torch.zeros(2, 3)                      # shape (2,3) of zeros
o = torch.ones_like(a)                     # same shape/dtype as a
r = torch.randn(2, 3)                      # standard normal
rng = torch.arange(0, 10, 2)               # [0,2,4,6,8]

# Attributes
print(a.shape, a.dtype, a.device)          # torch.Size([2,2]) torch.float32 cpu

# Reshaping (view shares memory; reshape may copy)
x = torch.arange(12)
x2 = x.view(3, 4)
x3 = x.reshape(2, 6)
x4 = x2.unsqueeze(0)                        # add a batch dim -> (1,3,4)
x5 = x4.squeeze(0)                          # remove size-1 dims

# Indexing & slicing (NumPy-style)
print(a[0])        # first row
print(a[:, 1])     # second column
print(a[a > 2])    # boolean mask

Broadcasting & Elementwise Math

m = torch.ones(3, 4)
bias = torch.tensor([1., 2., 3., 4.])
print((m + bias).shape)      # (3,4): bias broadcast across rows

# Matrix multiply: @ or matmul; * is elementwise
A = torch.randn(2, 3)
B = torch.randn(3, 5)
C = A @ B                    # (2,5)

# Reductions along axes
t = torch.randn(4, 6)
print(t.sum(dim=0).shape)    # (6,) sum over rows
print(t.mean(dim=1).shape)   # (4,) mean over columns
print(t.argmax(dim=1))       # index of max per row
Fig 2. A tensor is a 1D storage buffer plus shape/stride metadata; views reinterpret the same bytes.
Watch out view() requires contiguous memory. After operations like transpose() you may need .contiguous() first, or use reshape() which copies when needed.

Autograd: Automatic Differentiation

Autograd is the engine that makes training possible. Set requires_grad=True on a tensor and PyTorch records every operation into a dynamic graph. Calling .backward() walks that graph in reverse, applying the chain rule to populate each leaf's .grad.

x = torch.tensor(2.0, requires_grad=True)
y = x ** 3 + 2 * x          # y = x^3 + 2x
y.backward()                 # dy/dx = 3x^2 + 2 = 14 at x=2
print(x.grad)                # tensor(14.)

# Vector case: provide a gradient (upstream) or reduce to a scalar
w = torch.randn(3, requires_grad=True)
loss = (w ** 2).sum()
loss.backward()
print(w.grad)                # 2*w
Fig 3. Autograd records each op's grad_fn during the forward pass, then applies the chain rule in reverse.

Controlling the Graph

# Disable tracking for inference / updates (saves memory, speeds up)
with torch.no_grad():
    preds = model(x)

# Detach a tensor from the graph (stop gradient)
frozen = tensor.detach()

# Zero grads each step — gradients ACCUMULATE by default!
optimizer.zero_grad()        # or model.zero_grad(set_to_none=True)
Gotcha Gradients accumulate across .backward() calls. Forgetting zero_grad() is the #1 silent training bug — your updates become sums of stale gradients.

Building Models with nn.Module

nn.Module is the base class for all models and layers. You declare submodules in __init__ and define the computation in forward. PyTorch automatically tracks parameters for you.

import torch.nn as nn
import torch.nn.functional as F

class MLP(nn.Module):
    def __init__(self, in_dim, hidden, out_dim):
        super().__init__()
        self.fc1 = nn.Linear(in_dim, hidden)
        self.fc2 = nn.Linear(hidden, out_dim)
        self.dropout = nn.Dropout(0.2)

    def forward(self, x):
        x = F.relu(self.fc1(x))
        x = self.dropout(x)
        return self.fc2(x)          # logits (no softmax here)

model = MLP(784, 256, 10)
print(sum(p.numel() for p in model.parameters()))  # param count
print(model)                                         # pretty structure

Datasets & DataLoader

A Dataset maps indices to samples; a DataLoader wraps it to provide batching, shuffling, and parallel loading.

from torch.utils.data import Dataset, DataLoader

class CSVDataset(Dataset):
    def __init__(self, X, y):
        self.X = torch.as_tensor(X, dtype=torch.float32)
        self.y = torch.as_tensor(y, dtype=torch.long)

    def __len__(self):
        return len(self.X)

    def __getitem__(self, idx):
        return self.X[idx], self.y[idx]

train_ds = CSVDataset(X_train, y_train)
train_loader = DataLoader(
    train_ds, batch_size=64, shuffle=True,
    num_workers=4,          # parallel CPU workers
    pin_memory=True,        # faster host->GPU transfer
    drop_last=True,
)
Throughput tip Combine num_workers>0, pin_memory=True, and non_blocking=True on .to(device) to overlap data transfer with compute. On Windows, guard the entry point with if __name__ == "__main__": when using workers.

The Training Loop

PyTorch does not hide the loop — you write it. The five steps are always the same: forward, loss, zero grads, backward, step.

model.to(device)

for epoch in range(num_epochs):
    model.train()
    running = 0.0
    for xb, yb in train_loader:
        xb = xb.to(device, non_blocking=True)
        yb = yb.to(device, non_blocking=True)

        optimizer.zero_grad(set_to_none=True)   # 1. clear old grads
        logits = model(xb)                       # 2. forward
        loss = criterion(logits, yb)             # 3. compute loss
        loss.backward()                          # 4. backprop
        optimizer.step()                         # 5. update weights

        running += loss.item() * xb.size(0)
    scheduler.step()

    # ---- validation ----
    model.eval()
    correct = total = 0
    with torch.no_grad():
        for xb, yb in val_loader:
            xb, yb = xb.to(device), yb.to(device)
            pred = model(xb).argmax(dim=1)
            correct += (pred == yb).sum().item()
            total += yb.size(0)
    print(f"epoch {epoch}: loss={running/len(train_ds):.4f} acc={correct/total:.3f}")
zero_grad-> forward-> loss-> backward-> step

Mixed Precision (AMP)

from torch.amp import autocast, GradScaler

scaler = GradScaler("cuda")
for xb, yb in train_loader:
    xb, yb = xb.to(device), yb.to(device)
    optimizer.zero_grad(set_to_none=True)
    with autocast("cuda", dtype=torch.float16):   # or bfloat16
        loss = criterion(model(xb), yb)
    scaler.scale(loss).backward()      # scale to avoid fp16 underflow
    scaler.step(optimizer)
    scaler.update()
Why AMP runs most ops in fp16/bf16 for ~2x speed and ~half the memory on modern GPUs, keeping a fp32 master copy for stability.

Saving & Loading Checkpoints

Save the state_dict (a dict of tensors), not the whole model object — it is portable and version-robust.

# Save a full training checkpoint
torch.save({
    "epoch": epoch,
    "model_state": model.state_dict(),
    "optim_state": optimizer.state_dict(),
    "scheduler_state": scheduler.state_dict(),
    "best_acc": best_acc,
}, "checkpoint.pt")

# Restore
ckpt = torch.load("checkpoint.pt", map_location=device, weights_only=True)
model.load_state_dict(ckpt["model_state"])
optimizer.load_state_dict(ckpt["optim_state"])
start_epoch = ckpt["epoch"] + 1
Security As of recent PyTorch, pass weights_only=True to torch.load for untrusted files — the default was flipped to True to block arbitrary-code execution via pickle. Only disable it for files you fully trust.

Worked Mini-Example: XOR in 30 Lines

Show the full runnable example
import torch, torch.nn as nn, torch.optim as optim

X = torch.tensor([[0.,0.],[0.,1.],[1.,0.],[1.,1.]])
y = torch.tensor([[0.],[1.],[1.],[0.]])

model = nn.Sequential(
    nn.Linear(2, 8), nn.Tanh(),
    nn.Linear(8, 1),
)
criterion = nn.BCEWithLogitsLoss()
opt = optim.Adam(model.parameters(), lr=0.05)

for step in range(2000):
    opt.zero_grad()
    loss = criterion(model(X), y)
    loss.backward()
    opt.step()

model.eval()
with torch.inference_mode():
    preds = (torch.sigmoid(model(X)) > 0.5).float()
print(preds.squeeze().tolist())   # [0.0, 1.0, 1.0, 0.0]

Best Practices & Common Pitfalls

Do Use zero_grad(set_to_none=True), pass logits to CrossEntropyLoss (never pre-softmax), seed RNGs for reproducibility, and move the model to the device before constructing the optimizer.
Do Profile with torch.profiler and prefer AdamW + a cosine schedule as a strong modern default. Checkpoint every epoch and keep the best-by-validation copy.
Avoid Calling .cuda() on data but not the model (device mismatch); accumulating loss tensors instead of .item(); forgetting eval(); applying softmax before CrossEntropyLoss.
Never Load untrusted checkpoints with weights_only=False, and never leave requires_grad=True on inputs during inference — it silently builds graphs and wastes memory.

Interview Questions & Answers

What is the difference between a dynamic and a static computation graph, and which does PyTorch use?
PyTorch builds a dynamic (define-by-run) graph: the graph is constructed as the forward pass executes, so Python control flow works naturally and debugging is easy. Static-graph frameworks define the whole graph first, then execute it — faster to optimize but harder to debug. torch.compile now gives PyTorch much of the static-graph performance while keeping the eager programming model.
Why must you call optimizer.zero_grad() each iteration?
Because .backward() accumulates gradients into .grad rather than overwriting them. Without zeroing, each step uses the sum of all previous gradients, corrupting training. (Accumulation is intentional — it lets you simulate larger batches by delaying the step.)
What does requires_grad do, and what is a leaf tensor?
requires_grad=True tells autograd to track operations on that tensor so gradients can be computed. A leaf is a tensor created directly by the user (e.g. model parameters) rather than as the result of an op; only leaves with requires_grad accumulate .grad after backward().
When would you use torch.no_grad() vs detach() vs torch.inference_mode()?
no_grad() is a context that disables graph tracking for everything inside — used during validation. detach() returns a single tensor cut off from the graph. inference_mode() is like no_grad but even faster because it also skips view/version tracking; use it for pure forward-only inference.
Why pass raw logits to CrossEntropyLoss instead of softmax probabilities?
nn.CrossEntropyLoss fuses LogSoftmax + NLLLoss internally for numerical stability (the log-sum-exp trick avoids overflow/underflow). Applying softmax yourself first double-counts the normalization and produces wrong, unstable gradients.
What is the difference between model.train() and model.eval()?
They toggle layer behaviour. In train(), Dropout randomly zeros activations and BatchNorm uses per-batch statistics while updating running estimates. In eval(), Dropout is a no-op and BatchNorm uses the stored running mean/variance. They do not disable gradients — pair eval() with no_grad().
How do view() and reshape() differ?
view() returns a tensor sharing the same storage and requires the data to be contiguous — it only changes strides. reshape() returns a view when possible but silently copies when the layout prevents a view. Use view() when you want to guarantee no copy, reshape() when you just want the shape.
What causes a CUDA out-of-memory error and how do you reduce memory?
Common causes: batch size too large, holding onto tensors still attached to the graph (e.g. accumulating loss instead of loss.item()), or retaining the graph with retain_graph=True. Fixes: lower batch size, use AMP, gradient accumulation, torch.no_grad() for eval, gradient checkpointing, and free references so Python can garbage-collect.
Why save state_dict() rather than the whole model?
A state_dict is just an OrderedDict of tensors — it is portable, inspectable, and does not pickle your class definitions or file paths. Saving the whole model via pickle breaks if you refactor the class or move modules, and is a code-execution security risk on load.
What does torch.compile do and when should you use it?
It traces your model with TorchDynamo and compiles fused kernels via TorchInductor, typically giving a sizeable speedup with one line and no rewrite. Use it once your model is correct and stable; expect a slow first iteration (compilation) and watch for recompilations caused by changing input shapes (control with dynamic=True).
How does DistributedDataParallel differ from DataParallel?
DataParallel runs on one process, splitting a batch across GPUs with a single Python GIL — simple but slow and now discouraged. DistributedDataParallel runs one process per GPU, each with its own data shard, syncing gradients via all-reduce. DDP scales far better across GPUs and nodes and is the recommended approach.
What is gradient accumulation and why is it useful?
Instead of calling optimizer.step() every batch, you run backward() on several small batches (letting grads accumulate) and step once every N batches, dividing loss by N. This simulates a batch N times larger than fits in memory — crucial for training big models on limited GPUs.
