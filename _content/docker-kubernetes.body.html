Why Containers Won

Before containers, shipping software to a customer meant shipping a document. "Install Python 3.9, these 40 packages, this version of libssl, set these six environment variables, and make sure the locale is UTF-8." Half of it was wrong, the other half was undocumented tribal knowledge, and the first deployment call ran four hours. A container image replaces that document with an artifact: one file, one hash, byte-identical on your laptop and in the customer's data centre.

What a container actually is

There is no "container" object in the Linux kernel. A container is an ordinary process that has been started with a particular arrangement of three long-standing kernel features:

Namespaces

Isolate what the process can see: PID (its own process tree, where your app is PID 1), mount (its own filesystem view), network (its own interfaces and ports), UTS (hostname), IPC, user (UID mapping), cgroup.

cgroups

Limit what the process can use: CPU shares and quota, memory ceiling, block I/O weight, PIDs count. This is what makes --memory=512m enforceable rather than advisory.

Union filesystem

Stack read-only image layers with a thin writable layer on top via overlayfs. Ten containers from one image share the same underlying bytes on disk until they write.

A VM virtualises hardware and runs a full guest kernel — gigabytes of image, tens of seconds to boot, strong isolation. A container shares the host kernel — megabytes, sub-second start, weaker isolation. That kernel sharing has two consequences you will explain to customers repeatedly: a Linux container cannot run on a Windows kernel without a Linux VM underneath (which is exactly what Docker Desktop and WSL2 provide), and a container escape is a host compromise, which is why security teams care about what runs as root inside.

The structural difference: a duplicated kernel per workload versus one shared kernel with isolated views.

Images, Layers, Registries, Tags and Digests

Understanding the layer model is what separates a 1.2 GB image that rebuilds in four minutes from a 90 MB image that rebuilds in eight seconds. It also explains why the secret you deleted in a later layer is still in the image.

The layer model

Each instruction in a Dockerfile that changes the filesystem (RUN, COPY, ADD) produces a new read-only layer containing only the delta. Metadata-only instructions (ENV, WORKDIR, EXPOSE, LABEL, USER, CMD, ENTRYPOINT) change the image config, not the filesystem. At runtime, overlayfs stacks the layers and adds a thin writable layer on top. Writing to a file that exists in a lower layer triggers a copy-up: the whole file is copied into the writable layer first.

Deleting a file does not shrink the imageRUN wget secrets.tar && tar xf secrets.tar && rm secrets.tar in three separate RUN instructions leaves the tarball permanently in layer 1. The later rm only writes a whiteout marker in a higher layer — anyone can docker save the image and extract it. The same applies to ARG-injected tokens, .git directories, and ~/.aws/credentials copied in by an over-broad COPY . .. Fix it by doing the download, use and delete in one RUN, by using a multi-stage build, or by using BuildKit secret mounts.

Tags versus digests

A tag is a mutable pointer. :latest is just a tag with a conventional name and no special meaning — nothing guarantees it is the newest. A digest is the SHA-256 of the image manifest: content-addressable, immutable, verifiable. If you pull by digest you provably get the same bytes every time.

Writing a Dockerfile Properly

Most Dockerfiles in the wild are a transliteration of a README. A good one is engineered around two things the engine actually cares about: the order of layers for cache reuse, and what ends up in the final filesystem.

Instruction by instruction

ENTRYPOINT vs CMD, and the PID 1 signal problem

# exec form - argv array, no shell, signals reach your process
ENTRYPOINT ["/usr/local/bin/uvicorn"]
CMD ["app.main:app", "--host", "0.0.0.0", "--port", "8080"]

# shell form - runs as: /bin/sh -c "uvicorn app.main:app"
# sh becomes PID 1, forwards NOTHING, your app never sees SIGTERM
ENTRYPOINT uvicorn app.main:app        # avoid

With exec form, docker run myapp --port 9090 replaces CMD and runs uvicorn --port 9090. With no ENTRYPOINT and only CMD ["python","app.py"], docker run myapp bash gives you a shell — handy for debugging. Choose ENTRYPOINT when the image is a single-purpose tool, CMD-only when you want it to double as a general runtime.

Zombie reapingIf your process spawns children and is PID 1, it must reap them or you accumulate zombies until the PID limit. Either handle SIGCHLD properly in the app, or add a tiny init: docker run --init (injects tini), or ENTRYPOINT ["/sbin/tini","--","./app"], or in Kubernetes rely on the fact that most frameworks handle it — but verify with ps -ef inside the container under load.

Layer caching: the single highest-leverage idea

Docker reuses a cached layer when the instruction string is identical and, for COPY/ADD, the checksum of the copied files is unchanged. The moment one layer misses, every layer after it rebuilds. Therefore: order from least-frequently-changed to most-frequently-changed.

# BAD - every source edit reinstalls 200 MB of dependencies
FROM python:3.12-slim
WORKDIR /app
COPY . .
RUN pip install -r requirements.txt
CMD ["python", "app.py"]

# GOOD - dependency layer survives source edits
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
CMD ["python", "app.py"]

Same idea in every ecosystem: COPY package.json package-lock.json ./ then RUN npm ci then COPY . .; COPY go.mod go.sum ./ then RUN go mod download then COPY . .; COPY pom.xml . then RUN mvn -B dependency:go-offline then COPY src ./src.

# One RUN, cleaned up in the same layer - the apt idiom
RUN apt-get update \
 && apt-get install -y --no-install-recommends \
      curl ca-certificates libpq5 \
 && rm -rf /var/lib/apt/lists/*

--no-install-recommends typically saves 50–150 MB. The rm -rf /var/lib/apt/lists/* must be in the same RUN or the cache files are already committed to a layer. On RHEL-family bases the equivalent is microdnf install -y … && microdnf clean all; on Alpine, apk add --no-cache does it in one flag.

BuildKit cache mounts and secrets

# syntax=docker/dockerfile:1.7
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
# Persist the pip cache ACROSS builds without baking it into a layer
RUN --mount=type=cache,target=/root/.cache/pip \
    pip install -r requirements.txt

# A secret that is mounted during the RUN and never recorded in any layer
RUN --mount=type=secret,id=netrc,target=/root/.netrc \
    pip install --extra-index-url https://nexus.corp/simple internal-sdk==2.1.0

DOCKER_BUILDKIT=1 docker build --secret id=netrc,src=$HOME/.netrc -t myapp:1.4.2 .

Cache mounts are the difference between a 4-minute and a 25-second rebuild on a slow customer network. Secret mounts are the correct way to use a private package index token at build time without it appearing in docker history.

Multi-Stage Builds, Slim Bases, and Non-Root

A build toolchain is not a runtime dependency. Multi-stage builds let you compile with gcc, Maven or the full Node toolchain and then ship only the artifact. Typical result: 1.1 GB becomes 120 MB, and the CVE count drops by an order of magnitude because there is nothing left to be vulnerable.

Python — compile wheels, ship a venv

# syntax=docker/dockerfile:1.7
FROM python:3.12-slim AS builder
ENV PIP_DISABLE_PIP_VERSION_CHECK=1 PYTHONDONTWRITEBYTECODE=1
RUN apt-get update && apt-get install -y --no-install-recommends \
      build-essential libpq-dev gcc \
 && rm -rf /var/lib/apt/lists/*
WORKDIR /app
COPY requirements.txt .
RUN python -m venv /opt/venv
ENV PATH="/opt/venv/bin:$PATH"
RUN --mount=type=cache,target=/root/.cache/pip \
    pip install -r requirements.txt

# ---------- runtime ----------
FROM python:3.12-slim AS runtime
RUN apt-get update && apt-get install -y --no-install-recommends \
      libpq5 curl ca-certificates \
 && rm -rf /var/lib/apt/lists/* \
 && groupadd -r app -g 10001 \
 && useradd -r -u 10001 -g app -d /app -s /sbin/nologin app
COPY --from=builder /opt/venv /opt/venv
ENV PATH="/opt/venv/bin:$PATH" \
    PYTHONUNBUFFERED=1 \
    PYTHONDONTWRITEBYTECODE=1
WORKDIR /app
COPY --chown=app:app ./app ./app
USER 10001
EXPOSE 8080
HEALTHCHECK --interval=30s --timeout=3s --start-period=20s --retries=3 \
  CMD curl -fsS http://127.0.0.1:8080/healthz || exit 1
ENTRYPOINT ["uvicorn"]
CMD ["app.main:app", "--host", "0.0.0.0", "--port", "8080"]

gcc, build-essential and libpq-dev exist only in the builder stage and never reach the final image — that alone removes roughly 400 MB and dozens of CVEs.

FROM node:20-bookworm-slim AS deps

Non-root, properly

RUN groupadd -r app -g 10001 \
 && useradd -r -u 10001 -g app -d /app -s /sbin/nologin app
COPY --chown=app:app . /app
USER 10001:10001           # numeric UID, so Kubernetes runAsNonRoot can verify it

Use a numeric UID: runAsNonRoot: true in a Pod spec cannot resolve a username to a UID and will refuse to start the container with CreateContainerConfigError: container has runAsNonRoot and image has non-numeric user. Pick a high UID (10000+) to avoid colliding with host users. A non-root process cannot bind ports below 1024, so listen on 8080 and map it — in Kubernetes a Service maps 80 to 8080 transparently.

Running Containers

The run-time flags are where theory meets the customer's host. Get ports, mounts, environment and limits right and most "it doesn't work here" problems never happen.

docker run -d \
  --name api \
  --restart unless-stopped \
  -p 127.0.0.1:8080:8080 \
  -e APP_ENV=prod \
  --env-file ./prod.env \
  -v api-data:/var/lib/app \
  -v /etc/ssl/corp-root.pem:/etc/ssl/certs/corp-root.pem:ro \

  --cpus 1.5 \
  --pids-limit 256 \
  --read-only --tmpfs /tmp:rw,noexec,nosuid,size=128m \

  --health-cmd 'curl -fsS http://127.0.0.1:8080/healthz || exit 1' \
  --health-interval 30s --health-timeout 3s --health-retries 3 \
  registry.corp/platform/api:1.4.2

Bind-mount permission deniedThe container's UID must be able to read the host path. If the container runs as UID 10001 and the host directory is 0700 root:root, it fails regardless of what is inside. "The API container can't reach the database container" is the Compose-era version of the connectivity problem. Three facts resolve nearly all of it: which network each container is on, what name DNS resolves, and which port the process inside is actually bound to.

On a user-defined bridge, db resolves to the database container's IP from inside api — that is Docker's embedded DNS at 127.0.0.11. It does not work on the default bridge, which is why beginners end up using the deprecated --link.

localhost inside a container is the containerDB_HOST=localhost in a container means "this container", not the host and not the database container. Use the service name on a shared network. To reach a service on the host machine, use host.docker.internal (Docker Desktop, and on Linux with --add-host=host.docker.internal:host-gateway) or the bridge gateway IP. And remember the port you connect to is the container's port, not the published host port: api talks to db:5432 even if the host mapping is 15432:5432.
# Debug from inside, without installing anything in the app image

docker run --rm -it --network container:api nicolaka/netshoot ss -tulpn

That last form is the one to remember: it puts a fully-equipped debug container inside the exact network namespace of your minimal distroless app container, so ss, tcpdump and curl all see what the app sees — without adding a single byte to the production image.

"It works on my machine" — the real failure modes

Architecture mismatch

Built arm64 on a Mac, ran on amd64. Symptom: exec format error or exec /app: no such file or directory on a binary that clearly exists. Fix: docker buildx build --platform linux/amd64. Check with docker image inspect --format '{{.Architecture}}'.

Stale build cache

A RUN apt-get update layer cached from last month installs stale packages, or a COPY cache hit hides a changed file. Confirm with docker build --no-cache.

Missing runtime library

Works in the builder stage, fails in runtime because libpq5 was never installed in the final stage. Symptom: ImportError: libpq.so.5: cannot open shared object file. Check with ldd inside the image.

Env present locally, absent in the image

Your shell exported OPENAI_API_KEY; the container never received it. docker exec api env | sort is the one-command check.

Bound to 127.0.0.1 inside

The app listens on loopback inside its own namespace, so the published port connects to nothing. It must bind 0.0.0.0. Verify with docker exec api ss -tulpn.

File permissions after USER

COPY without --chown leaves files owned by root; the app runs as UID 10001 and cannot write its cache directory. docker exec -u 10001 api touch /app/cache/x reproduces it instantly.

Corporate CA missing

Outbound HTTPS fails with "unknown authority" because the image trusts public roots only. Copy the corporate root into the image or mount it, and set REQUESTS_CA_BUNDLE / NODE_EXTRA_CA_CERTS / SSL_CERT_FILE.

Clock and timezone

Containers inherit the host clock but default to UTC. Signature validation and JWT expiry fail if the host clock drifts. docker exec api date -u versus the host.

The Kubernetes Mental Model

Kubernetes is a control loop over a declarative API. You write down the state you want; a set of controllers continuously compares that to reality and acts to close the gap. Every object, every failure mode and every debugging step makes sense once you hold that one idea firmly.

You never create a container. You record intent; controllers make reality match it, continuously.

Why it exists (the honest version)

Kubernetes solves scheduling across many machines, self-healing when a node dies, rolling updates with health gating, service discovery and load balancing, declarative configuration with rollback, and horizontal autoscaling — all behind one API with a consistent extension model. That is a genuinely large amount of operational work it removes.

And when it is the wrong answerA single-service prototype on one VM does not need a cluster; systemd or Compose is less to run, less to secure and less to explain. If the customer has no platform team, introducing Kubernetes transfers an operational burden they cannot carry after you leave. The FDE judgement is to match the platform to what the customer can actually operate on their own — and to say so out loud even when they asked for Kubernetes by name.

Core Objects, With Worked YAML

You will spend most of your Kubernetes time with about ten object types. Here is each one, what it is for, and YAML you can adapt rather than invent.

Pod — the unit of scheduling

A Pod is one or more containers that share a network namespace (same IP, same localhost, same port space) and can share volumes. You rarely create one directly; you create a Deployment that creates them. But understanding the Pod spec is essential because every higher object embeds it as template.

apiVersion: v1
kind: Pod
metadata:
  name: debug-shell
  namespace: ragdemo
  labels: { app: debug }
spec:
  terminationGracePeriodSeconds: 5
  securityContext:
    runAsNonRoot: true
    runAsUser: 10001
    fsGroup: 10001
    seccompProfile: { type: RuntimeDefault }
  containers:
    - name: shell
      image: nicolaka/netshoot:latest
      command: ["sleep", "3600"]
      securityContext:
        allowPrivilegeEscalation: false
        readOnlyRootFilesystem: true
        capabilities: { drop: ["ALL"] }
      resources:
        requests: { cpu: 50m, memory: 64Mi }
        limits:   { cpu: 200m, memory: 256Mi }
      volumeMounts:
        - { name: tmp, mountPath: /tmp }
  volumes:
    - name: tmp
      emptyDir: { sizeLimit: 64Mi }

Multi-container patterns worth knowing: a sidecar runs alongside (log shipper, proxy); an init container runs to completion before app containers start (schema migration, waiting for a dependency, fetching config); an ambassador proxies outbound connections. Containers in a Pod are always co-scheduled on one node — that is the defining property.

Deployment — what you actually write

Deployment manages ReplicaSets; a ReplicaSet manages Pods. On an update, the Deployment creates a new ReplicaSet and shifts replicas across according to the rollout strategy, keeping old ReplicaSets around for rollback.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: rag-api
  namespace: ragdemo
  labels: { app.kubernetes.io/name: rag-api, app.kubernetes.io/version: "1.4.2" }
spec:
  replicas: 3
  revisionHistoryLimit: 5
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1          # at most 1 extra pod above replicas during rollout
      maxUnavailable: 0    # never drop below 3 ready - zero-downtime
  selector:
    matchLabels: { app: rag-api }      # IMMUTABLE after creation
  template:
    metadata:
      labels: { app: rag-api }
      annotations:
        prometheus.io/scrape: "true"
        prometheus.io/port: "8080"
        checksum/config: "{{ sha256sum of the ConfigMap }}"   # forces rollout on config change
    spec:
      serviceAccountName: rag-api
      imagePullSecrets:
        - name: corp-registry
      securityContext:
        runAsNonRoot: true
        runAsUser: 10001
        fsGroup: 10001
        seccompProfile: { type: RuntimeDefault }
      topologySpreadConstraints:
        - maxSkew: 1
          topologyKey: kubernetes.io/hostname
          whenUnsatisfiable: ScheduleAnyway
          labelSelector:
            matchLabels: { app: rag-api }
      initContainers:
        - name: wait-for-db
          image: busybox:1.36
          command: ['sh','-c','until nc -z postgres 5432; do echo waiting; sleep 2; done']
      containers:
        - name: api
          image: registry.corp/platform/rag-api@sha256:9f2c1a3b7e4d5c6a8b9f0e1d2c3b4a5968778899aabbccddeeff00112233445566
          imagePullPolicy: IfNotPresent
          ports:
            - { name: http, containerPort: 8080, protocol: TCP }
          env:
            - name: LOG_LEVEL
              valueFrom: { configMapKeyRef: { name: rag-api-config, key: log_level } }
            - name: DATABASE_PASSWORD
              valueFrom: { secretKeyRef: { name: rag-api-secrets, key: db_password } }
            - name: POD_NAME
              valueFrom: { fieldRef: { fieldPath: metadata.name } }
            - name: NODE_NAME
              valueFrom: { fieldRef: { fieldPath: spec.nodeName } }
          envFrom:
            - configMapRef: { name: rag-api-config }
          resources:
            requests: { cpu: 250m, memory: 512Mi }
            limits:   { cpu: "2",  memory: 2Gi }
          startupProbe:
            httpGet: { path: /healthz, port: http }
            failureThreshold: 30
            periodSeconds: 5          # allows up to 150 s to start
          readinessProbe:
            httpGet: { path: /readyz, port: http }
            initialDelaySeconds: 5
            periodSeconds: 10
            timeoutSeconds: 2
            failureThreshold: 3
          livenessProbe:
            httpGet: { path: /healthz, port: http }
            periodSeconds: 20
            timeoutSeconds: 3
            failureThreshold: 3
          lifecycle:
            preStop:
              exec: { command: ["sh","-c","sleep 5"] }   # let endpoints drain first
          securityContext:
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            capabilities: { drop: ["ALL"] }
          volumeMounts:
            - { name: cache, mountPath: /app/.cache }
            - { name: tmp,   mountPath: /tmp }
            - { name: corp-ca, mountPath: /etc/ssl/certs/corp-root.pem, subPath: corp-root.pem, readOnly: true }
      volumes:
        - name: cache
          emptyDir: { sizeLimit: 512Mi }
        - name: tmp
          emptyDir: { sizeLimit: 128Mi }
        - name: corp-ca
          configMap: { name: corp-ca-bundle }
      terminationGracePeriodSeconds: 45
The preStop sleep is not a hackWhen a Pod is deleted, two things happen in parallel: the kubelet sends SIGTERM, and the endpoints controller removes the Pod from Service endpoints. The second propagates to every kube-proxy asynchronously, so for a second or two traffic still arrives at a shutting-down Pod. A short preStop sleep plus a graceful shutdown in the app removes the 502 spike that customers notice during every deploy.

apiVersion: networking.k8s.io/v1
kind: Ingress

Kubernetes Secrets are base64, not encryptionAnyone with get secret RBAC in the namespace, or read access to etcd, can recover the plaintext. Scheduling and Reliability

Requests and limits are the two numbers that determine whether your workload gets scheduled, whether it gets throttled, and whether it gets killed first when a node runs out of memory. Most production incidents in a customer cluster trace back to these being wrong or absent.

Requests versus limits

resources:
  requests:            # used by the SCHEDULER to pick a node; a reservation
    cpu: 250m          # 0.25 of a core
    memory: 512Mi
  limits:              # enforced by the KERNEL via cgroups at runtime
    cpu: "2"
    memory: 2Gi

CPU is compressible: exceeding the limit causes throttling (the process is paused within each 100 ms period), not termination. Memory is not compressible: exceeding the limit causes an immediate OOM kill with exit code 137. That asymmetry drives the standard advice — set memory request equal to memory limit, and be generous or omit CPU limits entirely if latency matters more than noisy-neighbour fairness.

QoS classConditionEviction order under node pressure
GuaranteedEvery container has requests == limits for both CPU and memoryEvicted last
BurstableAt least one request set, but not matching limitsEvicted second, worst-offender-over-request first
BestEffortNo requests or limits at allEvicted first, always
kubectl get pod rag-api-xk2mq -o jsonpath='{.status.qosClass}'
kubectl describe node ip-10-0-3-21 | sed -n '/Allocated resources/,/^Events/p'
# Resource  Requests      Limits
# cpu       3250m (81%)   9 (225%)       <- overcommitted on limits; fine, but watch throttling
# memory    7409Mi (62%)  16Gi (137%)
kubectl top pod --containers -n ragdemo
CPU limits cause latency you will be blamed forA pod with limits.cpu: "1" that briefly needs 1.5 cores is throttled — the kernel freezes it for the rest of the 100 ms period. The symptom is p99 latency spikes with CPU utilisation that looks comfortable. Check container_cpu_cfs_throttled_seconds_total in Prometheus. For latency-sensitive services, many teams set requests carefully and omit CPU limits entirely.

HPA utilisation is calculated against the CPU request, not the limit — so a tiny request makes the HPA scale out constantly. A PDB constrains voluntary disruptions only: node drains, cluster upgrades, descheduler evictions. It does not protect against a node crashing. Set one for anything the customer considers production, or their next cluster upgrade will drain all your replicas simultaneously.

Placement: affinity, taints, tolerations

spec:
  nodeSelector: { "node.kubernetes.io/instance-type": "g5.xlarge" }
  tolerations:
    - key: "nvidia.com/gpu"
      operator: "Exists"
      effect: "NoSchedule"
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
          - matchExpressions:
              - { key: topology.kubernetes.io/zone, operator: In, values: [ap-south-1a, ap-south-1b] }
    podAntiAffinity:
      preferredDuringSchedulingIgnoredDuringExecution:
        - weight: 100
          podAffinityTerm:
            topologyKey: kubernetes.io/hostname
            labelSelector:
              matchLabels: { app: rag-api }

A taint on a node repels pods; a toleration on a pod lets it ignore a specific taint. That is how GPU nodes, spot instances and dedicated node pools are reserved. Effects: NoSchedule (do not place new pods), PreferNoSchedule (soft), NoExecute (also evict pods already running). Anti-affinity on kubernetes.io/hostname spreads replicas across nodes so one node failure does not take the whole service down — use preferred rather than required on small clusters or your pods will sit Pending.

You are a guest in a cluster someone else is accountable for. Everything you deploy will be reviewed against their policy. Knowing the controls in advance means you write compliant manifests the first time instead of iterating through rejections for a week.

PodSecurityPolicy was removed in 1.25. Its replacement, Pod Security Admission, is a namespace label enforcing one of three profiles.

CrashLoopBackOff

The container starts and exits repeatedly; the kubelet backs off exponentially (10 s, 20 s, 40 s … capped at 5 min). CrashLoopBackOff is a symptom, never a cause — the cause is in the previous container's output.

kubectl logs rag-api-xk2mq --previous          # THE command for this state
kubectl get pod rag-api-xk2mq -o jsonpath='{.status.containerStatuses[0].lastState.terminated}' | jq

kubectl describe pod rag-api-xk2mq | grep -E 'Last State|Exit Code|Reason|Restart Count'
  • Exit 1 with a stack trace — application config error: missing env var, bad DSN, unreachable dependency
  • Exit 137 with OOMKilled — memory limit too low, or a real leak. Raise the limit once to confirm, then investigate properly
  • Exit 127 — command not found; wrong path or a distroless image with no shell for a shell-form command
  • Exit 126 — not executable; missing chmod +x or CRLF line endings in an entrypoint script
  • Exit 0 immediately — your command finished; the process daemonised itself or the CMD is wrong
  • No logs at all — the failure is before your code runs: check describe for mount and secret errors

Deploying Into a Customer's Environment

The technical work is often the easy half. Getting your image through an air gap, past a security review, and running inside a policy-enforced namespace with no egress is the part that determines whether the engagement lands on time.

Air-gapped registries

  1. Enumerate every imageNot just yours — Postgres, Redis, the vector store, ingress-nginx, cert-manager, the metrics server, every sidecar, and every init container. helm template . | grep -Eo 'image: .*' | sort -u is the starting point, and kubectl get pods -A -o jsonpath='{..image}' | tr ' ' '\n' | sort -u catches what you missed.
  2. Pin to digestsResolve every tag to a digest before you mirror, so what you validated is provably what ships.
  3. Mirrorskopeo copy --all docker://upstream/img:tag docker://registry.corp/mirror/img:tag — --all preserves the multi-arch manifest list. For a true air gap, skopeo sync --src docker --dest dir to a directory, carry it across, then skopeo sync --src dir --dest docker.
  4. Rewrite referencesHelm values with an image.registry prefix, or a Kustomize images: block, or a cluster-wide ImageContentSourcePolicy / containerd mirror config so the rewrite happens at the node.

The pre-flight checklist before you ask for a deployment window

  • Image mirrored to the internal registry, pinned by digest, scanned, SBOM attached
  • Runs as a numeric non-root UID with allowPrivilegeEscalation: false and drop: ALL
  • readOnlyRootFilesystem: true with emptyDir volumes for every writable path
  • CPU and memory requests and limits set on every container — a ResourceQuota will reject you otherwise
  • Startup, readiness and liveness probes defined, with the startup probe sized for the real cold-start time
  • PodDisruptionBudget and anti-affinity so the next cluster upgrade does not take you down
  • NetworkPolicy written, including the DNS egress rule, and tested in a namespace with default-deny
  • Secrets sourced from the customer's vault, not from a manifest in git
  • Corporate CA mounted and the right per-runtime env var set
  • Proxy variables set with a complete NO_PROXY
  • Manifests render cleanly through their policy engine: kubectl apply --dry-run=server
  • Rollback path rehearsed: helm rollback or kubectl rollout undo, tested in staging
  • Logs go to stdout in the format their aggregation stack expects; metrics exposed on a scrapeable port
  • A one-page runbook: what it is, what it depends on, how to restart it, who to call

Interview Questions

These come up constantly in FDE, platform and SRE loops. Answer with the mechanism, then the operational consequence — that combination is what distinguishes someone who has run this in production.

What is a container, really? How is it different from a VM?
A container is a normal Linux process that the kernel has placed into a set of namespaces and cgroups. Namespaces control what it can see — PID namespace so it has its own process tree with your app as PID 1, mount namespace for its own filesystem view, network namespace for its own interfaces and port space, plus UTS, IPC and user namespaces. cgroups control what it can consume — CPU quota, memory ceiling, I/O weight, PID count. The filesystem comes from stacked read-only image layers plus a thin writable layer, usually via overlayfs. A VM, by contrast, virtualises hardware and boots a complete guest kernel on a hypervisor. The practical differences follow directly: containers start in under a second and cost megabytes because there is no kernel to boot; they share the host kernel, so a Linux container cannot run natively on Windows and a kernel exploit from inside a container compromises the host. That last point is why customers care about running as non-root, dropping capabilities, and seccomp profiles — and why workloads with hard multi-tenancy requirements sometimes use Kata Containers or Firecracker to get a lightweight VM boundary back.
Your image is 1.4 GB. How do you get it under 200 MB?
First I measure where it actually went with docker history and dive, because guessing wastes time. Then, in rough order of impact: introduce a multi-stage build so compilers and dev headers — build-essential, gcc, libpq-dev, the full Node toolchain — exist only in the builder stage and never reach the runtime image; that is typically 400–600 MB on its own. Switch the final stage to a slim or distroless base. Collapse package installation into a single RUN with --no-install-recommends and rm -rf /var/lib/apt/lists/* in the same layer, since cleanup in a later layer frees nothing. Add a proper .dockerignore so .git, node_modules, test fixtures and local virtualenvs never enter the build context. For Node, npm prune --omit=dev after the build; for Python, install into a venv in the builder and copy only the venv. I would be cautious about jumping to Alpine for a Python service — musl means no manylinux wheels, so pip compiles from source and the image can end up larger and far slower to build. And I would verify the result with a CVE scan, because the size reduction usually drops the vulnerability count by an order of magnitude too, which is what the customer's security review actually cares about.
Walk me through what happens when you run kubectl apply -f deployment.yaml.
kubectl reads the file, merges it with the previous applied configuration annotation, and sends a request to the kube-apiserver. The apiserver authenticates the caller, authorises via RBAC, runs mutating admission webhooks (which might inject a sidecar or defaults), validates the object against the schema, runs validating admission webhooks and Pod Security Admission, then persists it to etcd. The Deployment controller is watching Deployments; it sees the new spec and creates or updates a ReplicaSet with a pod-template hash. The ReplicaSet controller sees a replica count it has not satisfied and creates Pod objects with nodeName unset. The scheduler watches for unscheduled Pods, filters nodes by resource requests, taints, affinity and volume topology, scores the survivors, and binds the Pod to a node. The kubelet on that node sees a Pod bound to it, pulls the image through containerd, sets up the sandbox and CNI networking, mounts volumes, starts the containers, and begins running probes. Once readiness passes, the endpoints controller adds the Pod IP to the Service's EndpointSlice, kube-proxy programs iptables or IPVS rules on every node, and traffic starts flowing. Every one of those stages is a place it can get stuck, which is exactly why kubectl describe and the Events list are the first things I read when a Pod is not where I expect it.
A pod is in CrashLoopBackOff. Diagnose it.
CrashLoopBackOff is never the cause, only the kubelet's exponential backoff after repeated exits. The first command is kubectl logs <pod> --previous, because plain logs shows the current container which may have just started and printed nothing. In parallel I read kubectl get pod -o jsonpath='{.status.containerStatuses[0].lastState.terminated}' for the exit code and reason. Exit 1 with a stack trace is an application or configuration failure — a missing environment variable, a bad connection string, a dependency that is not up. Exit 137 with reason OOMKilled means it exceeded its memory limit; I raise it once to confirm the diagnosis and then look at whether it is a genuine leak or just a limit set from a guess. Exit 127 is command not found — often a shell-form command in a distroless image. Exit 126 is not executable, frequently CRLF line endings in an entrypoint script written on Windows. Exit 0 immediately means the process completed, so the CMD is wrong or the app daemonised itself. If there are no logs at all, the failure is before my code runs, so I go to describe and look for mount failures, missing secrets or ConfigMaps. To get hands-on I either run the image with --command -- sleep 3600 so it stays up, or attach an ephemeral debug container with kubectl debug --target, which works even on a distroless image with no shell.
Explain requests versus limits, and what happens when each is exceeded.
Requests are what the scheduler uses to decide whether a Pod fits on a node; they are a reservation and the node's allocatable capacity is divided among them. Limits are enforced at runtime by the kernel through cgroups. The two resources behave completely differently. CPU is compressible: exceeding the limit causes CFS throttling — the process is frozen for the remainder of each 100 ms period — so the symptom is latency, not failure, and it is invisible in average CPU utilisation. Memory is incompressible: exceeding the limit means an immediate OOM kill with exit code 137 and no chance to clean up. The combination also determines QoS class: requests equal to limits on every container gives Guaranteed, which is evicted last under node pressure; some requests set gives Burstable; nothing set gives BestEffort, which is evicted first. My practical defaults are memory request equal to memory limit so the pod is predictable and never surprises the node, a CPU request based on measured steady-state usage, and a CPU limit that is either generous or absent for latency-sensitive services because throttling causes p99 spikes that customers notice. I also check whether the runtime honours the cgroup — an older JVM or a library sizing thread pools from os.cpu_count() will read host values and badly over-provision inside a small limit.
Difference between liveness, readiness and startup probes?
Readiness controls traffic: if it fails, the Pod is removed from the Service's endpoints and receives no requests, but it is not restarted. Liveness controls lifecycle: if it fails, the kubelet kills and restarts the container. Startup gates the other two: while it is running, liveness and readiness are suspended, which is how you protect a slow-starting application without having to set a huge initialDelaySeconds on liveness. The classic production incident comes from pointing a liveness probe at an endpoint that checks the database — when the database has a brief hiccup, every replica fails liveness simultaneously, all restart, the cold-start thundering herd hits the database again, and a five-second blip becomes a twenty-minute outage. So liveness should test only "is this process alive and not deadlocked", with no external dependencies; readiness is where it is safe to check dependencies, because the only consequence is traffic shedding. I also make sure readiness fails during shutdown and pair it with a short preStop sleep, since endpoint removal propagates asynchronously and without that gap you get a burst of 502s on every deploy.
How does a request get from an external user to a container?
DNS resolves the hostname to the external IP of a cloud load balancer or the node IPs behind a DNS record. The load balancer forwards to a NodePort on some node, where the ingress controller's Service is listening. The ingress controller — nginx, Traefik, an ALB controller — terminates TLS, matches the Host header and path against Ingress rules, and selects a backend Service. Importantly, modern ingress controllers do not route through the Service's cluster IP; they watch EndpointSlices and proxy straight to a Pod IP, which is why they can do their own load balancing and session affinity. If traffic does go via a ClusterIP, kube-proxy has programmed iptables or IPVS rules on every node that DNAT the virtual IP to one of the ready backend Pod IPs. The packet then traverses the CNI — a veth pair into the Pod's network namespace, possibly via an overlay like VXLAN, possibly native VPC routing — and arrives at the container's listening socket. For debugging I walk that chain backwards: check endpoints exist, port-forward to the Pod, then to the Service, then test DNS from inside the cluster, then read the ingress controller logs. The layer where it stops failing tells you exactly which component is broken.
Helm or Kustomize?
They solve adjacent problems. Helm is templating plus release management: it renders Go templates against a values file and tracks installed releases so you get helm history, helm rollback, hooks and atomic upgrades. Kustomize is patching: the base files are valid YAML you can read and kubectl apply directly, and overlays apply strategic merge patches on top. My rule is that if I am distributing software to other people — which as an FDE I usually am — Helm wins, because the chart's values.yaml is a documented configuration contract and the customer can version, review and upgrade it like any other dependency. If I am managing my own application across a few environments in a GitOps repo, Kustomize is less machinery and the diffs are readable. They also compose: Argo CD can render a Helm chart and then apply Kustomize patches, which is how teams customise a third-party chart without forking it. The practical warnings are that Helm templates become genuinely painful to debug once they grow conditionals — helm template and helm diff upgrade are non-negotiable before any production apply — and that Kustomize alone has no rollback story, so you are relying on git and your deployment tool for that.
How do you deploy into an air-gapped customer cluster?
The first step is enumerating every image, not just mine — the database, cache, vector store, ingress controller, cert-manager, metrics-server, every sidecar and init container. helm template | grep image: gets most of it. I resolve each tag to a digest so what I validated is provably what ships, then mirror with skopeo copy --all to preserve multi-arch manifests, or skopeo sync to a directory for physical transfer across the gap. On the inside I rewrite references through Helm values with a registry prefix, a Kustomize images: block, or a node-level containerd mirror so the rewrite is transparent. Three things routinely bite people: the registry's TLS certificate is signed by the corporate CA, which must be trusted by containerd on every node — that is a cluster-admin change, not something a manifest can fix; vulnerability scanners need their database pre-staged because they cannot phone home; and any Helm chart that pulls a dependency at install time will fail, so charts must be fully vendored. I also budget calendar time deliberately — image approval and firewall exceptions at a regulated customer are routinely two to three weeks of waiting for two hours of work, so I start that process on day one with a placeholder if necessary.
What is a Service, and why does my pod get "connection refused" calling another service?
A Service is a stable virtual IP and DNS name that load-balances across the set of Pods matching its label selector and currently passing readiness. The backing implementation is an EndpointSlice maintained by the endpoints controller plus iptables or IPVS rules programmed by kube-proxy on every node. For "connection refused" I check four things in order. First, does the Service have endpoints at all — kubectl get endpoints; empty is the most common cause and means the selector does not match any ready Pod's labels, usually because someone matched the Deployment name instead of the pod template labels, or because every Pod is failing readiness. Second, is the name right — cross-namespace calls need service.namespace or the FQDN, and using the bare name from another namespace fails silently. Third, is the port right — the Service port is what clients dial and targetPort is the container port; mixing them up gives exactly this error. Fourth, is the application bound to 0.0.0.0 rather than 127.0.0.1 inside the container, which I verify with kubectl exec -- ss -tulpn. If all four are fine I look at NetworkPolicy — but note that a policy drop usually produces a timeout rather than a refusal, so the error text itself narrows the search.
What does readOnlyRootFilesystem: true break, and how do you fix it?
It breaks anything that writes outside an explicitly mounted volume: temp files in /tmp, a framework's cache directory, a log file written to disk, a PID or lock file, a Python __pycache__, a Node package cache, SQLite's journal. The fix is not to turn it off; it is to mount an emptyDir at each path that genuinely needs to be writable, with a sizeLimit so a runaway write cannot trigger DiskPressure on the node and evict every pod. I find the paths empirically — run the container, watch it fail, add a mount, repeat, or use docker diff on a locally running container which lists exactly which files were modified relative to the image. Applications should also be configured to log to stdout rather than a file, which is what the cluster's log aggregation expects anyway. It is worth doing properly because readOnlyRootFilesystem is part of the restricted Pod Security profile that most enterprise clusters enforce, so if I do not solve it at build time the customer's admission controller will reject my deployment and I will be solving it under time pressure instead.
When would you tell a customer not to use Kubernetes?
When the operational cost exceeds the benefit, which is more often than the industry admits. If they are running one or two services with predictable load on a couple of VMs, systemd units with a reverse proxy, or Docker Compose on a single host, delivers the same outcome with a fraction of the surface area to secure, upgrade and debug. If they have no platform team and no on-call rotation, handing them a cluster means handing them a system nobody can operate once I leave — cluster upgrades, certificate rotation, CNI troubleshooting and etcd maintenance are real recurring work. If their workload is genuinely serverless-shaped, a managed container service or a function platform removes the cluster entirely. I would push toward Kubernetes when they need multi-service orchestration with real service discovery, horizontal autoscaling, zero-downtime rolling deploys with health gating, self-healing across node failures, or when they already run a cluster and adding my workload is marginal cost rather than new cost. The honest version of this conversation is also good consulting: recommending less infrastructure than the customer expected builds the credibility you need for the recommendations where you do say yes.

Deliberate failure drills

Drill 1 — Six broken pods

Create one Pod for each failure mode and diagnose it from kubectl get pods output alone before touching anything else. (a) An image tag that does not exist, then the same image in a private registry with no pull secret — note the different describe messages. (b) A container whose command exits 1 after printing a config error. (c) A memory limit of 32Mi on a JVM. (d) Requests of 100 CPU so nothing can schedule it. (e) A readiness probe on port 9090 when the app listens on 8080. (f) A Service whose selector has a typo so endpoints stay empty. For each, write down the one command that revealed the cause. The goal is a reflex, not a search.

Drill 2 — Zero-downtime rollout

Run a continuous load generator (hey -z 300s -c 20 http://rag.local/api/healthz) while you roll out a new image. Record the error count. Now do it four more times, each with one change: maxUnavailable: 0; a correct readiness probe; a preStop sleep of 5 seconds; graceful shutdown in the application with a terminationGracePeriodSeconds that exceeds the longest request. Plot the error count after each change. Seeing it go from several hundred dropped requests to zero teaches the mechanism far better than reading about it, and it is a demo customers find genuinely persuasive.

Drill 3 — Air-gapped install, end to end

Run a local registry (docker run -d -p 5000:5000 registry:2), mirror every image your Helm chart references into it, then recreate the kind cluster with no internet access (block egress with an iptables rule or run it on a disconnected VM). Install the chart. You will discover, in roughly this order: an image you forgot (probably a sidecar or the ingress controller's webhook job), a chart dependency fetched at install time, a scanner that cannot update its database, and a CA trust problem on the registry. Each of those is a real finding you would otherwise make for the first time in front of a customer.

Drill 4 — Resource exhaustion

Deploy three workloads with QoS classes Guaranteed, Burstable and BestEffort. Use a memory-hungry pod to drive a node toward MemoryPressure and observe which gets evicted first — the ordering is not theoretical, you can watch it happen in kubectl get events --field-selector reason=Evicted. Then set a CPU limit of 500m on a CPU-bound service, run a load test, and correlate the p99 latency spike with container_cpu_cfs_throttled_seconds_total. Finally fill a node's disk with an unbounded emptyDir write and watch DiskPressure trigger image garbage collection and then pod eviction. These three behaviours explain the majority of mysterious production incidents in customer clusters.
