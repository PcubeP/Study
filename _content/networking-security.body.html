Why the Network Is Where Deployments Fail

Your code works. Your container runs. Your tests pass. And then you deploy it inside a customer's environment and nothing can reach anything. In a decade of Forward Deployed Engineering, the single largest category of "it works on my machine" is not language runtime differences or missing dependencies — it is the network, and the identity layer sitting on top of it. The customer's environment has a proxy you were not told about, a firewall rule nobody can find the owner of, a DNS view that resolves differently inside the VPN, a TLS-inspecting middlebox re-signing every connection, and an identity provider whose token lifetime breaks your refresh logic.

The four questions to ask on day one

  1. What can this workload reach, and over what?Not "is there internet" — specifically, which destinations, which ports, through which proxy, with which credentials. Get it in writing, because "we have open egress" is wrong roughly half the time.
  2. Who issues the certificates, and does anything trust them?An internal CA that your containers do not trust produces failures that look like network failures but are not.
  3. What is the identity provider, and what does "integrate with our SSO" mean to them?Entra ID with OIDC is a day of work. On-prem ADFS with SAML, mutual TLS and a group-claim mapping exercise is three weeks.
  4. Who do I call when a packet does not arrive?The network team, the firewall team, the proxy team and the DNS team are frequently four different groups with four different ticket queues and four different SLAs. Find them before you need them.
Make connectivity a deliverable, not an assumptionWrite a one-page connectivity matrix in week one: source, destination, port, protocol, direction, purpose, and current status. Hand it to the network team as a firewall request rather than discovering each rule one timeout at a time. It typically takes one afternoon to write and saves two weeks of serialised ticket latency, and it makes you the person who brought structure rather than the person asking for favours.

TCP versus UDP, and why it matters to you

TCP gives you a connection, ordered delivery, retransmission and flow control. It also gives you a three-way handshake, which is why a blocked port behaves differently from an unreachable host: the handshake gets no reply and you wait for the timeout. UDP has none of that — fire and forget. DNS, NTP, QUIC/HTTP/3, syslog and most metrics protocols run on UDP, which is exactly why a firewall that only allows TCP produces the baffling "DNS does not work but HTTPS to an IP does."

TCP CONNECTION ESTABLISHMENT          WHAT YOU SEE WHEN IT GOES WRONG
client            server
  |---- SYN ------>|                  no reply at all      -> firewall DROP  -> "timeout"
  |<-- SYN,ACK ----|                  RST comes back       -> nothing listening / firewall REJECT
  |---- ACK ------>|                                          -> "connection refused"
  |   established  |                  SYN,ACK then silence -> asymmetric routing or MTU black hole
  |---- FIN ------>|                  RST mid-stream       -> idle timeout on a NAT/LB, or app crash
  |<--- FIN,ACK ---|
MTU — the failure that looks like magicStandard Ethernet MTU is 1500 bytes. VPNs, VXLAN overlays and some cloud networks reduce the usable size (IPsec typically leaves ~1400, WireGuard ~1420, many Kubernetes CNIs ~1450). If an intermediate device needs to fragment but the Don't Fragment bit is set, it should send ICMP "fragmentation needed" — and many corporate firewalls block all ICMP. The result is a black hole: the TCP handshake succeeds, small requests work, then any response above about 1400 bytes vanishes. Symptom: curl hangs after printing the response headers, or git clone stalls at a fixed percentage. Test it with ping -M do -s 1472 host (1472 + 28 bytes of header = 1500) and bisect downward to find the real MTU.
# Find the real path MTU
ping -M do -s 1472 -c 2 api.customer.internal   # 1500 total; fails if path MTU is lower
ping -M do -s 1372 -c 2 api.customer.internal   # 1400 total
# Linux shorthand: tracepath prints the discovered PMTU
tracepath api.customer.internal

# Mitigate on a VPN/overlay: clamp TCP MSS so endpoints negotiate a smaller segment
sudo iptables -t mangle -A FORWARD -p tcp --tcp-flags SYN,RST SYN \
     -j TCPMSS --clamp-mss-to-pmtu
# Kubernetes: set the CNI MTU explicitly, e.g. Calico FELIX_IPINIPMTU / spec.mtu

IP Addressing, CIDR and Routing

You will be asked to pick a subnet range for a new environment, and if you pick one that overlaps with the customer's on-prem network or an existing VPC, the VPN peering will fail and you will spend a week rebuilding. CIDR arithmetic is a five-minute skill with a very high cost of ignorance.

CIDR worked out

An IPv4 address is 32 bits. /24 means the first 24 bits are the network and the last 8 identify hosts. Addresses available = 2(32 − prefix), minus 2 on-premises (network and broadcast) or minus 5 in AWS and Azure, which reserve extra addresses in every subnet.

# Asymmetric routing (out one path, back another) is silently dropped by stateful firewalls.

SNAT (source NAT) rewrites the source address so many private hosts share one public IP outbound — this is how a NAT gateway works, and it is why the customer's partner sees one IP for all your traffic. DNAT (destination NAT) rewrites the destination so an inbound public address reaches a private host — this is port forwarding and load balancer VIPs. The operational consequences you will hit: SNAT port exhaustion (a NAT gateway has a finite number of source ports per destination; a chatty service opening thousands of short-lived connections to one endpoint will exhaust them and you will see sporadic connection timeouts under load — fix with connection pooling, keep-alive, or more outbound IPs), and the fact that behind SNAT your application sees the NAT address as the client IP unless you read X-Forwarded-For.

DNS End to End

"It's always DNS" is a joke because it is usually true. DNS is the layer where enterprise complexity is highest: split-horizon views, conditional forwarders, private zones, stale caches and TTLs that nobody agreed on. Learn to read it precisely, because DNS failures masquerade as application failures.

The enterprise DNS failure modes

Split-horizon confusion

The same hostname resolves to a private IP inside the corporate network and a public IP outside. Your CI runner sits in a DMZ and gets the wrong view, so it connects to an internet-facing endpoint that rejects it. Diagnose by querying both resolvers explicitly with dig @.

Stale cache after cutover

You change an A record, it works for you, and 30% of users still hit the old IP for hours. Cause: a long TTL that was never lowered beforehand. Fix: drop the TTL to 60 seconds at least 2x the old TTL before the change, cut over, then raise it again.

ndots and the search-domain storm

Kubernetes sets ndots:5. Any name with fewer than five dots — so almost all of them — is first tried against every search domain. api.customer.com becomes five failed queries before the correct one. Under load this saturates CoreDNS and shows as random latency spikes. Fix: use a fully qualified name with a trailing dot (api.customer.com.) or set dnsConfig.options ndots:1 on the pod.

Conditional forwarder gaps

Corporate DNS forwards *.corp.local to on-prem domain controllers and everything else to a public resolver. Your new private Azure zone privatelink.database.windows.net is in neither, so private endpoint resolution silently returns the public IP and the connection is refused by the firewall. Fix: add the forwarder. This is a one-line change that takes three weeks to get approved, so request it early.

Prove it is DNS before you blame itdig +short host tells you the resolver's answer. getent hosts host tells you what the C library actually returns — including /etc/hosts and NSS modules that dig bypasses entirely. When those two disagree, the answer is in /etc/hosts or nsswitch.conf, and you have just saved yourself an afternoon of packet captures. Then confirm reachability separately with nc -vz ip port against the resolved address, so you can state clearly whether the problem is name resolution or connectivity.

CORS, explained once properly

CORS is a browser restriction. It does not protect your server; it stops a page on evil.com from reading responses from api.customer.com using the user's cookies. Server-to-server calls, Postman and curl are unaffected — which is why "it works in curl but not in the browser" is the signature of a CORS problem.

SIMPLE REQUEST (GET/HEAD/POST with a simple content type) — no preflight
  Browser  --> GET /data            Origin: https://app.customer.com
  Server   <-- 200
               Access-Control-Allow-Origin: https://app.customer.com

PREFLIGHTED (custom headers, PUT/DELETE/PATCH, or application/json)
  Browser  --> OPTIONS /data
               Origin: https://app.customer.com
               Access-Control-Request-Method: PUT
               Access-Control-Request-Headers: authorization, content-type
  Server   <-- 204
               Access-Control-Allow-Origin: https://app.customer.com
               Access-Control-Allow-Methods: GET, PUT, DELETE
               Access-Control-Allow-Headers: authorization, content-type
               Access-Control-Max-Age: 600
  Browser  --> PUT /data   (only now)
The combination that breaks everythingAccess-Control-Allow-Origin: * together with Access-Control-Allow-Credentials: true is rejected by every browser — the wildcard is forbidden when credentials are in play. You must echo the specific requesting origin after validating it against an allow-list. And never reflect the Origin header unconditionally: that is equivalent to allowing every site on the internet to make authenticated requests on behalf of your users.

The cache-poisoning incident everyone has seenA CDN or reverse proxy caching an authenticated response without Cache-Control: private and a correct Vary header will serve user A's account page to user B. It is a data-breach-class bug that hides until traffic is high enough for a cache hit to land on a different user. Rule: any response that varies by identity must be private (or no-store) and must declare Vary: Authorization or Vary: Cookie.

Load balancer layers

L4 (AWS NLB, Azure Load Balancer, HAProxy in TCP mode) forwards TCP/UDP without understanding the payload: very fast, preserves the client IP easily, cannot route by URL path or inspect headers, and TLS passes through to the backend. L7 (ALB, Application Gateway, nginx, Envoy) terminates TLS and understands HTTP: it can route by host and path, rewrite headers, retry idempotent requests, inject tracing IDs, and do sticky sessions — but it becomes a place where headers get stripped and timeouts bite.

The idle timeout that eats your long-running requestDefault idle timeouts: AWS ALB 60 s, Azure Load Balancer 4 min, Application Gateway 20 s backend request timeout, nginx proxy_read_timeout 60 s. Any request that takes longer — a large report, an LLM streaming response, a slow batch trigger — gets cut with a 504 or a reset, and your application logs will show the work completing successfully afterwards. Fix it properly by making long work asynchronous (202 Accepted plus a status endpoint), and only raise the timeout as a stopgap. For streaming responses you must also disable proxy buffering (proxy_buffering off, X-Accel-Buffering: no), or the proxy holds every token until the response ends.

WAFs

A Web Application Firewall inspects requests against rule sets (usually the OWASP Core Rule Set) and blocks things that look like SQL injection, XSS, path traversal or scanning. It is a useful compensating control and a terrible primary defence — it is pattern matching, and it generates false positives against perfectly legitimate traffic. Characteristic FDE experience: a customer's WAF blocks your JSON payload because a field contains the word select, or rejects a base64 blob as "possible command injection", and the response is a generic 403 with no detail. Always ask for the WAF log ID from the blocked request — X-Azure-Ref, the ALB request ID, or the ModSecurity rule ID — because without it you are guessing. Run a new WAF in detection mode for at least two weeks before enforcing, and tune per-path rather than disabling rules globally.

API gateways

A gateway centralises the things every API needs: authentication and token validation, rate limiting and quotas, request/response transformation, routing and versioning, logging and analytics, and sometimes caching. The architectural question you will be asked is "gateway or service mesh?" — the honest answer is that they solve different problems. A gateway handles north-south traffic (clients entering your system) and a mesh handles east-west traffic (service to service, with mTLS, retries and observability). Many customers need both; many more are sold a mesh they do not need. If the customer has fewer than roughly fifteen services and no mTLS mandate, a mesh is usually cost without benefit.

TLS and PKI

Certificate problems are the most common hard-stop you will hit in a customer deployment, and the most commonly misdiagnosed. Learn the handshake and the openssl s_client output properly — being the person who can read a certificate chain out loud in a bridge call is disproportionately valuable.

The handshake

TLS 1.3 (one round trip — this is what you should be using)

Zero trust in one paragraph

The old model was a hard perimeter and a soft interior: get onto the VPN and you could reach everything. Zero trust assumes the network is already hostile and makes every request prove itself: strong identity for users and workloads, device posture, per-application authorisation rather than network-level access, least privilege with just-in-time elevation, encryption everywhere including east-west, and comprehensive logging. Practically, for the systems you build, this means: no implicit trust because a caller is "inside the VNet"; every service authenticates every other service (mTLS or signed tokens); network segmentation limits lateral movement; and human access to production goes through an audited, MFA-protected, time-bound path rather than a standing VPN credential.

Segmentation that regulators look for

  • Separate subscriptions/accounts per environment, not just separate resource groups — a blast-radius boundary that also prevents accidental cross-environment references
  • Separate subnets per tier (ingress, application, data, management) with NSG/security group rules between them, default deny
  • Kubernetes NetworkPolicy with a default-deny baseline per namespace, then explicit allows
  • No direct database access from the application subnet except on the database port, from the specific security group
  • Egress through a controlled NAT or proxy with an allow-list, so a compromised workload cannot exfiltrate to an arbitrary host
  • Management plane separated: CI runners, bastions and monitoring in their own segment

Cryptography You Must Not Get Wrong

You will not design a cipher. You will choose between library functions, and the wrong choice produces a system that looks encrypted and is not. Four distinctions carry almost all of the practical risk: encoding versus hashing versus encryption, symmetric versus asymmetric, how passwords are stored, and what "encrypted at rest and in transit" actually obliges you to do.

base64 is not encryptionA Kubernetes Secret stores values base64-encoded. That is encoding for transport, nothing more — anyone with read access to the object has the plaintext after one command. This appears in every security review of a first Kubernetes deployment, and committing a Secret manifest to git is committing the credential. Enable encryption at rest for etcd, restrict RBAC on secrets, and prefer an external secret store with a CSI driver.

Symmetric and asymmetric

Symmetric (AES-256-GCM, ChaCha20-Poly1305)

One key encrypts and decrypts. Fast — gigabytes per second. Used for bulk data: disks, databases, files, the body of a TLS session. The problem it does not solve is getting the key to the other party. Always use an AEAD mode (GCM, Poly1305) so you get integrity as well as confidentiality; plain CBC without a separate MAC is how padding-oracle attacks happen.

Asymmetric (RSA, ECDSA, Ed25519)

A key pair: public encrypts/verifies, private decrypts/signs. Thousands of times slower, so it is used to establish a symmetric key or to sign. This is TLS key exchange, JWT signing, SSH keys, code signing, and certificates. Prefer Ed25519 or ECDSA P-256 over RSA for new work: smaller keys, faster, no padding-mode footguns.

Password storage

hashlib.sha256(password.encode()).hexdigest()           # fast by design = billions of guesses/sec
hashlib.sha256((salt + password).encode()).hexdigest()  # salted, but still far too fast

  • Never roll your own, never store reversible passwords, never log them (including in request bodies captured by APM)
  • Use a constant-time comparison for anything secret-adjacent (hmac.compare_digest), not ==

  • Check new passwords against a breached-password list (Have I Been Pwned's k-anonymity API) — far more effective than complexity rules

Keys and rotation

Use envelope encryption: data is encrypted with a per-object data key; the data key is encrypted with a key-encryption key held in a KMS/HSM. Rotating the KEK is then cheap because you re-wrap the small data keys rather than re-encrypting terabytes. Store keys in a managed KMS (Azure Key Vault / Managed HSM, AWS KMS, GCP KMS, HashiCorp Vault), never in application config. Give every key an identifier that travels with the ciphertext (a kid), so you can decrypt old data after rotation.

What "encrypted at rest and in transit" actually requires

Customers put this phrase in contracts without definition. When you are answering their questionnaire, be specific about each of these, because each is a separate control:

  • In transit, external: TLS 1.2 minimum (1.3 preferred), HSTS, modern cipher suites, valid certificates with automated renewal
  • In transit, internal: east-west traffic also encrypted — mTLS in the mesh, TLS to the database (sslmode=verify-full, not require, which does not validate the certificate)
  • At rest, storage: disk/volume encryption, object storage encryption, with customer-managed keys if they require control of the key lifecycle
  • At rest, database: transparent data encryption, plus column-level or application-level encryption for the sensitive fields
  • At rest, backups: the most commonly missed one. Backups and snapshots must be encrypted with the same rigour and their keys retained long enough to restore
  • In use / in logs: no secrets or PII in application logs, APM traces, crash dumps or error reports — this is where most real leakage happens
  • Key management: who can access keys, how rotation works, how deletion is proven

Validating a JWT correctly

import jwt                      # PyJWT
from jwt import PyJWKClient

JWKS = PyJWKClient(
    "https://login.microsoftonline.com/9f3c.../discovery/v2.0/keys",
    cache_keys=True, lifespan=3600,        # cache; do NOT fetch per request
)
ISSUER   = "https://login.microsoftonline.com/9f3c.../v2.0"
AUDIENCE = "api://payments-api"

def validate(token: str) -> dict:
    signing_key = JWKS.get_signing_key_from_jwt(token)   # selects by 'kid'
    claims = jwt.decode(
        token,
        signing_key.key,
        algorithms=["RS256"],      # PIN the algorithm. Never read it from the header.
        issuer=ISSUER,             # exact match
        audience=AUDIENCE,         # exact match
        leeway=30,                 # tolerate small clock skew, not minutes
        options={
            "require": ["exp", "iat", "nbf", "iss", "aud", "sub"],
            "verify_signature": True, "verify_exp": True,
            "verify_nbf": True, "verify_iat": True,
            "verify_aud": True, "verify_iss": True,
        },
    )
    if claims.get("tid") != EXPECTED_TENANT:          # multi-tenant isolation
        raise PermissionError("wrong tenant")
    if claims.get("jti") in revocation_cache:         # bounded revocation window
        raise PermissionError("revoked")
    return claims

Refresh tokens and lifetimes

LIFETIMES THAT WORK IN PRACTICE
  access token    5–15 min   (bounds the damage window from a stolen token)
  ID token        5–15 min   (consumed once at sign-in anyway)
  refresh token   8–90 days, sliding, with ROTATION and REUSE DETECTION
  session cookie  tied to the refresh token lifetime, Secure + HttpOnly + SameSite

REFRESH TOKEN ROTATION
  Each use returns a NEW refresh token and invalidates the old one.
  If an OLD refresh token is presented again -> it was stolen and replayed
  -> revoke the entire token family and force re-authentication.
  This is mandatory for public clients (SPAs, mobile) where the token cannot be kept secret.
When the customer's token lifetime breaks your appEnterprises often set very short access-token lifetimes via conditional access, sometimes five minutes or less, and may require re-authentication on sensitive operations. If your client only refreshes on a 401 and your long-running job holds a token for an hour, it will fail mid-operation. Build refresh around expiry with a margin (refresh at 80% of lifetime), handle a 401 by refreshing once and retrying exactly once, make the refresh path concurrency-safe so twenty threads do not each trigger a refresh, and never retry indefinitely — a revoked token must surface as a real error.

SAML 2.0 and Enterprise SSO

"Integrate with our IdP" is one of the most underestimated line items in enterprise delivery. If the customer is on modern Entra ID or Okta and will accept OIDC, it is a day or two. If they are on on-prem ADFS, require SAML, have a group-claim mapping exercise and a certificate exchange through a change process, it is three weeks and you should plan it as such. Knowing which situation you are in on day one is the whole skill.

SAML in structure

SAML validations you must not skip

  • Signature — verify the XML signature against the IdP's certificate from metadata. Verify the assertion is signed, not only the response wrapper.
  • Issuer — matches the expected entity ID exactly.
  • Audience — the AudienceRestriction names your SP entity ID.
  • Destination / Recipient — matches your actual ACS URL.
  • Time window — NotBefore / NotOnOrAfter, with minimal clock skew allowance.
  • InResponseTo — matches a request you issued and have not already consumed.
  • Replay — cache assertion IDs for the validity window and reject duplicates.
XML Signature WrappingSAML's signature covers a referenced XML element, and many libraries have historically validated a signature over one element while the application read claims from a different, attacker-inserted element. This produced authentication-bypass CVEs across multiple major SAML libraries. Never write your own SAML processing. Use a maintained library (python3-saml, ruby-saml, passport-saml, Spring Security SAML), keep it patched, and make sure the version you pin is after the relevant advisories. The same applies to XML parsing generally: disable DTD and external entity resolution to prevent XXE.

SCIM — the part everyone forgets

SSO answers "can this person log in?" It does not answer "does this person exist in your system, what is their name, which groups are they in, and what happens when HR terminates them?" That is provisioning, and the standard is SCIM 2.0: a REST API your application exposes so the IdP can create, update, deactivate and delete users and groups automatically.

Without SCIM, offboarding is manual — and auditors check itIf a leaver's account remains active in your application after HR terminates them in the HR system, that is a finding in SOC 2, ISO 27001 and most internal audits. Either implement SCIM, or implement just-in-time provisioning from SSO claims combined with a scheduled reconciliation that deactivates anyone who has not authenticated in N days. Agree which, explicitly, during design — discovering it during the customer's audit is expensive.

What "integrate with our IdP" means as a work item

  1. Determine the protocol and the productOIDC or SAML; Entra ID, Okta, Ping, ForgeRock, ADFS, Keycloak. Ask for the metadata URL — if they cannot produce one, that is a signal about how long this will take.
  2. Register the applicationSomeone on their identity team does this. There is a request form and an SLA. Start it in week one, not week four.
  3. Agree the claims contractWhich attribute is the stable user identifier (insist on an immutable one, not email)? How are groups or roles conveyed — group GUIDs, group names, or application roles? Entra emits group object IDs by default, and if a user is in more than ~150 groups it emits an overage claim pointing at Graph instead, which breaks naive implementations.
  4. Exchange certificates and endpointsRecord expiry dates for every certificate involved and set calendar alerts; IdP signing certificate rollover is a classic outage.
  5. Handle conditional accessMFA, device compliance, IP restrictions and session lifetimes are all controlled on their side and can break your flows without warning.
  6. Define provisioning and deprovisioningSCIM, JIT, or manual with reconciliation.
  7. Test the unhappy pathsUser not assigned to the app; user in no mapped group; expired assertion; clock skew; IdP down; logout and single-logout behaviour.

Service identity and least privilege

  • Every workload gets its own identity — managed identity, IRSA, workload identity, or a SPIFFE SVID. Never a shared service account across services.
  • Permissions scoped to the specific resource, not the subscription or account. "Storage Blob Data Reader on this container", not "Contributor on the subscription".
  • Separate identities per environment, so a dev credential cannot touch production under any circumstances.
  • Human access to production is read-only by default, with time-bound elevation (PIM / just-in-time) that alerts and logs.
  • Review grants quarterly and remove what has not been used — cloud providers can report last-used time for most permissions.

A10 — Server-Side Request Forgery (SSRF)

Your server fetches a URL that a user supplied, and the user points it at something internal — the cloud metadata endpoint, an internal admin API, a database. SSRF is how the Capital One breach extracted credentials from the EC2 metadata service. It has become more common, not less, because webhook configuration, URL preview, document import and "fetch from URL" features are everywhere — and because AI agents with browsing tools are SSRF engines by design.

from urllib.parse import urlparse

ALLOWED_HOSTS = {"docs.partner.com", "cdn.partner.com"}

def safe_fetch(url: str) -> str:
    p = urlparse(url)
    if p.scheme != "https":
        raise ValueError("https only")
    if p.hostname not in ALLOWED_HOSTS:          # allow-list beats any deny-list
        raise ValueError("host not permitted")

    # Resolve and check EVERY address: DNS can return a private IP for a public name
    for family, _, _, _, sockaddr in socket.getaddrinfo(p.hostname, 443):
        ip = ipaddress.ip_address(sockaddr[0])
        if ip.is_private or ip.is_loopback or ip.is_link_local or ip.is_reserved:
            raise ValueError("resolves to a non-public address")

    return requests.get(url, timeout=5, allow_redirects=False).text   # redirects can re-target
Defence in depth for SSRFApplication-level checks are racy — DNS rebinding can return a public address at validation time and a private one at connection time. The durable controls are network-level: run outbound fetches through an egress proxy with an allow-list, block the metadata endpoint at the network layer, and enforce IMDSv2 on AWS (which requires a PUT-obtained token and blocks the naive GET that SSRF exploits). In Kubernetes, a NetworkPolicy that denies egress to 169.254.169.254/32 and RFC1918 ranges turns a critical SSRF into an information-free timeout.

Pen test findings

  1. Triage against realityReports are produced by tools plus a human and frequently contain findings that do not apply — a "missing HttpOnly" on a cookie that holds nothing, a "weak cipher" on a port reachable only from a management subnet. Verify each one by reproducing it.
  2. Reproduce before you argueIf you can reproduce it, fix it. If you cannot, say so precisely and ask for the exact request. "We could not reproduce" without detail reads as a brush-off.
  3. Classify honestlyCritical and high get fixed before go-live. Medium gets a ticket and a date. Low and informational get a documented accept-or-fix decision, signed by a named person.
  4. Dispute with evidence, not opinionIf a finding is a false positive or already mitigated by a compensating control, demonstrate it: the network policy, the WAF rule, the test that proves the behaviour.
  5. Fix the class, not just the instanceIf they found one IDOR, there are more. Fix the pattern — add tenant scoping at the data layer and write a generated test across every route.
  6. Request a retestAnd budget time for it. The retest is what closes the finding formally and unblocks go-live.

Incident Response Basics

You will be in the room — possibly the only engineer in the room — when something goes wrong in a customer environment. The difference between a controlled response and a chaotic one is almost entirely preparation and discipline in the first hour.

The lifecycle

Prepare→ Detect→ Contain→ Eradicate→ Recover→ Learn

The first hour

  1. Declare itSay the word "incident" out loud. Ambiguity is the enemy; an explicit declaration starts the clock, the comms channel and the roles. Over-declaring costs an hour; under-declaring costs the company.
  2. Assign rolesIncident commander (decides, does not debug), communications lead (updates stakeholders on a fixed cadence), scribe (timestamps everything in the channel), and one or two investigators. If you are alone, you are the commander and you write things down.
  3. Preserve evidence before you change anythingSnapshot the disk, capture memory if you can, export logs to a separate account, record the exact state. Rebooting or redeploying destroys the forensic trail and you cannot get it back. This matters most when it is a security incident rather than an outage.
  4. ContainStop the bleeding without destroying evidence. Isolate the host at the network level rather than powering it off. Revoke the suspected credential. Disable the compromised account. Block the source IP. Take the affected feature offline with a feature flag.
  5. Establish a timelineWhen did it start? What changed in the preceding 24 hours — deploy, config change, certificate expiry, dependency update, traffic shift? The scribe's notes become the timeline.
  6. Communicate on a scheduleEvery 30 minutes, even when the update is "no change, still investigating". Silence is read as loss of control and generates its own escalation.
  7. Escalate earlyInvolve the customer's security team immediately for anything that may be a breach. Do not investigate quietly and tell them later — in most contracts and most regulations, notification clocks have already started.
Notification clocks are shorter than people thinkGDPR requires notification to the supervisory authority within 72 hours of becoming aware of a personal-data breach. Many customer contracts specify 24 hours to notify them, and some sectors are shorter. You are not the person who decides whether to notify — the customer's legal and privacy functions are — but you are the person who starts their clock by telling them. Tell them immediately and let them assess. Delay is the thing that converts a technical incident into a legal one.

The postmortem

Blameless, written within a week, and published. The structure that works: a one-paragraph summary a non-engineer can read; impact in concrete terms (duration, users affected, data involved); a minute-by-minute timeline; root cause analysis that keeps asking why until it reaches a systemic answer; what went well; what went badly; and action items — each with a named owner, a due date and a ticket. Action items without owners are decoration. The single most valuable question is "what would have made us detect this in five minutes instead of fifty?", because detection time compounds across every future incident.

Blameless is a practice, not a sentimentIf engineers believe a postmortem can end their career, you will get incomplete timelines and defensive narratives, and you will never learn the real cause. The framing that works: a person made a reasonable decision given the information and tooling available, so the fix is to change the information or the tooling. "Why was it possible for a single command to delete the production database?" is a systems question. "Why did Sam run that command?" is not.

Interview Questions

A service cannot reach a database. Walk me through your diagnosis.
I work up the layers and stop at the first one that fails, because that tells me both the cause and who owns the fix. First, name resolution: getent hosts db.customer.internal rather than just dig, because getent includes /etc/hosts and NSS, and if those two disagree the answer is a static override. If the name resolves to an unexpected address — a public IP where I expect a private endpoint — the problem is DNS zone linkage or a missing conditional forwarder, not connectivity. Second, TCP: nc -zvw3 ip 5432. A refusal means something answered and nothing is listening, so the service is down or bound to loopback; a timeout means a packet was silently dropped, which is a firewall, NSG, NACL or route problem and belongs to the network team. Third, if TCP connects but TLS hangs or the application sees truncated data, I suspect MTU, and I test with ping -M do -s 1472 and bisect down. Fourth, if TLS fails with a certificate error I run openssl s_client and read the issuer and SANs. Only after all that do I look at application configuration and credentials. The discipline matters because each layer has a different owner, and walking into a bridge call able to say "TCP connects, TLS fails with an unknown issuer, this is our trust store not your firewall" ends the argument immediately.
What is the difference between "connection refused" and "connection timed out", and why do you care?
Refused means a TCP RST came back: a host was reachable and actively said no, so either nothing is listening on that port or a firewall is configured to REJECT rather than DROP. Timed out means the SYN went out and nothing at all came back, so a device silently dropped the packet — a firewall, a security group, a NACL or a routing black hole. The distinction matters because it tells you who can fix it. Refused is almost always mine: the process crashed, it bound to 127.0.0.1 instead of 0.0.0.0, or it is on a different port, and ss -tulpn settles it in one command. Timed out is almost always the network team's, and I need to go to them with a specific source, destination, port and timestamp rather than "it does not work". There is also a middle case worth knowing — the handshake completes and then the connection resets or stalls mid-stream — which usually points at an idle timeout on a load balancer or NAT, or an MTU black hole, and those are diagnosed with tcpdump and path MTU testing rather than more firewall tickets.
Explain OAuth 2.0 authorisation code flow with PKCE, and what each parameter defends against.
The client generates a cryptographically random code verifier and derives a challenge as the base64url of its SHA-256 hash. It redirects the user to the authorisation server with the client ID, redirect URI, requested scopes, a random state value, a nonce, and that code challenge. The user authenticates directly with the identity provider — the application never sees their password — and the server redirects back with a short-lived authorisation code. The client then POSTs that code to the token endpoint along with the original verifier, and the server recomputes the hash and compares. PKCE defends against authorisation code interception: on mobile a malicious app can register the same custom URL scheme and capture the code, and on any platform the code can leak through logs or referrers, but the code is useless without the verifier, which never left the client. State defends against CSRF on the callback — without validating it, an attacker can inject their own authorisation code into a victim's session and cause the victim to be logged in as the attacker. Nonce binds the resulting ID token to this specific authentication request, preventing token replay. The other critical control is on the server side: exact-string matching of the redirect URI, because any wildcard or prefix matching turns an open redirect into an account takeover.
What is the difference between an ID token and an access token, and what goes wrong if you confuse them?
An ID token is an OIDC artifact minted for the client application; it describes who authenticated, when and how, and its audience claim is the client ID. An access token is an OAuth artifact minted for the resource server; its audience is the API, and it carries scopes or roles describing what the bearer may do. You send the access token to the API; you never send the ID token. The confusion happens constantly because both are often JWTs and both will "work" if the API validates sloppily. If an API accepts ID tokens, then any application the user has ever signed into with that identity provider can obtain a token that your API will accept — the attacker does not need to compromise your client at all, they just need the user to log into their own app in the same tenant. The defence is strict audience validation: reject any token whose aud is not your API's identifier, and additionally check iss exactly, pin the signing algorithm rather than reading it from the header, and in a multi-tenant application check the tenant claim. Those five checks — signature, issuer, audience, expiry, tenant — are the whole of safe JWT validation, and skipping any of them has produced real breaches.
A customer says "integrate with our IdP". What do you need to find out, and how long will it take?
My first three questions are: which product, which protocol, and can you send me the metadata URL. If the answer is Entra ID or Okta with OIDC and they can register an application quickly, it is one to two days of work. If the answer is on-premises ADFS with SAML, a certificate exchange through a change process, and a group-claims mapping exercise, it is two to three weeks and most of that is their internal lead time, not my coding. After that I need the claims contract in writing: which attribute is the stable, immutable user identifier — I insist on something like oid or sub, never email, because email changes and can be reassigned — and how group or role membership is conveyed. With Entra specifically I check for the group overage case, where a user in more than about 150 groups gets a claim pointing at Microsoft Graph instead of the group list, which breaks naive implementations in production for exactly the senior people who complain loudest. Then conditional access: MFA requirements, device compliance, IP restrictions and token lifetimes are all controlled by them and can break my flows without notice. And finally provisioning, which everyone forgets — SSO lets a person log in, but SCIM or a reconciliation job is what makes a leaver's account actually get disabled, and that gap is an audit finding.
Your curl works but the browser gets a CORS error. Explain what is happening.
CORS is a browser-enforced policy, not a server-side protection, so curl and Postman are completely unaffected — they simply do not implement the same-origin policy. The browser is refusing to let JavaScript on one origin read a response from another origin unless the server explicitly opts in with the right headers. If the request is "simple" — a GET or a form-encoded POST with no custom headers — the browser sends it and then blocks the response if Access-Control-Allow-Origin does not match. If the request has a JSON content type, a custom header such as Authorization, or a method like PUT or DELETE, the browser first sends an OPTIONS preflight, and the server must answer with the allowed origin, methods and headers. The failures I see most often are: the preflight hitting an authentication middleware that returns 401 because OPTIONS requests carry no credentials; a wildcard origin combined with Allow-Credentials: true, which every browser rejects outright; and a server echoing the Origin header back unconditionally, which is functionally equivalent to allowing every website on the internet to make authenticated requests on behalf of your users. The correct implementation validates the origin against an allow-list and echoes only matching values, excludes OPTIONS from authentication, and sets a sensible Access-Control-Max-Age so the browser is not preflighting every single call.
How would you store user passwords, and why not SHA-256?
With argon2id, or bcrypt at cost 12 or above if argon2 is not available, or PBKDF2-HMAC-SHA256 with at least 600,000 iterations when FIPS compliance forces it. SHA-256 is wrong because it is designed to be fast — that is its entire purpose — and a modern GPU rig computes billions of SHA-256 hashes per second, so a leaked database of SHA-256 password hashes is effectively a leaked database of passwords for anything but genuinely random secrets. Salting helps against precomputed rainbow tables but does nothing about raw speed. A password-hashing function is deliberately slow and, in argon2's case, memory-hard, which also defeats the GPU and ASIC parallelism advantage; argon2id with 64 MB of memory, three iterations and parallelism four is a reasonable starting point to be tuned against your hardware. Around that I would use constant-time comparison, rate limiting and account lockout on repeated failures, identical error messages and response timing whether or not the account exists, a transparent rehash on successful login when the cost parameters have been raised since the hash was created, and a check against a breached-password corpus using the k-anonymity API — which in practice prevents far more account compromises than any complexity rule ever has.
What is SSRF, why has it become more dangerous, and how do you actually prevent it?
Server-side request forgery is when an attacker gets your server to make an HTTP request to a destination they choose. It is dangerous because your server sits inside the network perimeter and can reach things the attacker cannot — internal admin interfaces, databases, and most notoriously the cloud instance metadata endpoint at 169.254.169.254, which hands out IAM credentials to anything that asks. That is precisely how the Capital One breach exfiltrated credentials. It has become more common because URL-fetching features are everywhere: webhook configuration, link previews, document import, and now AI agents with browsing or fetch tools, which are SSRF engines by construction. Application-level defence means an allow-list of permitted hosts rather than a deny-list, HTTPS only, resolving the hostname and rejecting any result in a private, loopback, link-local or reserved range, and disabling redirect following because a redirect can re-target after validation. But application checks are racy — DNS rebinding can return a public address at validation and a private one at connect — so the durable controls are at the network layer: send outbound fetches through an egress proxy with an allow-list, block the metadata address with a network policy or security group rule, and enforce IMDSv2 on AWS so a naive GET cannot retrieve credentials. Defence in depth matters here more than almost anywhere else.
The customer's proxy breaks all your tooling with certificate errors. What do you do?
First I confirm what is actually happening by running openssl s_client -connect pypi.org:443 and reading the issuer — if it is the customer's internal CA rather than a public one, they are intercepting TLS, inspecting the plaintext and re-signing. Then I fix the trust properly. The internal root CA goes into the operating system trust store with update-ca-certificates or update-ca-trust, and then into each runtime individually, because none of them share: Python's requests needs REQUESTS_CA_BUNDLE, Node needs NODE_EXTRA_CA_CERTS, Java needs an import into its own cacerts keystore via keytool, Git has http.sslCAInfo, and containers need the certificate copied into both the builder and runtime stages. I package all of that as a composite action or a base image so every team gets it consistently instead of rediscovering it. What I will not do is set NODE_TLS_REJECT_UNAUTHORIZED=0 or use curl -k or verify=False, because those disable the verification that makes an inspected connection safe at all, they inevitably become permanent once they are in a Dockerfile, and they will show up as a finding on the customer's own pen test. While I am in there I also check that NO_PROXY includes 169.254.169.254, because routing the metadata endpoint through a proxy breaks managed identity in a way that looks entirely unrelated and costs people days.
How do you guarantee tenant isolation in a multi-tenant application?
Not by asking developers to remember a WHERE clause, because eventually one query will not have it and that single query is a company-level incident. I enforce it structurally, at the lowest layer I can reach. In Postgres that means row-level security: enable and force RLS on every tenant-scoped table, define a policy comparing the tenant column to a session variable, and have the connection pool set that variable on checkout. A query that forgets the filter then returns zero rows instead of everyone's data. Where RLS is not available I use a repository layer that cannot be constructed without a tenant context, or an ORM global filter, or separate schemas per tenant. On top of that, authorisation checks happen at object level, not just route level, and a denial returns 404 rather than 403 so I do not leak the existence of other tenants' records. Then I prove it: a test that enumerates every route from the application's route table and asserts that a token from tenant A gets a 404 for a resource belonging to tenant B, so new endpoints are covered automatically rather than relying on someone remembering to write the test. And on the retrieval side, if there is a vector index or search index involved, the source system's ACLs have to be carried into the index as filterable metadata and applied at query time — filtering after generation does not work, because by then the content is already in the model's context.
You discover a production credential has been compromised. Walk me through the first hour.
Revoke first, investigate second — the credential is already out, and every minute it stays valid is a minute an attacker can use it. So the first action is deleting or disabling the key, secret or account, within minutes, even before I fully understand the scope. Then I declare an incident explicitly and tell the customer's security team immediately, because in most contracts and under GDPR there are notification clocks that start when they become aware, and the decision about whether to notify regulators is theirs and not mine; delaying to "check first" is how a technical problem becomes a legal one. Next I preserve evidence before changing anything else — snapshot affected hosts, export the relevant audit logs to a separate location, record state — because redeploying destroys the forensic trail irrecoverably. Then blast radius: pull cloud audit logs filtered on that credential from the earliest possible exposure date, looking at source IPs and operations, and specifically hunt for persistence, because a competent attacker creates a second way in — new IAM users, new access keys, new app registrations, new cluster role bindings created since the exposure window. Then I rotate everything that credential could have reached, not just the one key, and re-issue through the right mechanism — OIDC federation or a managed identity — rather than minting another static secret. Throughout, someone is writing a timestamped timeline in the channel, and I give a status update every thirty minutes even when there is nothing new, because silence reads as loss of control.
What would you check before letting an AI agent run inside a customer's environment?
I treat the model as an untrusted component that can be made to do anything an attacker can get into its context, and I put the real security boundary at the tool layer rather than in the prompt. So: every tool is least-privilege and separately authorised, read-only by default, with write or destructive operations requiring explicit human confirmation and a role check. Any fetch or browse tool has an egress allow-list and cannot reach internal addresses or the metadata endpoint, enforced at the network layer as well as in code. Retrieval is permission-filtered at query time using the calling user's principals carried into the index as ACL metadata, because the question every customer asks is "can a junior retrieve the CFO's documents" and the answer has to be structurally no, not "the prompt says not to". Retrieved content is framed in the prompt as untrusted data that must never be followed as instructions, which reduces indirect prompt injection without eliminating it. Model output is treated exactly like user input — escaped on render, parameterised into any query, never passed to a shell or eval. Every tool invocation is logged with its arguments so an incident can be reconstructed. And on data flow, I document precisely what leaves the tenancy: which endpoint, which region, whether the provider's terms exclude training on the data, and what redaction happens before send, because that is the flow the customer's security team will focus on above all others.

TLS and certificates

  • TLS 1.2 minimum everywhere, 1.3 preferred; TLS 1.0/1.1 disabled
  • Full certificate chain served (leaf plus intermediates); verified with openssl s_client -showcerts
  • Automated renewal for every certificate, including internal and client certificates
  • Expiry alerting at 30/14/7 days, on both sides of any mTLS integration
  • Internal CA properly installed in every runtime's trust store; no verification disabled anywhere
  • Database connections use verify-full, not require

Identity

  • Authorisation code + PKCE for user flows; client credentials for machine-to-machine; no implicit or ROPC
  • Exact redirect URI matching; state and nonce validated on every callback
  • JWT validation checks signature, pinned algorithm, issuer, audience, expiry and tenant
  • JWKS cached, not fetched per request
  • Authorisation keyed on an immutable identifier, never email
  • Access tokens 5–15 minutes; refresh tokens rotated with reuse detection
  • Browser tokens in HttpOnly, Secure, SameSite cookies — not localStorage
  • MFA enforced for administrative access; provisioning and deprovisioning automated or reconciled

Application

  • Object-level authorisation on every endpoint; tenant isolation enforced in the data layer
  • All queries parameterised; no string-built SQL, shell commands or LDAP filters
  • Output escaped on render; CSP without unsafe-inline; frame-ancestors 'none'
  • No pickle or unsafe YAML deserialisation of untrusted input
  • URL-fetching features allow-listed, with private ranges blocked and redirects disabled
  • Security headers present; debug mode off; stack traces never returned to clients
  • Secrets from a managed store, never in config or environment-visible places; none in logs
  • Rate limiting and request size limits on every public endpoint

Operations

  • Authentication, authorisation-denial and administrative events logged with correlation IDs
  • Logs shipped off-host immediately; retention matches the audit period, not the platform default
  • Alerting on authentication-failure spikes, authorisation-denial spikes, and new privileged grants
  • Backups encrypted, and a restore tested within the last quarter with the output archived
  • Vulnerability scanning in the pipeline with an agreed remediation SLA and an exception register
  • Incident runbook written, with the customer's security contact and escalation path in it
  • Threat model documented and reviewed when the architecture changes

Practice lab plan

  1. Network fundamentalsTake a real service you run and map every hop with mtr, dig +trace, ss and tcpdump. Deliberately create each of the four failure modes — block a port with iptables to get a timeout, stop the service to get a refusal, point a name at the wrong address, and clamp MTU to 1200 — and learn the signature of each.
  2. CIDR drillGiven a /16, carve it for an AKS cluster, an application tier, private endpoints, an ingress subnet and a bastion, leaving half free. Then write the Python that proves non-overlap against a list of existing ranges. Do it until the arithmetic is instant.
  3. DNSStand up a split-horizon setup locally with dnsmasq or CoreDNS so the same name resolves differently from two networks. Break it with a stale TTL. Reproduce the Kubernetes ndots:5 search-domain storm and watch the query count in CoreDNS metrics.
  4. TLSBuild a two-level PKI with step-ca or OpenSSL: a root, an intermediate, and a leaf. Serve it from nginx. Then deliberately omit the intermediate and observe that the browser works while curl and Java fail. Issue a client certificate and get mTLS working end to end, then let it expire and read the error.
  5. InterceptionRun mitmproxy as a forward proxy with its own CA. Make Python, Node, Java, Git and Docker all work through it by fixing trust stores — with no verification disabled anywhere. This single exercise covers a large fraction of real FDE network pain.
  6. OAuth and OIDCStand up Keycloak locally. Implement authorisation code with PKCE by hand — no SDK — including state and nonce validation. Then write the token validation yourself and deliberately break each check in turn: accept an ID token at the API, skip audience validation, trust the header algorithm, and see exactly what becomes possible.
  7. SAMLConfigure Keycloak as a SAML IdP and a small app as the SP. Capture the SAMLResponse from the browser, decode it, and read every field. Then tamper with an attribute and confirm signature validation rejects it.
  8. AuthorisationBuild a two-tenant application with an intentional IDOR. Exploit it. Then fix it three ways — query-level scoping, an OPA policy, and Postgres row-level security — and write the generated cross-tenant test that covers every route.
  9. OWASP by handRun OWASP Juice Shop or WebGoat and work through injection, broken access control, XSS and SSRF until you can exploit each one without a walkthrough. Understanding the exploit is what makes the fix stick.
  10. SSRF and egressBuild a URL-fetch endpoint, exploit it against a local metadata simulator, then layer the defences: allow-list, resolve-and-check, no redirects, and finally an egress NetworkPolicy. Verify each layer independently.
  11. Threat modelTake something you have actually built and produce a one-page STRIDE table against its architecture diagram. Identify the three highest-risk flows and write the controls. Have someone try to poke holes in it.
  12. Incident drillRun a tabletop: "a service principal's secret was found in a public gist three days ago." Work through revoke, notify, preserve, assess blast radius, hunt for persistence, rotate, and write the timeline. Time yourself. Then write the runbook you wish you had had.
