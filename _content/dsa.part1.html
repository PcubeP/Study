How to Approach a Coding Interview

Most candidates lose points not because they lack knowledge, but because they jump straight to code. Interviewers are grading your process: how you clarify, how you reason about trade-offs, and how you verify. A repeatable framework keeps you calm and makes your thinking visible.

The UMPIRE framework

UMPIRE is a durable checklist you can run on any problem. It maps cleanly onto the shorter clarify → plan → code → test loop that experienced engineers use instinctively.

U — Understand

Restate the problem in your own words. Ask about input size, types, duplicates, empty/negative cases, and expected output format.

M — Match

Which known category is this? Sorting, graph search, DP, two pointers? Pattern-matching narrows the solution space fast.

P — Plan

Sketch the approach in plain language or pseudocode before typing. Agree on it with the interviewer.

I — Implement

Write clean, idiomatic code. Narrate as you go so your reasoning is auditable.

R — Review

Re-read your code line by line. Hunt for off-by-one errors, null handling, and mutation bugs.

E — Evaluate

State time and space complexity. Walk through examples and edge cases out loud.
Clarify-> Examples-> Plan-> Code-> Test-> Optimize
Fig 1. The core interview loop — clarify before you code, test before you declare done.
Tip Spend the first 2–3 minutes only on understanding and examples. A concrete worked example (including an edge case) catches most misunderstandings before they cost you.
Watch out Don't optimize prematurely. Get a correct brute-force solution verbalized first, then improve. A working O(n²) beats a broken O(n).

Communication checklist

  • Think out loud. Silence reads as being stuck.
  • Name your complexity as soon as you have an approach.
  • Ask before assuming — can inputs be empty? sorted? contain duplicates or negatives?
  • Dry-run your final code on one normal case and one edge case.

Big-O & Complexity Analysis

Big-O describes how an algorithm's running time or memory grows as the input size n grows. We drop constants and lower-order terms and keep the dominant growth term, because that is what matters at scale.

Fig 2. Growth curves. Flatter is better — small differences in order explode at large n.

Complexity cheat-sheet

NotationNameExample operationVerdict
O(1)ConstantArray index, hash lookup, stack pushExcellent
O(log n)LogarithmicBinary search, balanced-BST lookupExcellent
O(n)LinearSingle scan, linked-list traversalGood
O(n log n)LinearithmicMerge sort, heap sort, efficient sortsGood
O(n²)QuadraticNested loops, naive pair comparisonCaution
O(2ⁿ)ExponentialNaive recursion over subsetsBad
O(n!)FactorialBrute-force permutations (travelling salesman)Bad
Note Amortized complexity averages cost over a sequence of operations. A dynamic array's append is O(1) amortized even though occasional resizes cost O(n), because resizes are rare and double capacity.

Analyzing your own code

  • Sequential statements add: O(a) + O(b) = O(a + b).
  • Nested loops multiply: a loop inside a loop over n is O(n²).
  • Halving the input each step gives a log n factor.
  • Space counts auxiliary memory: the recursion call stack, extra arrays, and hash maps all add up.
Rule of thumb For n up to ~10⁵ an O(n log n) solution runs comfortably within a one-second limit. If n is tiny (≤ 20), an exponential solution may be acceptable — and sometimes expected.
