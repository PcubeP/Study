The Interview Framework

Every system design interview follows the same skeleton. Internalise this six-step arc and you will never lose the thread — even under pressure.

The six-step interview framework — work left to right, narrate each transition aloud.

Step 1 — Clarify Requirements

Never design until you ask. Spend 3–5 minutes surfacing functional and non-functional requirements. A missed assumption wastes 20 minutes of deep-dive on the wrong component.

Functional

What does the system do? Core user actions (write URL → get short URL; post tweet → timeline appears). Scope: read vs write flows, admin flows, mobile clients?

Non-Functional

Latency targets (p99 < 100 ms?), availability SLA (99.9% or 99.99%?), consistency model (strong vs eventual), geo distribution, security, compliance (GDPR?), cost sensitivity.

Step 2 — Estimate Scale

Back-of-envelope numbers anchor every architectural decision. Compute QPS, storage, and bandwidth before drawing a single box.

Step 3 — High-Level Design

Draw 5–8 components: clients, API gateway/LB, app servers, primary store, cache, async queue, CDN. Show data flow with arrows. Name the components clearly. Check in with the interviewer before going deep.

Step 4 — Deep-Dive

The interviewer will guide you to the hardest sub-problems: DB schema, consistency protocol, write path, failure handling. Lead with the most critical path. Speak complexity aloud.

Step 5 — Trade-offs

Every choice has a cost. SQL → strong consistency but limited horizontal scale. Kafka → high throughput but eventual delivery. Say "I chose X because Y, accepting Z." Interviewers reward trade-off reasoning over memorised answers.

Step 6 — Wrap-Up

Name 2–3 bottlenecks you haven't addressed (hot partitions, cache stampede, single-region fail). Suggest what to solve next. This signals engineering maturity.

Pro tip Draw on paper/whiteboard while narrating. An interviewer following your diagram retains it 3× better than one just listening.

Estimation Template

QPS

Peak QPS ≈ 2–3× average. Average = total requests per day ÷ 86 400. State read/write ratio (often 10:1 to 100:1).

Storage

Daily data = records/day × avg record size. Multiply by retention years. Add 20% overhead for indices, replication factor (usually 3).

Bandwidth

Ingress = write QPS × payload size. Egress = read QPS × response size. CDN can offload 80–95% of egress for media-heavy services.

Worked estimation: URL shortener at 100 M DAU

Writes: 1% of users create a short URL daily → 1 M writes/day ÷ 86 400 ≈ 12 writes/s.

Reads: 100:1 read/write ratio → 1 200 reads/s; peak 3× → ~3 600 reads/s.

Storage (5 years): 1 M new URLs/day × 365 × 5 = 1.825 B records. Each ~500 bytes (short key + long URL + metadata) → ~900 GB raw, ~2.7 TB with 3× replication.

Bandwidth: Read egress = 3 600 × 500 B ≈ 1.8 MB/s — trivial; most is HTTP redirects, not payload.

Note Estimation is about order of magnitude, not precision. Being off by 2× is fine. Reveal your assumptions explicitly — "assuming 100:1 read/write, roughly 10:1 peak/average…"

Load Balancers

A load balancer is the first distributed systems primitive. Know the layers, algorithms, and when sticky sessions matter.

L4 vs L7

Layer 4 (Transport)

Routes by IP + TCP port. Extremely fast — no HTTP parsing. Cannot inspect URL path, headers, or cookies. Used for raw throughput (databases, gRPC). Examples: AWS NLB, HAProxy in TCP mode.

Layer 7 (Application)

Routes by HTTP method, path, headers, cookies. Enables path-based routing (/api → service A, /static → CDN), SSL termination, health checks, WebSocket upgrades. Examples: AWS ALB, Nginx, Envoy.

Routing Algorithms

AlgorithmBest ForWeakness
Round-RobinHomogeneous servers, statelessIgnores server load
Least ConnectionsVariable request durationSlight overhead tracking connections
IP HashSticky sessions (stateful)Uneven distribution if few clients
Weighted Round-RobinHeterogeneous server capacityManual weight tuning
Least Response TimeLatency-sensitive APIsMore complex health tracking
RandomSimple, low overheadNot optimal; use for testing
Interview tip When the interviewer asks "how do you handle server failures?" — mention health checks (active probes every 5 s, passive circuit-breaking), automatic draining of in-flight connections, and auto-scaling triggers.

Health Checks & High Availability

LBs themselves are SPOFs — use an active-passive pair with a floating VIP (Virtual IP) and VRRP/ECMP. In cloud environments (AWS, GCP) the load balancer is a managed multi-AZ service and this is handled for you.

Caching

Caching is the single highest-leverage optimisation in most systems. Know the strategies, eviction policies, and failure modes cold.

Where to Cache

Client / Browser

Cache-Control headers, ETags. Zero server load for static assets. TTL-driven invalidation.

CDN Edge

Static + semi-static content served globally. Origin shield reduces origin traffic by 80–95%.

In-Process Memory

Fastest (nanoseconds). Limited to one server. Use for reference data — country codes, config flags.

Distributed Cache

Redis / Memcached shared across app servers. Millisecond latency. Central invalidation. 100 K–1 M+ ops/s per node.

DB Query Cache

Deprecated in MySQL 8+. Prefer application-level caching — more control, less contention.

Read Replicas

Not a cache per se, but offloads read traffic. Eventual consistency — replicas lag by milliseconds.

Cache Strategies

Three caching strategies — Cache-Aside is the default; Write-Through for read-heavy data that must be fresh; Write-Back for high-write, latency-sensitive workloads.

Eviction Policies

PolicyRuleUse When
LRU (Least Recently Used)Evict the key unused longestGeneral purpose — the safe default
LFU (Least Frequently Used)Evict the key hit least oftenLong-lived hot keys (song catalogue)
TTL (Time-to-Live)Expire after fixed durationSession tokens, OTP codes
FIFOEvict oldest inserted keyQueue-style, rare in caching
RandomEvict random keyApproximates LRU cheaply
allkeys-lru (Redis)LRU across all keys, no TTL requiredWhen TTLs are inconsistently set

Cache Failure Modes

Cache Stampede

Many threads miss simultaneously and all hit the DB. Fix with probabilistic early expiry, a mutex/lock on the first miss (cache aside with locks), or background refresh.

Cache Penetration

Queries for keys that never exist bypass the cache and hit the DB every time. Fix with a Bloom filter at the cache layer to reject known-absent keys.

Cache Avalanche

Many keys expire at the same time (e.g., after a cache flush). Fix with jittered TTLs — add ±10–20% random offset to each key's TTL.

Databases: SQL, NoSQL, and the CAP Theorem

Choosing the right database is the most consequential early decision. Understand the trade-offs, not just the names.

SQL vs NoSQL — When to Use Which

Relational (SQL)

Choose when: data has complex relationships, transactions span multiple tables (financial transfers, inventory), schema is stable, strong consistency is required. PostgreSQL is the modern default. MySQL for legacy systems. CockroachDB / Spanner for distributed ACID.

NoSQL

Choose when: massive scale (hundreds of millions of rows), flexible/evolving schema, high write throughput, simple access patterns (key-value, document). Cassandra for write-heavy time-series; MongoDB for document; DynamoDB for serverless key-value; Elasticsearch for full-text search.

Sharding / Partitioning

Sharding splits a dataset across multiple DB nodes. Each shard owns a range of keys. It is the primary path to horizontal write scaling.

StrategyHowProsCons
Hash Shardingshard = hash(key) % NEven distributionRange queries span all shards; resharding is painful
Range Shardingshard by key range (A–M, N–Z)Range queries efficientHot partition if range is uneven (time-series: latest shard gets all writes)
Directory / LookupMapping table: key → shard IDFlexible; easy reshardingLookup table is a SPOF; extra hop
Geo-Shardingshard by regionData locality, complianceCross-region queries slow
Warning Avoid cross-shard transactions whenever possible — they require distributed locks (2PC) and can degrade to O(n) latency. Design your data model to co-locate related records on the same shard.

Replication

Single-Leader

One primary accepts writes; replicas stream changes. Reads can go to replicas (replication lag ≈ ms). Most common. Failover: replica promoted on primary death.

Multi-Leader

Multiple nodes accept writes (geo-distributed teams, offline clients). Requires conflict resolution (last-write-wins, CRDTs, custom merge). Complexity cost is high.

Leaderless (Dynamo-style)

Any node accepts reads/writes. Quorum: W + R > N for consistency. Used in Cassandra, DynamoDB. Tunable consistency. Best for high availability.

The CAP Theorem

A distributed system can guarantee at most two of the three: Consistency, Availability, Partition Tolerance. Because network partitions are inevitable, you always choose between CP and AP.

CAP Triangle — real distributed systems sit on the CP or AP edge. CA is only possible without network partitions, i.e. single-node.
Note PACELC extends CAP: even without a partition (E), systems trade off Latency (L) vs Consistency (C). DynamoDB defaults to low latency with eventual consistency; it can be tuned toward consistency at the cost of latency.

Database Indexing Essentials

B-tree indexes (default in PostgreSQL/MySQL) excel at range queries and equality. Composite indexes follow left-prefix rules. Hash indexes suit exact equality only. Avoid over-indexing — each index adds write overhead and storage. Cover your most common query patterns; EXPLAIN ANALYZE every slow query.

Message Queues & Event Streaming

Async communication decouples services, absorbs traffic spikes, and enables durable processing. Know when to use a queue vs a stream.

Queue vs Stream

Message Queue (RabbitMQ, SQS)

Each message consumed once by one consumer. Message deleted on ACK. Best for task distribution, background jobs (send email, resize image). Supports fan-out via exchanges. Delivery guarantees: at-least-once or exactly-once (with transactions).

Event Stream (Kafka, Kinesis)

Log-based. Messages retained for days/weeks. Multiple consumer groups each read independently. Best for audit logs, analytics pipelines, CDC (Change Data Capture), event sourcing. Replay from any offset.

Kafka Architecture

Producer-> Topic Partitions-> Consumer Group A
    -> Consumer Group B

Kafka partitions enable parallel consumption. Within a partition messages are ordered. A consumer group scales horizontally up to the partition count — beyond that, consumers are idle. Key-based partitioning ensures ordering for related events (all events for user ID X go to the same partition).

ConceptKafkaRabbitMQ
ModelPersistent log / streamMessage queue (push)
RetentionDays to weeks (configurable)Until consumed/ACKed
OrderingPer-partitionPer-queue (FIFO)
ThroughputMillions/s per partitionTens of thousands/s
Consumer modelPull (consumer controls offset)Push (broker delivers)
ReplayYes — seek to any offsetNo — message gone after ACK
Best forEvent sourcing, analytics, CDCTask queues, RPC, work distribution
Tip When asked "how do you handle a spike in user uploads?" the answer is: write upload metadata to a Kafka topic; a downstream consumer pool processes them asynchronously. The API responds immediately; the queue absorbs the burst.

CDN & Rate Limiting

Content Delivery Network (CDN)

A CDN is a globally distributed cache of static (and increasingly dynamic) content. Edge nodes serve requests from the geographically nearest PoP (Point of Presence), reducing latency from hundreds of milliseconds to single-digit milliseconds.

Pull CDN

CDN fetches from origin on first cache miss, then caches. Simple to operate. Cold start latency on first request per edge. Examples: Cloudflare, Fastly.

Push CDN

You upload content to CDN nodes explicitly. Good for rarely-changing large files. Must manage cache invalidation. Examples: AWS CloudFront with S3 sync.

Use CDNs for: images/video, JavaScript/CSS bundles, HTML pages with long TTLs, API responses that are the same for all users (public product listings). Do not cache: personalised API responses, session-sensitive data.

Rate Limiting

Rate limiting protects services from abuse, runaway clients, and DDoS. Implement at the API gateway or a dedicated reverse proxy layer.

AlgorithmHowProsCons

API Design

API design is an interface contract. In system design interviews, briefly discuss the client-facing API before designing internals.

REST

Resource-oriented, stateless, HTTP verbs (GET/POST/PUT/PATCH/DELETE). Standard pagination: cursor-based (stable) or offset-based (simple but inconsistent on live data). Use HTTP status codes semantically: 200 OK, 201 Created, 400 Bad Request, 401 Unauthorized, 429 Too Many Requests, 503 Service Unavailable. Version via URL (/v1/) or Accept header.

gRPC

Protocol Buffers (binary serialisation), HTTP/2, bidirectional streaming, auto-generated clients. 5–10× smaller payload than JSON. Best for internal service-to-service communication. Requires HTTP/2 support from load balancers.

GraphQL

Client specifies exact fields needed. Eliminates over-fetching and under-fetching. Single endpoint. Trade-off: N+1 query problem mitigated by DataLoader (batching), but can be expensive server-side without query depth limits and cost analysis.

WebSocket

Full-duplex persistent connection. Use for: real-time chat, live dashboards, collaborative editing, notifications. Stateful — session is pinned to one server. Use IP-hash LB or move session state to Redis pub/sub for horizontal scaling.

API Gateway Pattern

Client-> API Gateway-> Auth Service
    -> Microservice A / B / C

The API gateway handles: authentication/authorisation, rate limiting, request routing, SSL termination, protocol translation (REST → gRPC), response aggregation, logging and tracing injection. Examples: AWS API Gateway, Kong, Nginx, Envoy.

Consistency Models

Distributed systems trade consistency for availability and latency. Know the spectrum — from strict serialisability to eventual consistency.

ModelGuaranteeLatencyExample
Strict SerialisabilityTotal order; reads see latest write globallyHighestSpanner, FoundationDB
LinearisabilityEvery operation appears instantaneous; real-time orderHighZookeeper, etcd
Sequential ConsistencyAll processes see same order; not necessarily real-timeMediumRaft consensus
Causal ConsistencyCausally related writes seen in order by all clientsMediumMongoDB sessions
Read-Your-WritesA client always sees its own writesLowSticky sessions or token routing
Eventual ConsistencyAll replicas converge given no new writesLowestDynamoDB default, DNS
Interview answer scaffold "For user profile reads after a write, I need read-your-writes consistency. I'll route all reads for a user to the same replica for 5 seconds after a write using a session token. For the global feed, eventual consistency is fine — a few seconds of staleness is invisible to users."

Achieving Read-Your-Writes at Scale

Three practical patterns: (1) route all requests for a user to the primary for N seconds after a write; (2) attach a "replication token" (write LSN) to the response and route reads to a replica only if its LSN ≥ token; (3) write to cache simultaneously on DB write so reads always find the latest version in cache.

Scalability Patterns

Scale by dimension: vertical (bigger box), horizontal (more boxes), or by sharding data and distributing state.

Vertical vs Horizontal Scaling

Vertical (Scale-Up)

Larger CPU, more RAM, faster SSD. Simple — no code changes. Hard ceiling (largest instance type). Single point of failure. Good for databases that resist horizontal sharding (complex joins, ACID transactions). Cost: diminishing returns beyond a threshold.

Horizontal (Scale-Out)

More servers behind a load balancer. Linear cost scaling. Requires stateless application tier — all state lives in shared storage (DB, Redis, object store). Fault tolerant — losing one node is not catastrophic. Required for >1 TB data or >100 K QPS sustained.

Stateless Services

A service is stateless when any instance can handle any request. Session state, user context, and ephemeral data must be externalised to Redis/Memcached (sessions), S3/GCS (file uploads), or a DB (persistent state). This is non-negotiable for horizontal scaling and zero-downtime deploys.

Database Scaling Ladder

Single DB-> Read Replicas-> Cache Layer-> Vertical Scale-> Sharding

Exhaust cheaper options before sharding. Sharding multiplies operational complexity: queries must be shard-aware, joins across shards are expensive, migrations require careful coordination.

Worked Example: URL Shortener

A URL shortener is the "hello world" of system design. Walk through the full design — estimation, schema, read/write paths, and failure handling.

Requirements

Functional

  • POST /shorten — accepts long URL, returns short code
  • GET /{code} — redirects to original URL (301/302)
  • Optional: custom aliases, expiry, click analytics

Non-Functional

  • 100:1 read/write ratio
  • Redirect latency p99 < 50 ms
  • 99.99% availability for redirects
  • Short codes: globally unique, hard to predict

Estimation

100 M DAU, 1% create URLs → 1 M writes/day ≈ 12 writes/s. Reads: 100:1 → 1 200 reads/s average, 3 600 reads/s peak. Storage: 1 M × 365 × 5 years × 500 B ≈ 900 GB. Bandwidth: trivial (HTTP redirects, no payload).

Short Code Generation

Options: (1) Random base62 (7 chars) — 62⁷ = 3.5 T URLs, collision probability low, but must check DB on collision; (2) Snowflake-style auto-increment ID → base62 — monotonically increasing, no collision check needed, reveals insertion order; (3) MD5/SHA hash of URL truncated — deterministic, deduplication free, but rare collision. Best answer: Snowflake ID (distributed, time-ordered, no collisions) encoded in base62 → 7 chars.

Architecture Diagram

URL Shortener architecture — write path (blue) vs read path (gold) with Redis cache-aside, read replicas, Kafka analytics stream, and a distributed Snowflake ID generator.

Read Path

GET /abc1234-> LB-> Read API-> Redis (hit?)-> 302 Redirect

On cache miss: Read API → DB Replica → populate Redis (TTL 24 h) → return 302. Click event published to Kafka asynchronously. Cache hit rate should be >95% for popular URLs; tail latency dominated by DB replica reads.

Write Path

POST /shorten-> Write API-> Snowflake ID-> base62 encode-> DB Primary-> Return short URL

DB Schema

SQL
CREATE TABLE url_map (
  id          BIGINT PRIMARY KEY,         -- Snowflake ID
  short_code  VARCHAR(10) NOT NULL UNIQUE, -- base62(id)
  long_url    TEXT        NOT NULL,
  user_id     BIGINT,
  created_at  TIMESTAMP   DEFAULT NOW(),
  expires_at  TIMESTAMP,
  click_count BIGINT      DEFAULT 0        -- updated by analytics consumer
);
CREATE INDEX idx_short_code ON url_map (short_code);

ML/LLM System Design

AI/ML workloads have unique infrastructure concerns: GPU affinity, large model weights, embedding indices, and streaming inference. Interviewers increasingly expect fluency here.

ML Model Serving Layer

Online Serving (Low Latency)

Real-time inference. Framework: TorchServe, Triton Inference Server, vLLM (for LLMs), ONNX Runtime. GPU instances (A10G/A100/H100). Batching: dynamic micro-batching (group requests in a 5–20 ms window). Auto-scaling on GPU utilisation + request queue depth.

Batch / Offline Serving

Bulk predictions — product recommendations, email content scoring, document classification. Spark / Ray for distributed processing. GPU spot instances for cost. Results written to a feature store or DB for downstream reads.

LLM Serving Optimisations

TechniqueWhat It DoesImpact
KV CacheCaches Key/Value attention tensors for the prompt prefixEliminates redundant prompt re-computation; critical for multi-turn chat
Continuous BatchingInterleave tokens from multiple requests mid-generation3–10× GPU utilisation improvement vs naive batching
Speculative DecodingSmall draft model proposes tokens; large model verifies2–4× throughput for low-temperature generation
Quantisation (INT8/INT4)Reduce weight precision2–4× memory reduction; slight quality trade-off
Tensor ParallelismShard weight matrices across GPUsFit larger models; latency scales sub-linearly
Prefix Caching (vLLM)Re-use KV cache across requests with identical system promptsDramatically reduces TTFT for shared-system-prompt workloads

RAG Pipeline at Scale

User Query-> Embed Query-> Vector DB ANN Search-> Top-K Chunks-> LLM + Context-> Response

Embedding Service

Dedicated embedding endpoint (e.g. text-embedding-3-small, GTE-large). Batch offline for document corpus. GPU for throughput; CPU for p99 latency with small models. Cache embeddings to avoid re-embedding identical chunks.

Vector Database

Stores dense vectors + metadata. ANN algorithms: HNSW (low latency, high recall), IVF-PQ (compression + speed). Options: Pinecone, Weaviate, Qdrant, pgvector (PostgreSQL). Scale: 100 M vectors needs dedicated vector DB, not in-process FAISS.

Retrieval Quality

Hybrid search: dense (semantic) + sparse (BM25 keyword) with RRF re-ranking. Chunk strategy: 256–512 token chunks with 10–20% overlap. Re-ranker (cross-encoder) re-orders top-K before sending to LLM. Metadata filters reduce search space.

Feature Store

A feature store centralises ML features so they are consistent between training and serving — eliminating training/serving skew. Offline store (S3 + Spark) for historical features. Online store (Redis/DynamoDB) for low-latency feature retrieval at serve time. Examples: Feast, Tecton, Vertex AI Feature Store.

ML System Design Checklist

Checklist
  • Define the ML task (classification, regression, ranking, generation)
  • Feature pipeline: sources → transform → online/offline store
  • Training: batch size, distributed training (DDP/FSDP), experiment tracking (MLflow, W&B)
  • Evaluation: offline metrics (AUC, NDCG, BLEU) vs online metrics (CTR, revenue)
  • Serving: online (latency < 100 ms) vs batch; model registry → canary deploy
  • Monitoring: data drift, concept drift, model performance decay, alerting
  • Feedback loop: user signals → labels → retraining pipeline

Q&A Practice

Drill these out loud. The ability to articulate concise answers under pressure is the interview skill.

How would you design Twitter's timeline?
Two approaches: (1) Fan-out on write — on tweet, push tweet ID to all followers' timeline caches in Redis. O(followers) write amplification; bad for celebrities. (2) Fan-out on read — merge timelines from followed users at read time. O(following) DB reads per page load. Hybrid: fan-out on write for <1 M followers; fan-out on read for celebrities. Cache precomputed timelines in Redis sorted sets (ZRANGEBYSCORE by timestamp).
How do you prevent a cache stampede?
Three patterns: (1) Probabilistic early expiry — before TTL expires, a small probability of refreshing on each read, so many callers don't all expire at once; (2) Mutex/lock on first miss — first thread to miss acquires a lock, fetches DB, populates cache; other threads wait and read from cache once populated; (3) Background refresh — a daemon refreshes keys proactively before TTL, so the cache never actually expires for hot keys.
Explain the difference between a message queue and an event stream.
A message queue (SQS, RabbitMQ) delivers each message to one consumer, deletes on ACK. An event stream (Kafka, Kinesis) is a durable log — messages are retained, and multiple independent consumer groups each read at their own offset. Use queues for task distribution; use streams for event sourcing, audit logs, and multi-consumer fanout.
When would you shard a database?
Only after exhausting: read replicas, caching, vertical scaling, and query optimisation. Sharding is warranted when: single-node write throughput is saturated (>~50 K writes/s), or data size exceeds single-node storage (~10 TB). Sharding adds complexity: cross-shard queries, distributed transactions, and resharding pain. Choose shard key carefully — avoid hot partitions; co-locate frequently joined data.
What is the CAP theorem and how does it guide database choice?
CAP: Consistency (all nodes return the same data), Availability (every request returns a response), Partition Tolerance (the system operates despite network splits). Since partitions are unavoidable in distributed systems, you choose CP (PostgreSQL, ZooKeeper — sacrifice availability under partition) or AP (Cassandra, DynamoDB — remain available, sacrifice strong consistency). For financial data: CP. For social feeds: AP with read-your-writes for self-reads.
How do you design a rate limiter at scale?
Use a Token Bucket algorithm (allows bursts) or Sliding Window Counter (accurate, low memory). Store counters in Redis with INCR+EXPIRE using a Lua script for atomicity. For multi-region: each region maintains a local counter (approximate global limit) or sync to a central Redis (exact but adds latency). Return 429 with Retry-After header. Apply limits at the API gateway before hitting application servers.
How does consistent hashing work and why is it used for sharding?
Nodes and keys are mapped to a hash ring (0 to 2³²). A key is owned by the first node clockwise from its hash. When a node is added/removed, only the keys between the new node and its predecessor move — typically 1/N of all keys, not all keys. This minimises data movement during scale-out events. Virtual nodes (vnodes) per physical node smooth key distribution and handle heterogeneous capacity.
How would you design a notification system for 100 M users?
Publisher writes notification event to Kafka. Fan-out service reads topic, looks up user device tokens, groups by channel (push/email/SMS). Channel workers (one per channel type) batch-send via Firebase FCM, AWS SES, Twilio. Store notification records in Cassandra (wide-column, write-heavy). Unread badge count in Redis INCR/DECR. For real-time: WebSocket gateway subscribes to a user-specific Redis pub/sub channel; notification event triggers push to connected clients.
What is read-your-writes consistency and how do you achieve it?
Read-your-writes guarantees that after you write, subsequent reads from the same session see your write. Strategies: (1) Route all reads to the primary for N seconds post-write; (2) Attach the write's LSN (log sequence number) to the response cookie; route reads to a replica only if replica_lsn ≥ write_lsn; (3) Populate the cache on write, so reads always hit the cache. Option 2 is cleanest for read-heavy workloads that have occasional writes.
How do you design a RAG system for 10 M documents?
Offline: chunk documents (256–512 tokens, 10% overlap) → embed with a sentence-transformer → store vectors + metadata in a dedicated vector DB (Qdrant/Weaviate with HNSW index). At query time: embed user query → ANN search (top-100) → BM25 keyword search → Reciprocal Rank Fusion → cross-encoder re-rank top-10 → inject into LLM context. Scale: dedicated embedding microservice (GPU or CPU depending on model size); vector DB sharded by document collection; KV cache for repeated system-prompt prefixes in vLLM.
What would you monitor in production for a system you just designed?
Four golden signals: Latency (p50/p99/p999), Traffic (QPS by endpoint), Errors (5xx rate, % of requests), Saturation (CPU/memory/disk, queue depth, DB connection pool). Plus: cache hit rate (if <80%, investigate), replication lag (if >1 s, investigate), queue consumer lag (Kafka: lag by consumer group), and business metrics (revenue, orders/min). Alert on anomaly detection (sudden drop in traffic = bad as much as sudden spike).
How does Kafka guarantee message ordering?
Kafka guarantees ordering within a partition. Messages with the same key always go to the same partition (key-based partitioning), so all events for a given entity (e.g. user_id=123) are ordered. Across partitions there is no total order — only per-partition ordering. For global order you would need a single partition (sacrificing parallelism) or a coordination layer. Consumer groups scale up to the partition count; adding more consumers than partitions yields idle consumers.

How to Communicate Your Design

Technical correctness is necessary but not sufficient. How you communicate is evaluated as heavily as what you design.

Narrate, Don't Draw in Silence

Speak every decision as you make it: "I'm adding a Redis cache here because reads are 100× more frequent than writes and DB latency would otherwise dominate." Silence reads as uncertainty. Narration shows reasoning, not just recall.

Check In Before Going Deep

After the high-level sketch, pause: "Does this structure look right to you? Is there a specific component you'd like me to go deeper on?" This prevents 20 minutes on the wrong deep-dive. It also shows collaborative instinct — a senior engineer would seek alignment before over-engineering one corner.

Lead with Trade-offs

Never present a decision without its cost: "I'm using eventual consistency here which means a user might see a stale count for a few seconds — that's acceptable for a social feed but I'd reconsider for financial transactions." Interviewers at senior levels are specifically listening for this vocabulary.

Name What You Are Not Solving

Explicitly park scope: "I'm not designing the recommendation engine today — that's a separate ML problem. I'll note it as a future extension." This demonstrates scope awareness and prevents rambling.

Handle Pushback Gracefully

When the interviewer challenges a decision, say: "That's a good point. If [concern] is true, the better approach would be [alternative] because [reason]. I chose the original approach assuming [assumption] — want me to redesign with your assumption?" This models how senior engineers actually change their minds.

Golden rule Drive the conversation. The best candidates never wait to be asked the next question — they say "Now that we have the high-level design, let me walk through the most interesting problem: how do we handle hot-key contention in the cache." Ownership of the narrative is itself a signal of senior-level behaviour.

Common Mistakes to Avoid

Jumping to Solutions

Saying "I'll use Kafka" before establishing the scale or requirement signals pattern-matching rather than reasoning. State the requirement first, then justify the choice.

Ignoring Failure Modes

Every component you add is a potential failure point. For each box you draw, briefly mention: what happens when it goes down? What is the fallback? What is the SLA impact?

Premature Optimisation

Designing for 1 billion users when the requirement is 10 million wastes interview time and signals poor prioritisation. Scale to the stated requirement; note what you'd change at 100×.

No Estimation

Skipping back-of-envelope math leaves your design ungrounded. Estimation reveals whether you need 1 server or 1 000. Always quantify before architecting.
