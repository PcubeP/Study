What DevOps Actually Means

DevOps is not a job title, a tool, or a team you can buy. It is a set of practices whose entire purpose is to shorten the distance between "a developer changed a line of code" and "that change is safely running in production, and we know it is working." Everything else — the YAML, the Terraform, the dashboards — exists to serve that one sentence. As a Forward Deployed Engineer you will walk into customers whose distance is measured in weeks and whose deployment process is a 14-page Word document, and your job is to compress it without breaking the controls their auditors depend on.

The origin of the problem

The traditional split was simple and destructive. Development was measured on throughput — ship features. Operations was measured on stability — change nothing. Those incentives are in direct opposition, so the interface between them became a gate: a release window, a ticket queue, a handover document, a change-advisory board. Every gate added latency, and because releases became expensive, they became large, and because they became large, they became risky, and because they became risky, more gates were added. That loop is the single most common pathology you will find in an enterprise customer.

DevOps breaks the loop by making deployment cheap and small. If deploying takes nine minutes and touches twelve lines, you do not need a war room. The counter-intuitive finding from a decade of DORA research is that speed and stability are not a trade-off — they are correlated. Teams that deploy more often have lower failure rates, because small changes are easier to reason about, easier to test, and trivially easy to revert.

The four DORA metrics

These come from Google's DevOps Research and Assessment programme and the book Accelerate. They are the only four numbers you need to describe the health of a delivery pipeline, and they are the first four numbers you should ask a customer for on day one. Two measure throughput, two measure stability.

Use these as a consulting wedgeDo not open a customer engagement by proposing a tool. Open it by instrumenting these four numbers from data they already have — git history, their CI system's API, their incident tracker. A one-page baseline ("your median lead time is 23 days, 70% of which is waiting for the Thursday CAB") converts arguments about tooling into arguments about evidence, and it gives you a before/after you can point at in six weeks.

A fifth metric was later added — reliability (how well the service meets its availability and latency targets) — because a team can optimise the first four and still deliver a fast, frequent, terrible service. In practice reliability is captured by SLOs and error budgets, which are covered properly in the observability guide; here it is enough to know that the pipeline must be able to answer "did this deploy make things worse?" automatically.

The three ways

Gene Kim's framing from The Phoenix Project is still the cleanest way to explain DevOps to a sceptical VP:

1. Flow

Optimise the whole left-to-right stream from idea to customer value. Make work visible, limit work in progress, reduce batch size, eliminate handoffs. A pipeline is the physical embodiment of flow.

2. Feedback

Create fast, constant right-to-left feedback. Tests that fail in four minutes, not four days. Monitoring that pages before the customer calls. Swarm on problems at the source rather than passing defects downstream.

3. Continual learning

Blameless postmortems, deliberate experimentation, converting local discoveries into global improvements. Chaos engineering and game days live here. So does writing the runbook before the incident.

What the FDE actually owns

On a customer site, you rarely get to build the platform team's dream. You get a GitLab instance from 2021 behind a corporate proxy, four shared runners, a change freeze from 15 December to 5 January, and a security team who have never approved a container registry. The DevOps work is 30% YAML and 70% negotiation: finding out who owns the runner fleet, what the egress rules are, which approval the auditors actually read, and what evidence satisfies them. Treat the organisational constraints as first-class engineering inputs, because they will shape the design more than any technical preference you have.

Anatomy of a Pipeline

Every CI/CD system — GitHub Actions, GitLab CI, Azure DevOps, Jenkins, Tekton, CircleCI, Buildkite — implements the same seven-stage shape with different nouns. Learn the shape once and the syntax becomes a lookup table. The shape is: something triggers a run, you build an artifact exactly once, you test and scan that artifact, you publish it somewhere immutable, you deploy it to successive environments, and you verify it works.

Trigger→ Build→ Test→ Scan→ Package→ Deploy→ Verify

Stage 1 — Trigger

What starts a run determines what the run is allowed to do. There are five triggers you will configure constantly:

  • Push to a branch — the fast feedback loop. Builds and tests, usually does not deploy.
  • Pull request opened/updated — the gate. Must run on a merge preview (the result of merging the PR into the target), not just the PR head, or you will merge code that was never tested in combination.
  • Tag push (e.g. v1.4.2) — the release. Produces a versioned, signed, published artifact.
  • Schedule (cron) — nightly full regression, dependency freshness checks, security rescans of already-published images (new CVEs appear against unchanged images every day).
  • Manual / API / upstream event — promotion between environments, emergency rollback, triggered by an ops tool or a webhook.
The pull_request_target trapIn GitHub Actions, pull_request from a fork runs with a read-only token and no secrets — safe. pull_request_target runs in the context of the base repository with full secrets, while checking out code the contributor controls. Combining pull_request_target with actions/checkout of github.event.pull_request.head.sha and then running a build script is a complete repository compromise: the attacker's package.json postinstall script runs with your secrets. This is a real, repeatedly-exploited pattern. If you must use it, check out only trusted paths and never execute contributor code.

Stage 2 — Build once

The single most important rule in the whole discipline: build the artifact exactly once, then promote that same artifact through every environment. If you rebuild for staging and rebuild again for production, you have not tested what you shipped. A transitive dependency published a new patch between the two builds; a base image tag moved; the build machine had a different toolchain. Your staging sign-off certified a different set of bytes.

Concretely this means the environment-specific parts — API endpoints, connection strings, feature flags, log levels — must be injected at runtime via environment variables, mounted config, or a config service. It must never be baked in at build time. The test for this is simple: can you take the exact image digest that is in production today and run it in dev by changing only environment variables? If not, you are not building once.

Stage 3 — Test

Tests are ordered by cost. Run the cheap ones first and fail fast: a 20-second lint failure should not wait behind a 14-minute integration suite. A practical ordering is lint and type-check, then unit tests, then component/integration tests against containers, then contract tests, then (post-deploy) smoke and end-to-end tests. Each layer gets its own job so the failure message tells you where the problem is without reading logs.

Stage 4 — Scan

Static analysis on your source (SAST), composition analysis on your dependencies (SCA), secret scanning on the diff and the full history, and vulnerability scanning on the built container image. Each produces findings with severities, and each needs a documented policy for what blocks a merge versus what files a ticket. Covered in depth in the DevSecOps section.

Stage 5 — Package & publish

Take the built artifact and put it somewhere immutable and addressable: a container registry (by digest), a package feed (npm/PyPI/Maven/NuGet), a release asset. Attach the metadata that makes it traceable — git SHA, build timestamp, SBOM, provenance attestation, signature. The rule here is that an artifact tag should never be reused. :latest is not a version; :1.4.2 must be immutable; the only truly safe reference is the digest.

Stage 6 — Deploy

Move the artifact into an environment. This should be a single idempotent operation that can be re-run safely — kubectl apply, helm upgrade --install, terraform apply, az webapp deploy. It must be the same operation in every environment, differing only in parameters, because that is what makes the production deploy boring: you have already executed it fifty times this week in dev.

Stage 7 — Verify

A deploy that "succeeded" because a command exited 0 proves nothing. Verification means: health endpoints return 200 with the expected version string; a handful of critical smoke tests pass against the real environment; error rate and latency stay within bounds for a defined bake period. If any of these fail, roll back automatically. Without this stage, your MTTR is however long it takes a human to notice.

BASH
#!/usr/bin/env bash
# verify.sh — post-deploy gate. Exits non-zero to trigger automated rollback.
set -euo pipefail

BASE_URL="${1:?usage: verify.sh <base-url> <expected-sha>}"
EXPECTED_SHA="${2:?}"
DEADLINE=$(( $(date +%s) + 180 ))

# 1. Wait for the new version to actually be serving.
until [ "$(date +%s)" -gt "$DEADLINE" ]; do
  got=$(curl -fsS --max-time 5 "$BASE_URL/healthz" | jq -r '.commit // "none"') || got="unreachable"
  if [ "$got" = "$EXPECTED_SHA" ]; then echo "version confirmed: $got"; break; fi
  echo "waiting: health reports '$got', want '$EXPECTED_SHA'"; sleep 5
done
[ "$got" = "$EXPECTED_SHA" ] || { echo "FAIL: version never rolled out"; exit 1; }

# 2. Critical-path smoke tests against the real environment.
curl -fsS --max-time 10 "$BASE_URL/api/v1/status" | jq -e '.database == "ok" and .cache == "ok"' >/dev/null \
  || { echo "FAIL: dependency health check"; exit 1; }

code=$(curl -s -o /dev/null -w '%{http_code}' -X POST "$BASE_URL/api/v1/search" \
       -H 'content-type: application/json' -d '{"q":"smoke"}')
[ "$code" = "200" ] || { echo "FAIL: search returned HTTP $code"; exit 1; }

# 3. Bake: error rate must stay under 1% for 120s (Prometheus-backed).
sleep 120
err=$(curl -fsS "$PROM_URL/api/v1/query" --data-urlencode \
  'query=sum(rate(http_requests_total{status=~"5..",app="checkout"}[2m]))/sum(rate(http_requests_total{app="checkout"}[2m]))' \
  | jq -r '.data.result[0].value[1] // "0"')
awk -v e="$err" 'BEGIN{ exit !(e < 0.01) }' || { echo "FAIL: error rate ${err}"; exit 1; }

echo "VERIFY PASSED"
Pipeline design heuristicsTarget under 10 minutes for the PR pipeline — beyond that developers context-switch and stop watching it. Make every job independently re-runnable. Never let a pipeline step depend on mutable external state (a tag that moves, pip install without a lockfile, a shared database). Put the slowest reliable signal as early as you can afford it. And print the exact reproduction command on failure, so the developer's first action is make test-integration, not "open the web UI and squint".
Build once, promote the digest, inject configuration at runtime, verify after every deploy.

Branching, Releases and Versioning

Branching strategy is not a style preference — it determines how often you can integrate, how painful merges are, and whether continuous integration is even possible. A customer running three-month feature branches cannot do CI by definition, no matter what their Jenkins server does. Changing the branching model is often the highest-leverage change you can make, and it is also the one that generates the most emotion, so bring data.

The three models you will meet

Trunk-based development

Everyone commits to main, or to branches that live hours, not days. Incomplete work is hidden behind feature flags. Release by tagging main, or by cutting a short-lived release branch. Requires strong tests and flags. This is what elite DORA performers do.

GitHub Flow

main is always deployable. Short-lived feature branches, PR, review, squash-merge, deploy. No develop, no release branches. The pragmatic default for web services deployed continuously. Trunk-based with a PR gate.

GitFlow

main, develop, feature/*, release/*, hotfix/*. Designed in 2010 for versioned desktop software with multiple supported versions in the field. Heavy merge overhead. Its own author now recommends against it for continuously delivered web apps.

Do not evangelise trunk-based into an on-prem product teamIf the customer ships software that runs in their customers' data centres and must support v3.2, v4.0 and v4.1 simultaneously with backported security fixes, GitFlow-style release branches are the correct answer, not legacy thinking. Ask "how many versions are live in the field right now?" before recommending anything. One answer means trunk-based; five answers means release branches.

Semantic versioning

MAJOR.MINOR.PATCH — a contract with consumers, not decoration.

  • MAJOR — you broke backward compatibility. Consumers must change code. Removed an endpoint, renamed a field, tightened validation, changed a default.
  • MINOR — you added functionality, backward compatible. New optional field, new endpoint, new config option with a safe default.
  • PATCH — bug fix only, no interface change.
  • Pre-release: 1.4.0-rc.1, 2.0.0-beta.3. Build metadata: 1.4.0+20250612.9f3c21a (ignored for precedence).
  • 0.y.z means "anything may change". Going to 1.0.0 is a promise about stability, so do not do it casually.

For internal services deployed continuously, many teams use CalVer (2025.06.12) or just the commit SHA, because nobody is pinning against your version — there is one consumer and it is you. For anything a customer integrates against (a library, an API, a CLI you hand over), SemVer is non-negotiable, and the first customer escalation about an unannounced breaking change will teach you why.

Conventional commits and automated changelogs

A structured commit message format that lets you derive the version bump and the changelog mechanically:

TEXT
<type>(<optional scope>): <description>

[optional body]

[optional footer(s)]

TYPES    feat (MINOR) | fix (PATCH) | docs | style | refactor | perf | test | build | ci | chore | revert
BREAKING append ! after type/scope, or add a "BREAKING CHANGE:" footer -> MAJOR

EXAMPLES
  feat(auth): support device-code flow for CLI login
  fix(ingest): handle UTF-16 CSV exports from the customer SFTP drop
  perf(search): cache embedding lookups, p95 1.8s -> 240ms
  refactor!: drop Node 16 support

  BREAKING CHANGE: minimum runtime is now Node 20; the Dockerfile base image changed.

With this in place, semantic-release, release-please or changesets will compute the next version, write CHANGELOG.md, tag the repo, and publish — with zero human judgement about version numbers. That removes an entire category of release-day argument.

YAML
# .github/workflows/release.yml — fully automated SemVer release from conventional commits
name: release
on:
  push:
    branches: [main]
permissions:
  contents: write        # create tags and releases
  issues: write
  pull-requests: write
  id-token: write        # npm provenance / OIDC
jobs:
  release:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }      # semantic-release needs full history to find the last tag
      - uses: actions/setup-node@v4
        with: { node-version: '20', cache: npm, registry-url: 'https://registry.npmjs.org' }
      - run: npm ci
      - run: npx semantic-release
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
          NPM_TOKEN: ${{ secrets.NPM_TOKEN }}

Release branches and hotfixes

Even on trunk-based teams you will eventually cut release/4.2 because a customer froze on it. The rules that keep this sane: fixes land on main first, then cherry-pick to the release branch (never the reverse, or the fix is lost on the next release); release branches are deleted when the version is EOL; and every release branch has its own pipeline that runs the full suite, because nobody is watching it daily.

BASH
# Hotfix discipline: fix forward on main, then backport.
git switch main && git pull
git switch -c fix/token-refresh-race
# ... fix, test ...
git commit -m "fix(auth): guard token refresh with a mutex to stop duplicate refreshes"
# merge the PR to main, note the resulting squashed SHA
git switch release/4.2 && git pull
git cherry-pick -x 7ab1c39          # -x records the original SHA in the message — essential for audit
git push                            # release pipeline builds 4.2.7 and ships it

# Verify a fix is present on every live branch before closing the ticket:
for b in main release/4.2 release/4.1; do
  printf '%-14s ' "$b"
  git log --oneline "origin/$b" --grep='token refresh race' | head -1 || echo 'MISSING'
done
Branch protection is where policy becomes realOn main: require pull requests, require at least one approving review (two for anything touching auth or billing), require status checks to pass, require branches to be up to date before merging, require signed commits if the customer's policy demands it, dismiss stale approvals on new pushes, and forbid force-push and deletion. Enforce for administrators too — an auditor will ask whether admins can bypass, and "yes" is a finding.

GitHub Actions in Depth

GitHub Actions is the system you are most likely to be handed, and the one where the gap between "works" and "production-grade" is largest. A workflow is a YAML file in .github/workflows/; it contains jobs; jobs contain steps; steps either run a shell command or uses an action. Everything else is detail — but the detail is where the security incidents and the 40-minute build times live.

A complete, production-shaped workflow

YAML
name: ci

on:
  push:
    branches: [main]
    tags: ['v*.*.*']
  pull_request:
    branches: [main]
  workflow_dispatch:
    inputs:
      deploy_env:
        description: 'Environment to deploy to'
        type: choice
        options: [dev, uat, prod]
        default: dev

# Least privilege by default; individual jobs widen this.
permissions:
  contents: read

# One run per branch; cancel superseded runs on PRs but never on main.
concurrency:
  group: ci-${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: ${{ github.event_name == 'pull_request' }}

env:
  REGISTRY: ghcr.io
  IMAGE_NAME: ${{ github.repository }}

jobs:
  # ---------------------------------------------------------------- fast gate
  lint:
    runs-on: ubuntu-latest
    timeout-minutes: 10
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: '3.12', cache: pip }
      - run: pip install -r requirements-dev.txt
      - name: ruff
        run: ruff check --output-format=github .
      - name: mypy
        run: mypy --strict src/

  # ---------------------------------------------------------- matrix unit test
  test:
    runs-on: ${{ matrix.os }}
    timeout-minutes: 25
    strategy:
      fail-fast: false            # see every failing combination, not just the first
      max-parallel: 6
      matrix:
        os: [ubuntu-latest, windows-latest]
        python: ['3.10', '3.11', '3.12']
        include:
          - os: ubuntu-latest
            python: '3.12'
            coverage: true        # only upload coverage from one canonical combination
        exclude:
          - os: windows-latest
            python: '3.10'        # customer does not run this combination
    services:
      postgres:
        image: postgres:16-alpine
        env:
          POSTGRES_PASSWORD: test
          POSTGRES_DB: appdb
        ports: ['5432:5432']
        options: >-
          --health-cmd "pg_isready -U postgres"
          --health-interval 5s --health-timeout 5s --health-retries 10
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: ${{ matrix.python }}
          cache: pip
          cache-dependency-path: requirements*.txt
      - run: pip install -r requirements.txt -r requirements-dev.txt
      - name: pytest
        env:
          DATABASE_URL: postgresql://postgres:test@localhost:5432/appdb
        run: |
          pytest -n auto --dist loadgroup \
                 --junitxml=reports/junit-${{ matrix.os }}-${{ matrix.python }}.xml \
                 --cov=src --cov-report=xml --cov-report=term-missing
      - name: Enforce coverage floor
        if: matrix.coverage
        run: |
          pct=$(python -c "import xml.etree.ElementTree as E;\
print(round(float(E.parse('coverage.xml').getroot().get('line-rate'))*100,1))")
          echo "coverage=${pct}%"
          awk -v p="$pct" 'BEGIN{ exit !(p >= 80) }' || { echo "::error::coverage ${pct}% < 80%"; exit 1; }
      - uses: actions/upload-artifact@v4
        if: always()              # upload test reports even when the job failed
        with:
          name: junit-${{ matrix.os }}-${{ matrix.python }}
          path: reports/
          retention-days: 7

  # ------------------------------------------------------------- build + push
  build:
    needs: [lint, test]
    runs-on: ubuntu-latest
    timeout-minutes: 30
    permissions:
      contents: read
      packages: write           # push to GHCR
      id-token: write           # OIDC for keyless signing
      attestations: write
    outputs:
      digest: ${{ steps.push.outputs.digest }}
      version: ${{ steps.meta.outputs.version }}
    steps:
      - uses: actions/checkout@v4

      - uses: docker/setup-buildx-action@v3

      - uses: docker/login-action@v3
        with:
          registry: ${{ env.REGISTRY }}
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - id: meta
        uses: docker/metadata-action@v5
        with:
          images: ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}
          tags: |
            type=semver,pattern={{version}}
            type=semver,pattern={{major}}.{{minor}}
            type=sha,format=long
            type=ref,event=branch
            type=raw,value=latest,enable={{is_default_branch}}

      - id: push
        uses: docker/build-push-action@v6
        with:
          context: .
          platforms: linux/amd64,linux/arm64
          push: ${{ github.event_name != 'pull_request' }}
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          cache-from: type=gha
          cache-to: type=gha,mode=max
          provenance: true
          sbom: true

      - name: Generate build provenance attestation
        if: github.event_name != 'pull_request'
        uses: actions/attest-build-provenance@v1
        with:
          subject-name: ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}
          subject-digest: ${{ steps.push.outputs.digest }}
          push-to-registry: true

  # ------------------------------------------------------------------- deploy
  deploy-dev:
    needs: build
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    environment:
      name: dev
      url: https://dev.internal.example.com
    permissions:
      id-token: write           # OIDC to Azure — no stored credentials
      contents: read
    steps:
      - uses: actions/checkout@v4
      - uses: azure/login@v2
        with:
          client-id: ${{ vars.AZURE_CLIENT_ID }}
          tenant-id: ${{ vars.AZURE_TENANT_ID }}
          subscription-id: ${{ vars.AZURE_SUBSCRIPTION_ID }}
      - name: Deploy by digest, never by tag
        run: |
          az containerapp update -n app-dev -g rg-platform-dev \
            --image "${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}@${{ needs.build.outputs.digest }}"
      - name: Verify
        run: ./scripts/verify.sh https://dev.internal.example.com "${{ github.sha }}"

  deploy-prod:
    needs: [build, deploy-dev]
    if: startsWith(github.ref, 'refs/tags/v')
    runs-on: ubuntu-latest
    environment:
      name: production          # required reviewers + wait timer configured in repo settings
      url: https://app.example.com
    permissions: { id-token: write, contents: read }
    steps:
      - uses: actions/checkout@v4
      - uses: azure/login@v2
        with:
          client-id: ${{ vars.AZURE_CLIENT_ID_PROD }}
          tenant-id: ${{ vars.AZURE_TENANT_ID }}
          subscription-id: ${{ vars.AZURE_SUBSCRIPTION_ID_PROD }}
      - run: |
          az containerapp update -n app-prod -g rg-platform-prod \
            --image "${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}@${{ needs.build.outputs.digest }}"
      - run: ./scripts/verify.sh https://app.example.com "${{ github.sha }}"
      - name: Roll back on verification failure
        if: failure()
        run: az containerapp revision set-mode -n app-prod -g rg-platform-prod --mode single &&
             az containerapp ingress traffic set -n app-prod -g rg-platform-prod --revision-weight latest=0 prior=100

Caching — where your build minutes go

Dependency installation usually dominates CI time. actions/setup-* has built-in caching for the common package managers, which is the first thing to turn on. For anything else, use actions/cache and get the key right: the key must change when the inputs change, and restore-keys gives you a partial hit to build from.

YAML
      - uses: actions/cache@v4
        with:
          path: |
            ~/.cache/pip
            ~/.cache/ms-playwright

          key: ${{ runner.os }}-py${{ matrix.python }}-${{ hashFiles('requirements*.txt', 'poetry.lock') }}

Cache poisoning is a real attack pathCaches are scoped per branch, but a cache written on a feature branch is readable from main's base branch scope in some configurations. OIDC: deleting your long-lived cloud credentials

The default pattern — paste an AZURE_CLIENT_SECRET or an AWS access key into repository secrets — creates a credential that lives forever, works from anywhere, and appears in every fork request your security team reviews. OIDC federation replaces it: GitHub mints a short-lived, signed JWT describing the workflow run, the cloud validates it against a trust policy, and issues a token valid for about an hour. Nothing long-lived is stored anywhere.

  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "Federated": "arn:aws:iam::123456789012:oidc-provider/token.actions.githubusercontent.com" },
    "Action": "sts:AssumeRoleWithWebIdentity",
    "Condition": {
      "StringEquals": {
        "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",

Self-hosted runners

In a customer tenancy you will usually run self-hosted. The things that bite:

  • Never attach a self-hosted runner to a public repository. A fork PR can execute arbitrary code on your machine inside the customer's network. GitHub warns about this; people do it anyway.
  • Ephemeral runners. Use --ephemeral (or Actions Runner Controller / autoscaling sets) so each job gets a clean machine. Persistent runners accumulate state and let one job poison the next.
  • Labels are your scheduling API. runs-on: [self-hosted, linux, x64, gpu, dmz] — be specific, because a job that lands on the wrong runner fails in confusing ways.
  • Runner groups restrict which repositories may use which runners. Production-network runners should be available to exactly the repositories that need them.
  • Outbound-only networking. The runner polls GitHub over HTTPS 443; GitHub never connects inbound. This is the fact that gets runners through a firewall review.
  • Disk. Docker layer caches and workspace directories fill disks silently. Schedule docker system prune -af --filter "until=168h" and monitor free space — "job failed with no space left on device" is the most common self-hosted outage.

Supply-chain hygiene for actions themselves

  • Pin third-party actions to a full commit SHA, not a tag: uses: foo/bar@a1b2c3d4.... Tags are mutable; the tj-actions/changed-files compromise in 2025 rewrote tags across thousands of repos.
  • Use permissions: at workflow and job level. Default to contents: read.
  • Restrict which actions can run at all (organisation setting: allow only GitHub-verified plus an explicit allow-list).
  • Enable Dependabot for github-actions so pinned SHAs still get updated.
  • Audit GITHUB_TOKEN default permissions at the organisation level — set them to read-only and widen per workflow.

The Azure DevOps footgun: compile-time vs runtime${{ }} is evaluated when the YAML is expanded, before anything runs — it can drive if on templates and loops, but cannot see anything computed by a job. $(var) is a runtime macro, expanded when the step executes. $[ ] is a runtime expression, used in condition: and to read job outputs. Jenkins, in one breath

You will meet it. A declarative Jenkinsfile with pipeline { agent { label 'linux' } stages { stage('Build') { steps { sh 'make' } } } } covers 80% of cases. Shared libraries live in a separate repo under vars/ and are loaded with @Library('corp-pipeline@v2'). The real risks are: pipelines written in Groovy scripted syntax that nobody understands; plugins pinned to versions with known CVEs; build logic that lives in the Jenkins UI rather than in the repo (invisible to code review and impossible to restore); and a single master with no backup of $JENKINS_HOME. When you meet one of these, migrating the logic into repo-resident shell scripts or a Makefile first — so the CI system only calls make ci-test — makes any future migration almost free. That refactor is often the best first deliverable.

An artifact is the output of your build that moves through environments. Everything about how you store and label it determines whether, nine months later, you can answer the question "is the version running in production affected by this CVE?" — which is exactly the question a customer's security team will ask you at 7pm on a Friday.

A machine-readable inventory of every component in your artifact: name, version, licence, supplier, and the hash. Two formats matter: SPDX (ISO standard, licence-compliance heritage) and CycloneDX (OWASP, security heritage, richer vulnerability model). Generate both if the customer is undecided; they are cheap.

Provenance and signing

An SBOM says what is inside. Provenance says where it came from: which source repo, which commit, which builder, which workflow, at what time. The SLSA framework defines levels; SLSA Build L3 effectively requires a hosted, non-falsifiable builder that produces signed provenance — which GitHub Actions' attest-build-provenance and GitLab's SLSA provenance give you nearly for free.

BASH

# Verify, pinning WHO signed it and WHICH workflow produced it

  --certificate-identity "https://github.com/acme/app/.github/workflows/release.yml@refs/tags/v1.4.2" \
  --certificate-oidc-issuer "https://token.actions.githubusercontent.com"

cosign verify-attestation --type slsaprovenance \
  --certificate-identity-regexp '^https://github.com/acme/' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  "ghcr.io/acme/app@sha256:3b8c..." \
| jq -r '.payload' | base64 -d \

Flaky tests — treat them as production incidents

A flaky test is a test that passes and fails on identical code. Its real cost is not the re-run; it is that the team learns to ignore red. Once "just re-run it" is normal, a genuine regression ships.

Common causes

Shared mutable state between tests; dependence on test execution order; sleep() instead of waiting on a condition; real clocks and timezones; real network calls; unseeded randomness; parallel tests sharing a database row, port, or temp file.

The policy that works

Detect (re-run failures once and flag any test that passes on retry), quarantine within 24 hours (move it out of the blocking suite into a tracked list), ticket it with an owner, and cap the quarantine list — if it exceeds ten, fixing flakes becomes the team's priority. Never leave a blanket retries: 3 on the whole suite; that hides the signal permanently.

pytest --lf                                      # last failed only

Coverage gates that are not theatre

A global "80% coverage" threshold on a legacy codebase either blocks every PR or gets lowered until it is meaningless. The useful gate is diff coverage: lines changed in this PR must be covered. It is achievable, it ratchets quality upward, and it never punishes a developer for the state of code they did not write.

Secrets Management

Every credential you handle on a customer engagement belongs to them, and losing one is a reportable incident on their side with your name on it. The hierarchy is simple: no secret is better than a short-lived secret, which is better than a long-lived secret in a vault, which is infinitely better than a long-lived secret in git.

The ladder, best to worst

  1. No secret at allWorkload identity: the compute resource has an identity the cloud recognises. Azure Managed Identity, AWS IAM roles for service accounts (IRSA), GCP Workload Identity, Kubernetes projected service account tokens. Nothing to steal, nothing to rotate.
  2. Federated short-lived credentialOIDC from the CI system to the cloud. A token valid for about an hour, scoped to one repository and environment, minted per run. This is the correct answer for pipelines.
  3. Vault-issued dynamic secretHashiCorp Vault's database engine creates a Postgres user on request with a 1-hour TTL and revokes it automatically. Leaked credentials expire before anyone can use them.
  4. Static secret in a managed storeAzure Key Vault, AWS Secrets Manager, GCP Secret Manager, Vault KV. Encrypted, access-controlled, audited, versioned, rotatable. Acceptable where nothing better exists.
  5. CI platform secret storeGitHub/GitLab/ADO encrypted variables. Fine for CI-only values; harder to rotate centrally and harder to audit across many repositories.
  6. Environment variable on a VMVisible in /proc/<pid>/environ, in crash dumps, in docker inspect, and in logs when something prints the environment.
  7. In the repositoryPermanent. Git history is forever, forks exist, and it is in every developer's laptop backup. This is an incident, not a mistake.

Why a file beats an environment variableEnvironment variables are inherited by every child process, appear in docker inspect and /proc, land in crash dumps, and get printed by well-meaning debug code. A file on tmpfs can be read by the one process that needs it, can be re-read when rotated without a restart, and never shows up in a stack trace. Where the framework supports it, read secrets from files.

Rotation

Rotation is not "change the password once a year". It is a tested, automated capability. The design pattern is two-slot: provision credential B while A is still valid, update consumers to B, verify, then revoke A. Applications must therefore accept two valid credentials during the overlap — that requirement is an application design decision, and if you do not make it early, rotation means downtime and the customer will stop doing it.

  • Inventory every secret with owner, store, consumer list, rotation method, and last-rotated date.
  • Automate: Key Vault/Secrets Manager rotation functions, Vault dynamic engines, cloud-native key rotation.
  • Rehearse rotation in a lower environment on a schedule. An untested rotation runbook is a decorative document.
  • Alert on expiry before it happens — 30/14/7 days. Certificate and secret expiry is a top-three cause of enterprise outages.

Infrastructure as Code: Concepts

Infrastructure as Code means the authoritative definition of your infrastructure is a file in version control, and the live environment is derived from it. The point is not automation for its own sake — it is that infrastructure becomes reviewable, diffable, testable, reproducible and auditable. A customer who can show an auditor a git history of every infrastructure change has solved a compliance problem that used to require a person and a spreadsheet.

Declarative vs imperative

DeclarativeImperative
You writeThe desired end stateThe steps to get there
Engine doesDiffs current vs desired, computes actionsExecutes your steps in order
Re-runningNo-op if already correctMay duplicate or fail unless you code the guards
ExamplesTerraform, Bicep/ARM, CloudFormation, Kubernetes manifests, Pulumi (declarative model in a real language)az/aws CLI scripts, bash, Ansible (mostly declarative modules, imperative ordering)
WeaknessFights you on anything the provider does not model; state managementDrift, partial failure leaves unknown state, no plan

The four properties that matter

Idempotency

Running the same definition twice produces the same result, and the second run changes nothing. This is what makes it safe to run the pipeline on every merge and what makes recovery possible: re-apply and the environment converges.

Drift

The gap that opens when someone changes the live environment by hand. Detect it on a schedule (terraform plan -detailed-exitcode in a nightly job), alert on it, and either codify the change or revert it. Undetected drift means your next apply silently destroys an emergency fix someone made at 3am.

Immutable infrastructure

Never patch a running server; build a new image and replace it. Eliminates snowflake servers and configuration entropy. The test: can you terminate any instance at random and be fine in ten minutes? If not, you have pets.

Reproducibility

Can you stand up an identical environment in a new region or subscription from the repository alone? This is both a DR capability and the fastest way to give a customer a clean, isolated test environment — and it is the thing that pins down every undocumented manual step.

ClickOps is the enemy, and the portal is where it startsEvery manual change in a cloud console is invisible to your code, absent from the audit trail, and lost on the next apply. The practical countermeasure in a customer tenancy: give humans read-only access to production, make the pipeline's service principal the only identity with write permission, and provide a documented break-glass path (a privileged identity, time-boxed, alerting the security channel on use, with a mandatory post-hoc codification task). Enforcement without a break-glass path just gets your controls bypassed.

State — the part that bites

Terraform's state file is the mapping between the resources in your code and the real objects in the cloud. It is also, unavoidably, a store of everything Terraform knows — including generated passwords, connection strings and certificate private keys, in plaintext JSON.

  • Treat state as a production secret. Encrypted at rest, access restricted to the pipeline identity and a small break-glass group, access logged. Never in a git repository.
  • Remote backend with locking — Azure blob leases, S3 + DynamoDB (or S3 native locking), GCS, Terraform Cloud. Two concurrent applies without a lock will corrupt state.
  • Versioning on the state container, so you can roll back to yesterday's state when something goes wrong. You will need this at least once.
  • One state per blast radius. Networking, shared data services, and per-app resources in separate state files. A single monolithic state means a 25-minute plan and one mistake that can destroy everything.
  • Cross-state references via terraform_remote_state data sources, or better, by looking resources up through data sources/tags so the coupling is looser.

Two errors that cause real outages(1) Running terraform apply from a laptop against production. It bypasses the plan review, may use a stale provider version, and if the laptop sleeps mid-apply you get a half-finished change and a stuck lock. Apply only from the pipeline. Modules

A module is a directory of .tf files with inputs and outputs. Good modules are small, opinionated, and own one logical thing. Signs you have it wrong: a module with 40 variables (it is a thin wrapper over the provider — delete it and use the resource directly), or a module that takes a provider block (callers should pass providers explicitly). Version module sources: git::https://git.corp.local/platform/tf-modules.git//network?ref=v2.3.1. An unpinned module source means someone else's commit changes your production plan.

Workspaces vs directories

Terraform workspaces give you multiple states from one configuration. They are fine for ephemeral, identical environments (per-PR preview stacks). They are a poor fit for dev/uat/prod, because real environments differ structurally (prod has geo-redundancy, a WAF, a different network), the difference ends up as sprawling conditionals, and a single terraform workspace select mistake applies dev config to prod. Prefer separate directories or separate backend keys per environment with explicit -var-file, which makes the environment visible in the command and in the pipeline logs.

CloudFormation and CDK (AWS)

CloudFormation is AWS's native declarative service with managed state, change sets (the plan equivalent), stack policies, drift detection and automatic rollback on failure. Deployment Strategies and Rollback

How you move traffic to new code determines your blast radius. The choice is a trade-off between infrastructure cost, deployment time, and how many users see a bad release. Customers almost always ask for "zero downtime" without having thought about what their database migrations or stateful sessions require, so part of your job is turning that phrase into specific constraints.

          readinessProbe:
            httpGet: { path: /readyz, port: 8080 }
            periodSeconds: 5
            failureThreshold: 3
          livenessProbe:
            httpGet: { path: /livez, port: 8080 }
            initialDelaySeconds: 30

            periodSeconds: 5                        # allows 150s for a slow JVM start
Readiness and liveness are not the same probeReadiness answers "should I receive traffic right now?" — failing it removes the pod from the service endpoints. Liveness answers "am I unrecoverably broken?" — failing it kills the pod. Pointing liveness at an endpoint that checks the database means a brief database blip restarts every pod simultaneously and turns a 30-second degradation into a full outage. Liveness should check only the process itself.

Database migrations — the real constraint

During a rolling or canary deploy, two versions of your code talk to one database. Any migration that is not backward compatible breaks the old version while it is still serving. The answer is the expand/contract (parallel change) pattern, executed across at least two releases:

  1. ExpandAdd the new nullable column / new table / new index. Deploy the migration alone. Old code ignores it; nothing breaks.
  2. Dual-writeRelease code that writes both old and new, reads old. Backfill the new column in batches, off-peak, with rate limiting.
  3. Switch readsRelease code that reads new, still writes both. Verify with a reconciliation query that the two agree.
  4. Stop writing oldRelease code that uses new only.
  5. ContractIn a later release, drop the old column. Only now, and only once no rollback target still needs it.
SQL
-- NEVER in a rolling deploy: breaks every running old pod instantly
ALTER TABLE invoices RENAME COLUMN amount TO amount_cents;

-- Expand/contract instead
-- Release 1
ALTER TABLE invoices ADD COLUMN amount_cents BIGINT NULL;
CREATE INDEX CONCURRENTLY idx_invoices_amount_cents ON invoices (amount_cents);  -- no table lock

-- Release 2: app dual-writes. Backfill in bounded batches to avoid a long transaction.
UPDATE invoices SET amount_cents = ROUND(amount * 100)
 WHERE amount_cents IS NULL AND id BETWEEN :lo AND :hi;

-- Release 3: reads switch; reconcile before proceeding
SELECT count(*) FROM invoices WHERE amount_cents <> ROUND(amount * 100);  -- must be 0

-- Release 4 (days later, after the rollback window closes)
ALTER TABLE invoices DROP COLUMN amount;

Also: every migration needs a tested down-path or an explicit "forward only, rollback is a new migration" policy. And ALTER TABLE on a 400-million-row table in Postgres or MySQL can hold a lock long enough to take the application down — use CONCURRENTLY, pt-online-schema-change or gh-ost, and rehearse on a production-sized copy.

GitOps with Argo CD and Flux

GitOps inverts the deployment direction. Instead of the pipeline pushing changes into the cluster (which requires giving CI powerful, long-lived cluster credentials), an agent inside the cluster pulls the desired state from git and continuously reconciles reality to match. Git becomes the single source of truth, and "what is running in production?" is answered by reading a repository rather than querying a cluster.

Push versus pull deployment. The pull model removes the cluster credential from CI entirely — which is often what unblocks a customer security review.

Repository layout

Separate the application repository from the config repository. The app repo holds source and builds images; the config repo holds Kubernetes manifests, Helm values and Kustomize overlays. CI's last step is to open a pull request against the config repo bumping the image digest. That PR is the deployment record: reviewed, approved, timestamped, and revertible with git revert.

Secrets in GitOps

Git is the source of truth, but you cannot put secrets in it. Three workable answers: External Secrets Operator (the manifest references a secret by name; the operator fetches it from Key Vault/Vault/Secrets Manager at runtime — preferred); Sealed Secrets (encrypt with the cluster's public key, commit the ciphertext, only that cluster's controller can decrypt); or SOPS + age/KMS (encrypt values in YAML, decrypt in the Flux kustomize-controller). Never commit a plain Secret with base64 data — base64 is encoding, not encryption, and that finding appears in every GitOps security review.

In a startup, "deploy to prod" is a button. In a bank, it is a process with named approvers, a change record, a risk classification, a back-out plan, a test evidence pack and a window. You will not abolish that process, and attempting to is how FDEs lose credibility in week two. What you can do is automate the production of the evidence it consumes, so the process costs minutes instead of days.

Change management, made cheap

An ITIL change record typically needs: what is changing, why, risk assessment, affected services, implementation plan, back-out plan, test evidence, and approver. Every one of those can be generated from the pipeline.

Standard (pre-approved) changes are the prizeMost ITIL frameworks allow a "standard change" category: a low-risk, well-understood, repeatable change that is pre-approved and does not need a CAB each time. Getting your deployment classified as a standard change is the single highest-leverage conversation you can have with a customer's change manager. The evidence you need is a track record — "forty deployments, zero change-related incidents, automated rollback demonstrated, every step logged". Start collecting that from day one so you can make the case in month three.

Change freezes

Retail freezes from November to January; banks freeze at quarter-end; everyone freezes at Christmas. Plan around them: know the dates before you plan a delivery milestone, agree in advance what qualifies as an emergency change and who can approve one out of hours, and keep shipping to lower environments so you are not stacking up a terrifyingly large first release in January. A frozen production with an active UAT is manageable; a three-month accumulation of unreleased change is not.

Evidence for auditors

  • Who approved — environment approval records in the CI system, immutable, with timestamps and identities.
  • What was deployed — image digest, git SHA, and the signed provenance attestation tying the two together.
  • Separation of duties — the person who wrote the code is not the person who approved the production deploy (configure it: branch protection plus environment reviewers excluding the author).
  • Test evidence — JUnit XML and coverage reports retained with the run, linked from the change record.
  • Security scan results — SARIF uploaded, findings triaged, suppressions justified and expiring.
  • Access control — who can modify the pipeline definition, who can change branch protection, who holds break-glass.
  • Retention — artifact and log retention periods that satisfy the customer's policy (often seven years in finance). Default CI retention is 30–90 days; this gap is a standard audit finding.

Corporate TLS interception

The symptom is instantly recognisable:

The proxy terminates TLS, inspects, and re-signs with the corporate root CA. Your OS may trust it; your language runtimes each maintain their own trust store and do not. Fix every store, and never use the "disable verification" escape hatch — it is a finding on their own pen test and it trains the team to turn off security when something is inconvenient.

Air-gapped builds

Interview Questions

What are the four DORA metrics, and what would you do first if a customer's lead time was 23 days?
Deployment frequency and lead time for changes measure throughput; change failure rate and mean time to restore measure stability. The important finding is that they are correlated rather than opposed — teams that deploy more frequently also fail less, because small changes are easier to reason about and revert. With a 23-day lead time my first action is not to change tooling, it is to decompose the 23 days: pull commit timestamps from git, deployment timestamps from the CI system, and plot where the time actually goes. In my experience the build itself is usually 40 minutes of it and the remaining 22 days are waiting — waiting for a reviewer, waiting for a weekly CAB, waiting for a shared UAT environment to be free. Each of those has a different fix: review SLAs and smaller PRs, getting the deployment classified as a pre-approved standard change, and ephemeral per-PR environments respectively. Measuring first means I am arguing about the customer's own data rather than my preferences, which is the only argument that wins in an enterprise.
Why is "build once, promote the same artifact" so important, and how do you enforce it?
If you rebuild the application for each environment, the thing you tested in UAT is not the thing you shipped to production. Between the two builds a transitive dependency published a patch, a base image tag moved, or the build agent had a different compiler — so your UAT sign-off certified different bytes. You enforce it by building a single immutable artifact, addressing it by content digest rather than a mutable tag, and injecting all environment-specific configuration at runtime through environment variables, mounted files or a config service. The practical test is: can you take the exact digest running in production today, start it in dev with only environment variables changed, and have it work? If any environment name, endpoint or credential is baked into the image, the answer is no. In the pipeline this shows up as the deploy job referencing image@sha256:... carried as a job output from the build stage, never a tag that a later build could overwrite.
Explain OIDC federation for CI, and the most common way people misconfigure it.
Instead of storing a long-lived cloud credential in CI secrets, the CI platform mints a short-lived JWT describing the run — repository, branch or tag, environment, workflow file — signed by its own OIDC issuer. The cloud provider is configured to trust that issuer and to exchange the token for temporary credentials when the token's claims match a trust policy. Nothing long-lived exists anywhere, so there is nothing to leak or rotate, and the credential only works from a matching workflow run. The classic misconfiguration is an overly permissive subject condition — using StringLike with repo:org/repo:* or a wildcard across the organisation. That means any branch, including one an attacker pushes after compromising a single developer account, can assume the production role. The correct scope pins to a specific environment (repo:org/repo:environment:production) and relies on that environment having required reviewers, or pins to an exact ref. The second common mistake is forgetting permissions: id-token: write on the job, which produces a confusing "unable to get ACTIONS_ID_TOKEN_REQUEST_URL" error.
A customer insists on GitFlow. When is that actually the right answer?
When they have multiple versions live in the field simultaneously. If they ship software that runs in their own customers' data centres and must support v3.2, v4.0 and v4.1 with backported security fixes, long-lived release branches are a genuine requirement, not nostalgia. The first question I ask is "how many versions are in production right now, and who decides when a customer upgrades?" If the answer is one version and they control it, GitFlow's develop branch and release branches are pure overhead and I would move them to trunk-based or GitHub Flow with feature flags. If the answer is five versions across different customers, I would keep release branches and instead focus on the discipline that makes them safe: every fix lands on main first and is cherry-picked forward with -x so the provenance is recorded, every release branch runs the full pipeline on its own schedule, and there is an explicit EOL date after which a branch is deleted. Pushing an inappropriate branching model is a fast way to lose credibility in week two.
Walk me through what you would do if a production API key appeared in a public repository.
Rotate first, clean second — the order matters because history rewriting is slow and the key is already compromised. Step one is revoking the credential at the source and issuing a replacement, within minutes. Step two is determining blast radius: pull the cloud provider's audit logs filtered on that credential from the date of the commit forward, looking for use from unfamiliar IPs or unusual API calls, because that determines whether this is a hygiene issue or a breach requiring notification. Step three is cleaning history with git filter-repo, force-pushing with lease, and telling every developer to re-clone, because old clones still contain the secret. Step four is asking the hosting platform to purge cached views of the commit, since the commit remains reachable by SHA even after a force push. Step five is filing the incident record the customer's policy requires — trying to handle it quietly is both a policy breach and, practically, how a small problem becomes a trust problem. Then the prevention work: pre-commit gitleaks hooks for speed, server-side secret scanning in CI because hooks can be bypassed, and moving that class of credential onto OIDC or a managed identity so there is nothing to leak next time.
What is Terraform state, and what are the ways teams destroy themselves with it?
State is Terraform's mapping between the resource addresses in your configuration and the real objects in the provider, plus a cache of their attributes. Terraform needs it to compute a diff; without it, it believes nothing exists. The failure modes I plan against are: keeping state local or in git, which breaks team collaboration and leaks secrets since state stores generated passwords and keys in plaintext; running concurrent applies without locking, which corrupts state; one monolithic state file for an entire estate, which gives you 25-minute plans and a single mistake that can destroy everything; and losing or deleting the state file, after which the next apply tries to recreate the world. The defences are a remote backend with locking and object versioning, treating the state container as a production secret with access restricted to the pipeline identity, splitting state by blast radius — network, shared data services, per-application — and applying only from CI against a saved plan file so that what is applied is exactly what was reviewed. I also run a nightly terraform plan -detailed-exitcode for drift detection, because exit code 2 tells me someone changed something by hand before the next deploy silently reverts their emergency fix.
Compare blue-green and canary. How do you choose?
Blue-green runs two complete environments and switches the router atomically: rollback is a second switch and takes seconds, but every user moves at once so a bad release affects everyone for however long it takes to notice, and you pay for double capacity during the window. Canary sends a small percentage of traffic to the new version, observes real metrics, and ramps gradually: the blast radius is bounded to the canary percentage and the decision can be automated against error rate and latency, but it takes longer and requires both versions to coexist — which means your API and database schema must be backward compatible throughout. I choose canary for risky, user-facing, behavioural changes where I want real traffic to be the test, and blue-green when I need an instant, total cutover, typically for an infrastructure-level change or where coexistence is impossible. In both cases the deciding constraint is usually the database: if the release includes a schema change that is not backward compatible, neither strategy is safe and the real work is splitting the migration into expand/contract phases across several releases.
What is GitOps, and what specific problem does it solve that a push pipeline does not?
In GitOps an agent runs inside the target cluster, pulls the desired state from a git repository, and continuously reconciles the live state to match it. Two things follow. First, CI no longer needs cluster credentials — there is no inbound path to the cluster at all, which is frequently the thing that unblocks a customer security review, because "your build system holds cluster-admin and can reach production" is a hard objection to argue against. Second, because reconciliation is a loop rather than a one-shot push, manual drift is detected and, with self-heal enabled, reverted within a few minutes. That converts "we audit configuration quarterly" into a continuously enforced control, which is exactly what an auditor wants to hear. The practical pattern is a separate config repository: the application pipeline builds an image and opens a pull request bumping the digest, so the deployment record is a reviewed, approved, timestamped commit that can be reverted with git revert. The part people underestimate is secrets — you cannot commit them, so you need External Secrets Operator, Sealed Secrets or SOPS in place before GitOps is usable for anything real.
You join a customer where every deploy requires a CAB meeting on Thursdays. What do you do?
I do not try to abolish the CAB; that fails and costs me credibility. I find out what the CAB actually needs to approve a change and automate the production of exactly that evidence. In most ITIL implementations the record needs: what is changing and why, risk classification, affected configuration items, implementation plan, back-out plan, test evidence and approver. Every one of those can be generated from the pipeline — the change log from git between tags, linked tickets from commit messages, test results from the JUnit report, the back-out plan from the fact that rollback is an automated traffic shift that was demonstrated in UAT. Then I aim for the real prize, which is getting this deployment classified as a standard pre-approved change. That requires a track record: a number of deployments with zero change-related incidents, a demonstrated automated rollback, and a complete audit trail. So from day one I collect that evidence deliberately, and around month two or three I take it to the change manager with a specific proposal. Meanwhile I keep shipping to lower environments continuously so the Thursday release is small, which also reduces its risk and helps the argument.
Your build fails on the customer's runner with "certificate verify failed" but works on your laptop. What is happening and how do you fix it properly?
The customer's network is terminating TLS at a forward proxy, inspecting the traffic, and re-signing it with an internal root CA. Their managed laptops trust that CA, but the runner's language runtimes maintain their own trust stores and do not. The fix is to install the internal root CA into the operating system trust store and then into each runtime's store individually, because Python's requests uses REQUESTS_CA_BUNDLE, Node uses NODE_EXTRA_CA_CERTS, Java uses its own cacerts keystore via keytool, Git has http.sslCAInfo, and containers need the CA copied into both the builder and runtime stages of the Dockerfile. I package all of that as a composite action or a base image so it is applied consistently rather than rediscovered by each team. What I will not do is set NODE_TLS_REJECT_UNAUTHORIZED=0 or pip --trusted-host, because those disable verification entirely, they inevitably become permanent, and they will be a finding on the customer's own pen test. While I am there I also check NO_PROXY includes 169.254.169.254, because routing the instance metadata endpoint through a proxy breaks managed identity in a way that looks completely unrelated.
What is an SBOM and why has it suddenly become a procurement requirement?
A Software Bill of Materials is a machine-readable inventory of every component in a build artifact — name, version, supplier, licence and hash — in either SPDX or CycloneDX format. It became a requirement because of US Executive Order 14028 and the EU Cyber Resilience Act, and because of Log4Shell: when that landed, the question "are we affected?" took most organisations weeks to answer, and a lot of them never answered it confidently. With SBOMs attached to every published image as OCI referrers, that question becomes a query that runs in seconds across every deployed digest. Generating one in CI with syft costs about fifteen seconds; retrofitting one to a release that shipped eighteen months ago costs a week of archaeology. The related artifact is provenance — a signed attestation saying which repository, commit, workflow and builder produced the image, which is what SLSA formalises. Together they let a customer verify both what is inside an artifact and where it came from, and with a Kyverno or Gatekeeper admission policy they can refuse to run anything that does not carry a valid signature from their own release workflow.
How do you build software in an air-gapped customer environment?
You accept that every external input must come in through their controlled import process, and you design the pipeline around that constraint rather than fighting it. Base images get mirrored into their internal registry with skopeo, either registry-to-registry if there is a one-way path, or to a directory for physical transfer. Dependencies get vendored on a connected machine — pip download with explicit platform and Python version so the wheels match the target, npm ci with a packed cache, go mod vendor, mvn dependency:go-offline — and the build runs with the offline flags. Terraform providers need a filesystem mirror configured in .terraformrc. Scanner vulnerability databases need exporting too, or Trivy fails on a database download you will not notice until it silently stops finding anything. GitHub Actions have to be vendored into their internal instance or checked in. The most important non-technical part is documenting the import process itself — who approves, what scan must pass, how long it takes — because if importing a new base image takes five working days, that is a hard dependency on your sprint plan and it needs to be visible to the delivery manager, not discovered on the Thursday before a milestone.

Hardening Checklist and Two-Week Lab Plan

Two artifacts to take onto an engagement: a checklist you can run against any customer pipeline in an hour and turn into a prioritised findings list, and a hands-on plan that builds the muscle memory before you need it under pressure.

Pipeline hardening checklist

Source control

  • Branch protection on main: PR required, at least one approval, status checks required, branch up to date before merge
  • Force-push and branch deletion disabled, and protection enforced for administrators
  • Stale approvals dismissed on new pushes; CODEOWNERS required for sensitive paths (auth, infra, pipeline definitions)
  • Secret scanning enabled with push protection; gitleaks in pre-commit and in CI
  • Signed commits where customer policy requires; a documented, alerting break-glass path

Pipeline definition

  • Default token permissions read-only at the organisation level; widened per job with an explicit permissions: block
  • Third-party actions pinned to full commit SHAs; an organisation allow-list for which actions may run at all
  • No attacker-controllable input (title, body, branch name) interpolated directly into a shell run block
  • No pull_request_target executing contributor-supplied code
  • Self-hosted runners are ephemeral, never attached to public repositories, grouped by network zone
  • Every job has a timeout-minutes; concurrency groups prevent overlapping production deploys

Credentials

  • OIDC federation or managed identity instead of long-lived cloud keys
  • OIDC trust policies scoped to a specific environment or ref, with no wildcards
  • Production credentials only reachable from the production environment, which has required reviewers
  • Every remaining static secret has a named owner, a store, a rotation method and a last-rotated date
  • Rotation rehearsed in a lower environment within the last 90 days

Artifacts

  • Tag immutability enabled in the registry; deployments reference digests, not tags
  • SBOM generated and attached for every published artifact
  • Images signed; admission control rejects unsigned or unattested images in production namespaces
  • Retention periods satisfy the customer's audit policy, not the platform default
  • Base images mirrored internally; no anonymous pulls from Docker Hub in the build path

Testing and gates

  • PR pipeline under 10 minutes; tests sharded by historical duration
  • Diff coverage gate rather than a global percentage; mutation testing nightly on critical modules
  • Flaky test quarantine process with owners and a capped backlog; no blanket suite-wide retries
  • SAST, SCA, secret, IaC and container scans wired in with a written, time-boxed triage policy
  • No allow_failure: true or continue-on-error quietly disabling a security gate
  • Policy-as-code evaluated against the Terraform plan JSON, not just the source files

Deployment

  • Automated post-deploy verification that asserts the running version equals the expected SHA
  • Automated rollback on verification failure, demonstrated in a lower environment this quarter
  • Database migrations follow expand/contract; no destructive change in the same release as the code that needs it
  • Production deploy requires an approver who is not the change author
  • Drift detection running on a schedule and alerting to a channel someone reads

Two-week hands-on lab plan

Everything below runs on a free GitHub account plus a free-tier cloud subscription. Do it with your hands, not by reading.

  1. Day 1 — A pipeline from zeroCreate a small Python or Node service with real tests. Write a workflow that lints, tests and uploads coverage. Deliberately break it four ways — a failing test, a syntax error in the YAML, a missing dependency, a permissions error — and read each failure message until the shape is familiar.
  2. Day 2 — Matrix, caching, speedAdd a three-version matrix with fail-fast: false. Add dependency caching and measure the before/after. Add a service container running Postgres and write one integration test that exercises a real migration. Target: full pipeline under five minutes.
  3. Day 3 — Containers and registryWrite a multi-stage Dockerfile with a non-root user. Build and push to GHCR with docker/metadata-action producing semver, SHA and branch tags. Deploy by digest. Verify with docker pull by digest that you get the same bytes.
  4. Day 4 — Supply chainGenerate an SBOM with syft, scan it with grype, sign the image keylessly with cosign, and attach a provenance attestation. Then verify the signature while deliberately using the wrong certificate identity so you see the failure, not just the success.
  5. Day 5 — Security scanningAdd gitleaks, Semgrep and Trivy. Commit a fake AWS key on a branch and watch the scan catch it. Add a deliberate SQL injection and watch Semgrep flag it. Write one custom Semgrep rule for a pattern specific to your codebase. Upload SARIF and look at the Security tab.
  6. Day 6 — OIDC, no stored keysDelete every cloud secret from your repository. Configure OIDC federation to Azure or AWS with a trust policy pinned to one environment. Make it fail first with a wildcard subject you then tighten, and decode the token claims to see exactly what is being matched.
  7. Day 7 — Review and write upDocument what you built as if handing it to a customer platform team: a README, a one-page architecture note, and the five things that would break it.
  8. Day 8 — Terraform fundamentalsProvision a resource group, storage account and container app from scratch. Configure a remote backend with locking. Run plan, read every line of the output, then apply. Change something in the portal by hand and watch the next plan detect the drift.
  9. Day 9 — Terraform structureRefactor into modules with typed variables and validation. Add for_each, moved blocks and lifecycle rules. Import a manually created resource. Write two .tftest.hcl tests. Break state deliberately in a sandbox and recover it from a versioned blob.
  10. Day 10 — Policy as codeWrite three Rego policies: required tags, no public storage, no deletion of stateful resources. Run them against terraform show -json in CI. Write opa test unit tests for the policies themselves.
  11. Day 11 — Deployment strategiesDeploy to a Kubernetes cluster (kind or a managed free tier). Implement a rolling update with correct readiness, liveness and startup probes. Then install Argo Rollouts and run a canary with a Prometheus analysis template. Force it to fail and watch the automatic abort.
  12. Day 12 — GitOpsSplit into an app repo and a config repo. Install Argo CD, set up app-of-apps, enable selfHeal. Run kubectl edit against a live deployment and watch it revert. Wire External Secrets Operator so no secret is in git.
  13. Day 13 — The hostile environmentRun your whole pipeline behind a proxy with TLS inspection (mitmproxy makes this easy locally). Fix every certificate error properly. Then disconnect the network entirely and get the build working from vendored wheels and a mirrored base image.
  14. Day 14 — Make it auditableAdd environments with required reviewers, generate a change record from the pipeline, retain test and scan evidence, and write the one-page "how to deploy and how to roll back" runbook. Then have someone else follow it without your help — that is the only real test of a handover.
What to carry onto every engagementA recon script that profiles a runner in sixty seconds. A composite action or base image that installs the corporate CA and proxy settings. A reusable workflow for build-scan-sign-publish. A Terraform module skeleton with remote state, tagging validation and a plan-then-approve pipeline. A set of Rego policies for the usual suspects. And the change-record generator. Those six artifacts turn the first two weeks of every engagement from improvisation into configuration.
