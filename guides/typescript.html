Why TypeScript, and When Plain JS Is Fine

TypeScript is JavaScript with a static type system bolted on at build time and erased at run time. That single sentence explains both its enormous value and every frustrating thing about it. As a Forward Deployed Engineer you will meet TypeScript in three places — the customer's frontend, their Node services, and the glue code you write to integrate with their APIs — and in all three, the types are the fastest way to understand a codebase you have never seen.

#1REASON TEAMS ADOPT IT: REFACTORING CONFIDENCE

What you actually get

Refactoring without fear

Rename a field on a widely used object and the compiler lists every place that must change. In a 200-file JavaScript codebase that same rename is a grep and a prayer. This is the benefit teams cite most, and it is the one that compounds.

Documentation that cannot rot

A function signature tells you what it needs and returns, and the compiler enforces that the signature is true. Comments lie after six months; types cannot, because the build fails.

Editor intelligence

Autocomplete that knows your domain, inline errors as you type, go-to-definition that works across packages. On an unfamiliar codebase this is how you orient in hours instead of days.

What you do not get

Types do not exist at runtimeTypeScript compiles to JavaScript by deleting the types. A value that arrives from fetch, JSON.parse, process.env, a form, or a database driver is typed by your assertion, not by any check. If the API returns {"id": "42"} and you declared id: number, TypeScript is perfectly happy and your arithmetic silently produces "421". Every boundary where data enters your program needs runtime validation — usually Zod. This is the single most important thing to understand about TypeScript and the most common cause of production bugs in "fully typed" codebases.

Setup: tsc, tsconfig and Bundlers

Most people's first painful day with TypeScript is a configuration problem, not a type problem. The compiler has roughly a hundred flags, about ten of which matter, and getting module resolution wrong produces errors that look like type errors but are not. Learn the ten flags and you will never fight the toolchain again.

Getting started

Primitives, Literals, Arrays, Tuples and the Three Special Types

The base of the type system is small, and three of its members — any, unknown and never — carry almost all the subtlety. Getting those three right separates people who write TypeScript from people who write JavaScript with annotations.

Primitives and inference

TYPESCRIPT
// Let inference do the work. Explicit annotations here add noise, not safety.
const name = "Pranit";          // type: "Pranit"  (literal, because const)
let city = "Pune";              // type: string    (widened, because let)
const count = 42;               // type: 42
const active = true;            // type: true
const nothing = null;           // type: null
const missing = undefined;      // type: undefined
const big = 9007199254740993n;  // type: bigint
const sym = Symbol("key");      // type: symbol

// Annotate where inference cannot help: function parameters and empty containers
function greet(who: string): string {
  return `Hello, ${who}`;
}
const ids: string[] = [];       // without this it is never[], and push fails

Literal types and widening

TYPESCRIPT
type Status = "draft" | "published" | "archived";

let s1 = "draft";               // string - widened
const s2 = "draft";             // "draft" - not widened

function publish(status: Status) { /* ... */ }
publish(s2);                    // OK
publish(s1);                    // ERROR: string is not assignable to Status

// Three ways to stop widening
const config1 = { status: "draft" as const };        // status: "draft"
const config2 = { status: "draft" } as const;        // whole object deeply readonly
const config3: { status: Status } = { status: "draft" };

// as const is the idiomatic way to build a lookup table AND its union type
const ROLES = ["admin", "editor", "viewer"] as const;
type Role = typeof ROLES[number];                    // "admin" | "editor" | "viewer"

const HTTP_STATUS = {
  OK: 200,
  NOT_FOUND: 404,
  SERVER_ERROR: 500,
} as const;
type StatusCode = typeof HTTP_STATUS[keyof typeof HTTP_STATUS];   // 200 | 404 | 500

Arrays, readonly arrays and tuples

TYPESCRIPT
const names: string[] = ["a", "b"];
const nums: Array<number> = [1, 2];               // identical; style preference

// readonly prevents mutation through this reference
const frozen: readonly string[] = ["a", "b"];
// frozen.push("c");                               // ERROR
const frozen2: ReadonlyArray<string> = ["a"];      // same thing

// Tuples: fixed length, position-specific types
type Point = [x: number, y: number];               // named elements are docs only
type Entry = [key: string, value: unknown];
type Range = [min: number, max: number, inclusive?: boolean];

const p: Point = [10, 20];
const [x, y] = p;                                  // x: number, y: number

// Variadic tuples
type Head<T extends readonly unknown[]> = T extends readonly [infer H, ...unknown[]] ? H : never;
type Tail<T extends readonly unknown[]> = T extends readonly [unknown, ...infer R] ? R : never;

type A = Head<[1, 2, 3]>;                          // 1
type B = Tail<[1, 2, 3]>;                          // [2, 3]

// This is how useState gets its type
function useLocal<T>(initial: T): [T, (next: T) => void] {
  let value = initial;
  return [value, (next) => { value = next; }];
}
noUncheckedIndexedAccess changes array accessWith the flag on, names[0] has type string | undefined, because TypeScript cannot know the array is non-empty. This is correct and initially annoying. Handle it with a guard, at() plus a check, or destructuring with a default. The flag catches a real bug class — iterating to length and off-by-one indexing — and is worth the noise on new code. Enabling it on a large existing codebase will produce hundreds of errors, so do that incrementally.

TYPESCRIPT
// Numeric enum - avoid. Values are numbers, reverse-mapped, and it emits runtime code.

TYPESCRIPT
// any is contagious - it disables checking everywhere it flows
const data: any = JSON.parse(raw);
data.user.profile.name.toUpperCase();     // compiles. Crashes at runtime.
const n: number = data.anything;          // compiles. Probably wrong.

// unknown forces you to prove the shape
const safe: unknown = JSON.parse(raw);
// safe.user;                              // ERROR - good
if (typeof safe === "object" && safe !== null && "user" in safe) {
  // narrowed enough to access .user, though you still need validation for depth
}

// never: the exhaustiveness check that makes unions safe to extend
type Shape =
  | { kind: "circle"; radius: number }
  | { kind: "square"; side: number }
  | { kind: "rect"; w: number; h: number };

function area(s: Shape): number {
  switch (s.kind) {
    case "circle": return Math.PI * s.radius ** 2;
    case "square": return s.side ** 2;
    case "rect":   return s.w * s.h;
    default: {
      // If someone adds a new member to Shape, s is no longer never
      // and THIS LINE fails to compile. That is the whole point.
      const exhaustive: never = s;
      throw new Error(`Unhandled shape: ${JSON.stringify(exhaustive)}`);
    }
  }
}

// never as a return type: this function does not return normally
function fail(message: string): never {
  throw new Error(message);
}

// never in a union disappears
type T = string | never;                   // string
The exhaustiveness pattern is the highest-value idiom in TypeScriptAdd a case to a union — a new payment method, a new event type, a new error code — and every switch that handles it exhaustively fails to compile, pointing you at exactly the code that needs updating. This is the refactoring superpower that justifies the whole language. Write the const exhaustive: never default in every switch over a union.

Interfaces vs Type Aliases

This is the most-asked beginner question and the answer is less dramatic than the debate suggests: they overlap heavily, each can do a couple of things the other cannot, and consistency within a codebase matters more than the choice. Knowing the two genuine differences is enough.

The overlap

TYPESCRIPT
interface User {
  id: string;
  name: string;
  email?: string;              // optional
  readonly createdAt: Date;    // cannot be reassigned after construction
}

type UserT = {
  id: string;
  name: string;
  email?: string;
  readonly createdAt: Date;
};

// Both work for objects, both support generics, both support extension.
interface Admin extends User { permissions: string[]; }
type AdminT = UserT & { permissions: string[] };

The two real differences

TYPESCRIPT
// Only `type` can do these
type Id = string | number;
type Coords = [number, number];
type Keys<T> = keyof T;
type Getter<T> = { [K in keyof T as `get${Capitalize<string & K>}`]: () => T[K] };

// Only `interface` can do this - declaration merging
interface Window { myAppVersion: string; }
interface Window { myAppFlags: Record<string, boolean>; }
// Window now has both. This is how you extend global/third-party types.
A rule you can defend in reviewUse interface for object shapes that are part of a public API or that someone might need to augment (React props, config objects, library surfaces). Use type for everything else — unions, function types, mapped and conditional types, and anything derived. If the team already has a convention, follow it; this is not worth a debate.

Index signatures and Record

TYPESCRIPT
// Index signature: arbitrary string keys
interface Headers {
  [header: string]: string;
}

// Record is usually clearer and composes better
type Headers2 = Record<string, string>;
type RoleFlags = Record<"admin" | "editor" | "viewer", boolean>;
// { admin: boolean; editor: boolean; viewer: boolean } - exhaustive, checked

// Mixing an index signature with known keys requires compatibility
interface Config {
  name: string;
  version: number;
  [key: string]: string | number;      // must include the types of known keys
}

// Partial Record for lookups that may miss
type Cache = Partial<Record<string, User>>;
const cache: Cache = {};
const u = cache["abc"];                 // User | undefined - correct
Index signatures lie by defaultRecord<string, User> says every string key yields a User, which is false — most keys yield undefined. Either enable noUncheckedIndexedAccess, which makes the lookup User | undefined globally, or use Partial<Record<string, User>> explicitly. Code that indexes a map and immediately dereferences the result is one of the most common runtime crashes in "type-safe" codebases.

Structural typing

TypeScript compares types by shape, not by name. Two types with identical members are interchangeable even if they are unrelated and declared in different files. This is usually convenient and occasionally dangerous.

TYPESCRIPT
interface Dog { name: string; legs: number }
interface Table { name: string; legs: number }

function walk(d: Dog) { /* ... */ }
const t: Table = { name: "kitchen", legs: 4 };
walk(t);                                 // compiles. Structurally identical.

// Branded types give you nominal behaviour when it matters
declare const brand: unique symbol;
type Brand<T, B extends string> = T & { readonly [brand]: B };

type UserId  = Brand<string, "UserId">;
type OrderId = Brand<string, "OrderId">;

function asUserId(s: string): UserId { return s as UserId; }
function getUser(id: UserId) { /* ... */ }

const oid = "ord_123" as OrderId;
// getUser(oid);                          // ERROR - exactly what you want
getUser(asUserId("usr_123"));             // OK
Where branding earns its keepAny codebase with several kinds of string identifier — userId, orderId, tenantId, sessionToken — will eventually pass the wrong one, and the bug is invisible because they are all strings. Branding costs five lines and turns that into a compile error. Also excellent for units (Minutes vs Seconds), currency amounts (Cents vs Rupees), and validated-vs-raw strings (SafeHtml vs string).

Unions, Intersections and Discriminated Unions

Unions are how TypeScript models "one of these", and the discriminated union is the single most useful modelling pattern in the language. Most "TypeScript is awkward here" complaints come from trying to model with optional properties what should be a discriminated union.

Unions and intersections

TYPESCRIPT
type Id = string | number;                       // either
type Timestamped = { createdAt: Date };
type Authored = { authorId: string };
type Post = Timestamped & Authored & { title: string };   // all of them

// On a union you can only access members present on EVERY member
type A = { kind: "a"; value: string; extra: boolean };
type B = { kind: "b"; value: number };
declare const ab: A | B;
ab.kind;                                          // OK - on both
ab.value;                                         // OK - string | number
// ab.extra;                                      // ERROR - only on A

// Intersections of primitives collapse to never
type Impossible = string & number;                // never

The optional-property anti-pattern

TYPESCRIPT
// BAD: everything optional, no invariants expressed, every access needs a check
interface RequestState {
  loading?: boolean;
  data?: User[];
  error?: Error;
}
// Nothing stops { loading: true, data: [...], error: new Error() } - a nonsense state.
// Every consumer writes defensive checks and they all disagree.

// GOOD: a discriminated union. Illegal states are unrepresentable.
type RequestState2 =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; data: User[]; fetchedAt: Date }
  | { status: "error"; error: Error; retryable: boolean };

function render(state: RequestState2) {
  switch (state.status) {
    case "idle":    return "Click to load";
    case "loading": return "Loading...";
    case "success": return `${state.data.length} users`;   // data is guaranteed here
    case "error":   return state.retryable ? "Retry?" : state.error.message;
    default: {
      const _never: never = state;
      return _never;
    }
  }
}
Make illegal states unrepresentableThis is the sentence to remember. If your type permits a combination that cannot occur in reality, you have pushed work onto every consumer and invited bugs. A discriminated union with a literal kind/status/type field is almost always the fix, and TypeScript's narrowing then gives you perfectly typed access inside each branch with no casts.

Discriminated unions in anger

TYPESCRIPT
// Domain events - the shape most backend TS codebases converge on
type DomainEvent =
  | { type: "order.created";   orderId: string; customerId: string; total: number }
  | { type: "order.paid";      orderId: string; paymentId: string; paidAt: Date }
  | { type: "order.shipped";   orderId: string; carrier: string; tracking: string }
  | { type: "order.cancelled"; orderId: string; reason: string; refunded: boolean };

type EventType = DomainEvent["type"];              // the union of all type strings

// Extract one member by its discriminant - extremely useful
type EventOf<T extends EventType> = Extract<DomainEvent, { type: T }>;
type PaidEvent = EventOf<"order.paid">;            // { type: "order.paid"; orderId: ...; }

// A fully typed handler map: every event must be handled, with the right payload
type Handlers = {
  [K in EventType]: (event: EventOf<K>) => Promise<void>;
};

const handlers: Handlers = {
  "order.created":   async (e) => { await notify(e.customerId, e.total); },
  "order.paid":      async (e) => { await receipt(e.paymentId, e.paidAt); },
  "order.shipped":   async (e) => { await track(e.carrier, e.tracking); },
  "order.cancelled": async (e) => { if (e.refunded) await refund(e.orderId); },
};

async function dispatch(event: DomainEvent): Promise<void> {
  // The cast is needed because TS cannot prove the correlation across the index,
  // but the DECLARATION of `handlers` above is fully checked, which is what matters.
  const handler = handlers[event.type] as (e: DomainEvent) => Promise<void>;
  await handler(event);
}

Result types instead of thrown exceptions

TYPESCRIPT
type Ok<T>  = { ok: true;  value: T };
type Err<E> = { ok: false; error: E };
type Result<T, E = Error> = Ok<T> | Err<E>;

const ok  = <T,>(value: T): Ok<T>  => ({ ok: true,  value });
const err = <E,>(error: E): Err<E> => ({ ok: false, error });

type ParseError =
  | { kind: "empty" }
  | { kind: "not_json"; raw: string }
  | { kind: "wrong_shape"; issues: string[] };

function parseConfig(raw: string): Result<Config, ParseError> {
  if (!raw.trim()) return err({ kind: "empty" });
  let parsed: unknown;
  try {
    parsed = JSON.parse(raw);
  } catch {
    return err({ kind: "not_json", raw: raw.slice(0, 80) });
  }
  const check = ConfigSchema.safeParse(parsed);
  if (!check.success) {
    return err({ kind: "wrong_shape", issues: check.error.issues.map((i) => i.message) });
  }
  return ok(check.data);
}

// The caller CANNOT forget to handle the failure - the compiler sees to it
const result = parseConfig(fileContents);

}
startServer(result.value);              // narrowed to Config here
Result types versus exceptionsTypeScript cannot type what a function throws — there is no throws clause, and catch (e) gives you unknown. So exceptions are invisible to the type system, which means the compiler cannot help you handle them. A Result type makes failure part of the signature and therefore impossible to ignore. The cost is verbosity and interop friction with libraries that throw. The pragmatic split most teams land on: Result for expected failures (validation, not-found, business rule violations) and exceptions for unexpected ones (programmer errors, infrastructure failure), with one top-level handler.

Narrowing and Control-Flow Analysis

Narrowing is TypeScript watching your code and tracking what a value could be at each point. It is the feature that makes unions pleasant to use rather than a constant source of casts. Knowing exactly which constructs narrow — and the two or three that silently stop narrowing — removes most of the friction people feel with the language.

The compiler tracks a narrowed type per code path. Mutation and function calls can invalidate it.

The narrowing constructs

TYPESCRIPT
function process(value: string | number | string[] | null | undefined) {
  // 1. typeof - for primitives
  if (typeof value === "string") {
    value.toUpperCase();                 // string
  }

  // 2. Array.isArray - special-cased by the compiler
  if (Array.isArray(value)) {
    value.map((s) => s.trim());          // string[]
  }

  // 3. Truthiness - but beware: "" and 0 are falsy
  if (value) {
    // string | number | string[]  - note that "" and 0 are EXCLUDED
  }

  // 4. Explicit null check - usually what you actually meant
  if (value != null) {                   // != null catches both null and undefined
    // string | number | string[]  - "" and 0 are INCLUDED
  }
}

// 5. instanceof - for classes
class HttpError extends Error { constructor(public status: number) { super(); } }
class TimeoutError extends Error {}

function handle(e: unknown) {
  if (e instanceof HttpError)    return `HTTP ${e.status}`;
  if (e instanceof TimeoutError) return "timed out";
  if (e instanceof Error)        return e.message;
  return String(e);
}

// 6. The `in` operator - for objects without a discriminant
type Cat = { meow(): void };
type Dog = { bark(): void };
function speak(pet: Cat | Dog) {
  if ("meow" in pet) pet.meow();
  else pet.bark();
}

// 7. Discriminant equality - the best one
type Shape = { kind: "circle"; r: number } | { kind: "square"; s: number };
function area(sh: Shape) {
  if (sh.kind === "circle") return Math.PI * sh.r ** 2;
  return sh.s ** 2;
}

Type predicates (user-defined type guards)

TYPESCRIPT
// The return type `x is T` tells the compiler what a true result proves.
function isString(x: unknown): x is string {
  return typeof x === "string";
}

function isNonEmpty<T>(arr: T[]): arr is [T, ...T[]] {
  return arr.length > 0;
}

// Filtering out null - the classic case the compiler cannot infer alone
function isDefined<T>(x: T | null | undefined): x is T {
  return x != null;
}

const maybe: (User | null)[] = [user1, null, user2];
const users1 = maybe.filter((u) => u !== null);     // (User | null)[] in older TS
const users2 = maybe.filter(isDefined);             // User[] - correct

// TypeScript 5.5+ infers predicates for simple arrow functions:
const users3 = maybe.filter((u) => u !== null);     // User[] in TS 5.5+

// A domain-level guard over unknown data
interface ApiError { code: string; message: string; details?: unknown }

function isApiError(x: unknown): x is ApiError {
  return (
    typeof x === "object" && x !== null &&
    "code" in x && typeof (x as Record<string, unknown>).code === "string" &&
    "message" in x && typeof (x as Record<string, unknown>).message === "string"
  );
}
A type predicate is a promise the compiler cannot verifyNothing stops you writing function isUser(x: unknown): x is User { return true; }. The compiler trusts you completely. A wrong predicate is as dangerous as an as cast and more insidious because it looks like a check. For data crossing a trust boundary, derive the guard from a schema (Zod's safeParse) rather than hand-writing it, so the check and the type cannot drift apart.

Assertion functions

TYPESCRIPT
// `asserts x is T` narrows for the REST of the enclosing scope, not just a block.
function assertIsDefined<T>(x: T, name = "value"): asserts x is NonNullable<T> {
  if (x == null) throw new Error(`${name} is required but was ${x}`);
}

function assertNever(x: never, context = "value"): never {
  throw new Error(`Unexpected ${context}: ${JSON.stringify(x)}`);
}

function handler(req: Request) {
  const userId = req.headers.get("x-user-id");    // string | null
  assertIsDefined(userId, "x-user-id header");
  userId.toUpperCase();                           // string, for the rest of the function
}
Assertion functions need an explicit type annotationYou cannot write const assertIsDefined = (x) => { ... } and have the assertion work — TypeScript requires the assertion signature to be explicitly declared on an identifier whose type is known at the call site. Use a function declaration, or annotate the const explicitly. The error message when you get this wrong ("Assertions require every name in the call target to be declared with an explicit type annotation") is one of the less obvious ones.

Where narrowing silently stops

TYPESCRIPT
class Container {
  value: string | null = null;

  bad() {
    if (this.value !== null) {
      doSomething();                 // this call could reassign this.value...
      // this.value.length;          // ERROR in some configurations - narrowing lost
    }
  }

  good() {
    const v = this.value;            // capture into a const FIRST
    if (v !== null) {
      doSomething();
      v.length;                      // still string - a const cannot change
    }
  }
}

// Closures over a mutable binding also lose narrowing
function example(x: string | undefined) {
  if (x === undefined) return;
  // x is string here
  const later = () => x.toUpperCase();     // OK - x is a parameter, never reassigned
}

function example2(x: string | undefined) {
  if (x === undefined) x = "default";      // reassignment inside the function
  const later = () => x.toUpperCase();     // OK in modern TS, but fragile
}

// Destructuring a discriminated union BREAKS the correlation before TS 4.6
type Action = { type: "add"; n: number } | { type: "reset" };
function reduce(action: Action) {
  const { type, ...rest } = action;
  // `type` and `rest` are now independent; narrowing on `type` does not narrow `rest`.
  // Narrow on the object FIRST, then destructure inside the branch.
  if (action.type === "add") {
    const { n } = action;                  // n: number - correct
  }
}
The habit that avoids most narrowing painCopy the value into a const at the top of the function, narrow the const, and work with that. Mutable bindings and object properties are the only things that lose narrowing, and a const local is neither. This single habit eliminates the large majority of "but I already checked that!" moments.

Functions: Overloads, Generics and satisfies

Function typing is where TypeScript's inference does the most work for you, and where a few specific tools — overloads, generic parameters, and the satisfies operator — let you express APIs that would otherwise require casts at every call site.

Basics and inference

TYPESCRIPT
// Annotate parameters, let the return type infer unless you want it enforced
function add(a: number, b: number) {
  return a + b;                                  // inferred: number
}

// Optional and default parameters
function greet(name: string, greeting = "Hello", punctuation?: string): string {
  return `${greeting}, ${name}${punctuation ?? "!"}`;
}

// Rest parameters
function sum(...nums: number[]): number {
  return nums.reduce((a, b) => a + b, 0);
}

// Function types
type Comparator<T> = (a: T, b: T) => number;
type AsyncHandler = (req: Request) => Promise<Response>;
type Predicate<T> = (value: T, index: number) => boolean;

// Contextual typing: the parameter types flow IN from the expected type

// void return means "I ignore whatever you return" - this is why forEach accepts anything

Overloads

TYPESCRIPT

Prefer a union or a generic to an overloadOverloads do not compose well: you cannot spread arguments into them easily, the implementation signature is unchecked against the overloads in some cases, and error messages degrade to "No overload matches this call", which tells the caller nothing about why. Reach for a union parameter type or a generic first. Overloads earn their place mainly when the return type genuinely depends on a literal argument, as above.

Generic functions

TYPESCRIPT
// The type parameter links input to output

  return out;
}

// Default type parameters

  items: T[];
  meta: M;
}
The generic smell testA type parameter is only useful if it appears at least twice — typically once in the parameters and once in the return type, or twice in the parameters to force them to match. If T appears exactly once, you almost certainly wanted a constraint or a union instead. function log<T>(x: T): void is just function log(x: unknown): void with extra ceremony.

TYPESCRIPT

  colors: { primary: "#2563eb", danger: "#dc2626" },

Generics in Depth

Everything beyond basic generics — conditional types, infer, mapped types, template literal types — forms a small functional programming language that runs at compile time. You do not need to write it often, but you absolutely need to read it, because every library you depend on is full of it, and because the error messages are unintelligible otherwise.

Conditional types

TYPESCRIPT
// T extends U ? X : Y - a ternary over types
type IsString<T> = T extends string ? true : false;
type A = IsString<"hello">;        // true
type B = IsString<42>;             // false

type NonNull<T> = T extends null | undefined ? never : T;
type C = NonNull<string | null>;   // string

// DISTRIBUTIVE: when T is a naked type parameter and the input is a union,
// the conditional distributes over each member and the results are unioned.
type ToArray<T> = T extends unknown ? T[] : never;
type D = ToArray<string | number>;       // string[] | number[]   (distributed)

// Wrap in a tuple to DISABLE distribution
type ToArrayNoDist<T> = [T] extends [unknown] ? T[] : never;
type E = ToArrayNoDist<string | number>; // (string | number)[]

// This is exactly how Exclude and Extract work
type MyExclude<T, U> = T extends U ? never : T;
type MyExtract<T, U> = T extends U ? T : never;
type F = MyExclude<"a" | "b" | "c", "a">;        // "b" | "c"
Distribution surprises everyone onceToArray<string | number> giving string[] | number[] rather than (string | number)[] is the most common conditional-type confusion. The rule: distribution happens only when the checked type is a bare type parameter. Wrapping both sides in a one-element tuple ([T] extends [U]) turns it off, which is what you want for "is this whole union assignable to that".

infer

TYPESCRIPT
// infer introduces a type variable inside a conditional's extends clause
type ElementOf<T> = T extends readonly (infer E)[] ? E : never;
type A = ElementOf<string[]>;                    // string
type B = ElementOf<readonly [1, "x", true]>;     // 1 | "x" | true

type ReturnOf<T> = T extends (...args: never[]) => infer R ? R : never;
type C = ReturnOf<() => Promise<User>>;          // Promise<User>

type ParamsOf<T> = T extends (...args: infer P) => unknown ? P : never;
type D = ParamsOf<(a: string, b: number) => void>;   // [a: string, b: number]

// Recursive unwrapping - this is essentially the built-in Awaited
type Unwrap<T> = T extends Promise<infer U> ? Unwrap<U> : T;
type E = Unwrap<Promise<Promise<string>>>;       // string

// Constrained infer
type FirstString<T> = T extends [infer H extends string, ...unknown[]] ? H : never;
type F = FirstString<["a", 1, true]>;            // "a"

// Practical: extract the payload type from a Zod-style schema
type InferSchema<S> = S extends { _output: infer O } ? O : never;

Mapped types

TYPESCRIPT
// Iterate the keys of T and transform each
type Mutable<T> = { -readonly [K in keyof T]: T[K] };     // remove readonly
type Required2<T> = { [K in keyof T]-?: T[K] };           // remove optional
type Nullable<T> = { [K in keyof T]: T[K] | null };
type Stringify<T> = { [K in keyof T]: string };

// Key remapping with `as` (TS 4.1+) - this is where it gets powerful
type Getters<T> = {
  [K in keyof T as `get${Capitalize<string & K>}`]: () => T[K]
};
interface Person { name: string; age: number }
type PersonGetters = Getters<Person>;
// { getName: () => string; getAge: () => number }

// Filter keys by mapping unwanted ones to never
type OnlyFunctions<T> = {
  [K in keyof T as T[K] extends (...a: never[]) => unknown ? K : never]: T[K]
};
type NonFunctionKeys<T> = {
  [K in keyof T]: T[K] extends (...a: never[]) => unknown ? never : K
}[keyof T];

// Deep variants - note the recursion and the array handling
type DeepPartial<T> = T extends (infer U)[]
  ? DeepPartial<U>[]
  : T extends object
    ? { [K in keyof T]?: DeepPartial<T[K]> }
    : T;

type DeepReadonly<T> = T extends (infer U)[]
  ? readonly DeepReadonly<U>[]
  : T extends object
    ? { readonly [K in keyof T]: DeepReadonly<T[K]> }
    : T;

Template literal types

TYPESCRIPT
type Protocol = "http" | "https";
type Url = `${Protocol}://${string}`;
const good: Url = "https://example.com";          // OK
// const bad: Url = "ftp://example.com";          // ERROR

// Combinatorial expansion
type Size = "sm" | "md" | "lg";
type Variant = "primary" | "secondary";
type ButtonClass = `btn-${Variant}-${Size}`;      // 6 literal members

// Built-in string manipulation types
type U = Uppercase<"hello">;                      // "HELLO"
type L = Lowercase<"HELLO">;                      // "hello"
type C = Capitalize<"hello">;                     // "Hello"
type Un = Uncapitalize<"Hello">;                  // "hello"

// Parse a route and extract its parameters - the pattern behind typed routers
type PathParams<P extends string> =
  P extends `${string}:${infer Param}/${infer Rest}`
    ? Param | PathParams<`/${Rest}`>
    : P extends `${string}:${infer Param}`
      ? Param
      : never;

type Params = PathParams<"/users/:userId/orders/:orderId">;   // "userId" | "orderId"

function buildPath<P extends string>(
  pattern: P,
  params: Record<PathParams<P>, string>
): string {
  return pattern.replace(/:(\w+)/g, (_, k: string) =>
    (params as Record<string, string>)[k]);
}

buildPath("/users/:userId/orders/:orderId", { userId: "1", orderId: "9" });
// buildPath("/users/:userId", { wrong: "1" });   // ERROR - caught at compile time

// Typed event names
type EventName = `on${Capitalize<"click" | "focus" | "blur">}`;  // "onClick" | ...
type Handlers = { [E in EventName]?: (e: Event) => void };
Template literal types explode combinatorially`${A}-${B}-${C}` where each union has 50 members produces 125,000 types. The compiler has a hard limit (around 100,000 union members) and will error with "Expression produces a union type that is too complex to represent". Worse, before hitting the limit it will make your editor sluggish for everyone on the team. Keep template literal unions to small, bounded sets.

Recursive types

TYPESCRIPT
// JSON - the canonical recursive type
type Json =
  | string | number | boolean | null
  | Json[]
  | { [key: string]: Json };

// A tree
type TreeNode<T> = { value: T; children: TreeNode<T>[] };

// Dot-notation paths into a nested object - useful for typed config/i18n lookups
type Paths<T, Depth extends readonly unknown[] = []> =
  Depth["length"] extends 5                      // depth guard: stop at 5 levels
    ? never
    : T extends object
      ? { [K in keyof T & string]:
            T[K] extends object ? K | `${K}.${Paths<T[K], [...Depth, 1]>}` : K
        }[keyof T & string]
      : never;

interface Settings {
  app: { name: string; theme: { mode: "light" | "dark"; accent: string } };
  limits: { maxUsers: number };
}

// "app" | "app.name" | "app.theme" | "app.theme.mode" | "app.theme.accent"
// | "limits" | "limits.maxUsers"
Always put a depth guard on a recursive typeWithout the Depth tuple accumulator above, a cyclic type (a parent that references a child that references the parent) sends the compiler into infinite recursion and you get "Type instantiation is excessively deep and possibly infinite". The tuple-length trick is the standard counter in type-level code: push a dummy element each recursion and check ["length"].

Modules, Declaration Files and Typing Third-Party JS

At a customer you will constantly meet JavaScript libraries with no types, internal packages with broken types, and global objects injected by some script tag in 2017. Knowing how declaration files work turns each of these from a blocker into a ten-minute fix.

Import and export syntax that matters

TYPESCRIPT

Why import type is not just styleUnder isolatedModules — which every esbuild/SWC/Vite setup uses — a transpiler sees one file at a time and cannot tell whether import { Foo } refers to a type or a value. If it drops it and Foo was a value, you lose the import. import type removes the ambiguity. Turn on verbatimModuleSyntax and the compiler will tell you where you need it.

Async Code: Promises, fetch and Error Typing

Asynchronous code is where TypeScript's limits are most visible: it can track what a promise resolves to, but it knows nothing about what it rejects with. Understanding that asymmetry — and designing around it — is most of what you need.

Promise basics

TYPESCRIPT
// An async function always returns a Promise; the annotation is the RESOLVED type

  getUser("1"),                       // Promise<User>
  getOrders("1"),                     // Promise<Order[]>
  getSettings("1"),                   // Promise<Settings>

  if (r.status === "fulfilled") console.log(r.value.name);   // narrowed to User

// Typing a concurrency-limited map
async function mapLimit<T, R>(
  items: readonly T[],
  limit: number,
  fn: (item: T, index: number) => Promise<R>
): Promise<R[]> {
  const out: R[] = new Array(items.length);
  let cursor = 0;
  const workers = Array.from({ length: Math.min(limit, items.length) }, async () => {
    while (cursor < items.length) {
      const i = cursor++;
      out[i] = await fn(items[i]!, i);
    }
  });
  await Promise.all(workers);
  return out;
}

// A reusable normaliser - put this in every codebase
function toError(e: unknown): Error {
  if (e instanceof Error) return e;
  if (typeof e === "string") return new Error(e);
  try { return new Error(JSON.stringify(e)); }
  catch { return new Error(String(e)); }
}

// Typed error hierarchy with discriminants so you can switch on them
abstract class AppError extends Error {
  abstract readonly code: string;
  abstract readonly httpStatus: number;
  constructor(message: string, readonly cause?: unknown) {
    super(message);
    this.name = new.target.name;         // so stack traces say "NotFoundError"
  }
}

class NotFoundError extends AppError {
  readonly code = "not_found" as const;
  readonly httpStatus = 404;
  constructor(readonly resource: string, readonly id: string) {
    super(`${resource} ${id} not found`);
  }
}

class ValidationError extends AppError {
  readonly code = "validation_failed" as const;
  readonly httpStatus = 422;
  constructor(readonly issues: Array<{ path: string; message: string }>) {
    super(`Validation failed: ${issues.length} issue(s)`);
  }
}

class UpstreamError extends AppError {
  readonly code = "upstream_failed" as const;
  readonly httpStatus = 502;
  constructor(readonly service: string, cause: unknown) {
    super(`Upstream ${service} failed`, cause);
  }
}

function toHttpResponse(e: unknown) {
  if (e instanceof AppError) {
    switch (e.code) {
      case "not_found":         return { status: 404, body: { error: e.code, resource: e.resource } };
      case "validation_failed": return { status: 422, body: { error: e.code, issues: e.issues } };
      case "upstream_failed":   return { status: 502, body: { error: e.code, service: e.service } };
    }
  }
  return { status: 500, body: { error: "internal" } };
}
There is no throws clause and there never will beTypeScript deliberately does not track thrown types, because JavaScript's throw is unconstrained and checked exceptions have a poor track record. The practical consequences: you cannot know from a signature what a function might throw; the compiler will never remind you to handle a failure; and a refactor that introduces a new throw is invisible. If a failure is part of your domain — not found, invalid input, business rule violated — model it in the return type with a Result, and reserve throw for genuinely exceptional conditions handled by one top-level boundary.

AbortController and timeouts

TYPESCRIPT
async function fetchWithTimeout(
  url: string,
  init: RequestInit = {},
  timeoutMs = 10_000
): Promise<Response> {
  const controller = new AbortController();
  const timer = setTimeout(() => controller.abort(new Error("timeout")), timeoutMs);
  try {
    return await fetch(url, { ...init, signal: controller.signal });
  } catch (e) {
    if (e instanceof DOMException && e.name === "AbortError") {
      throw new UpstreamError(url, `timed out after ${timeoutMs}ms`);
    }
    throw e;
  } finally {
    clearTimeout(timer);
  }
}

// Composing an external signal (e.g. React cleanup) with a timeout
function withTimeout(signal: AbortSignal | undefined, ms: number): AbortSignal {
  const signals = [AbortSignal.timeout(ms)];
  if (signal) signals.push(signal);
  return AbortSignal.any(signals);
}

Types are a compile-time fiction. Validation is the runtime reality. The crucial insight is that you should write the schema and derive the type from it — never the other way round — so that the thing you check and the thing you declare can never diverge. Validate once at the edge. Everything inside can then trust its types completely.

An end-to-end typed API client

TYPESCRIPT
// src/api/client.ts
import { z } from "zod";

export class ApiError extends Error {
  constructor(
    readonly status: number,
    readonly url: string,
    readonly body: unknown,
  ) {
    super(`API ${status} on ${url}`);
    this.name = "ApiError";
  }
}

export class ApiValidationError extends Error {
  constructor(readonly url: string, readonly issues: z.ZodIssue[]) {
    super(`Response from ${url} did not match the expected schema`);
    this.name = "ApiValidationError";
  }
}

interface RequestOptions<TBody> {
  method?: "GET" | "POST" | "PUT" | "PATCH" | "DELETE";
  body?: TBody;
  query?: Record<string, string | number | boolean | undefined>;
  signal?: AbortSignal;
  timeoutMs?: number;
}

export class ApiClient {
  constructor(
    private readonly baseUrl: string,
    private readonly getToken: () => string | null = () => null,
  ) {}

  async request<TResponse, TBody = never>(
    path: string,
    schema: z.ZodType<TResponse>,
    options: RequestOptions<TBody> = {},
  ): Promise<TResponse> {
    const { method = "GET", body, query, signal, timeoutMs = 15_000 } = options;

    const url = new URL(path, this.baseUrl);
    for (const [k, v] of Object.entries(query ?? {})) {
      if (v !== undefined) url.searchParams.set(k, String(v));
    }

    const token = this.getToken();
    const headers: Record<string, string> = { Accept: "application/json" };
    if (body !== undefined) headers["Content-Type"] = "application/json";
    if (token) headers.Authorization = `Bearer ${token}`;

    const signals = [AbortSignal.timeout(timeoutMs)];
    if (signal) signals.push(signal);

    const res = await fetch(url, {
      method,
      headers,
      body: body === undefined ? undefined : JSON.stringify(body),
      signal: AbortSignal.any(signals),
    });

    const text = await res.text();
    const json: unknown = text ? JSON.parse(text) : null;

    if (!res.ok) throw new ApiError(res.status, url.pathname, json);

    const parsed = schema.safeParse(json);
    if (!parsed.success) {
      // Log the full issue list - this is how you find API drift in minutes
      console.error("Schema mismatch", url.pathname, parsed.error.issues);
      throw new ApiValidationError(url.pathname, parsed.error.issues);
    }
    return parsed.data;
  }
}

Typing React Properly

React is where most TypeScript is written, and where most of it is written badly — React.FC everywhere, any on every event handler, props typed as object. The correct patterns are not hard and they make component APIs self-documenting, which matters enormously when you are handing a codebase to a customer's team.

Props

TYPESCRIPT

interface ButtonProps {

  onClick: () => void;
  variant?: "primary" | "secondary" | "danger";
  disabled?: boolean;
  children?: React.ReactNode;

interface InputProps extends React.ComponentPropsWithoutRef<"input"> {
  label: string;
  error?: string;
}

function Input({ label, error, id, ...rest }: InputProps) {
  const inputId = id ?? React.useId();
  return (
    <div>
      <label htmlFor={inputId}>{label}</label>
      <input id={inputId} aria-invalid={!!error} {...rest} />
      {error && <span role="alert">{error}</span>}
    </div>
  );
}

    return <input ref={ref} aria-label={label} {...rest} />;
  }
);

interface Input19Props extends React.ComponentPropsWithRef<"input"> {
  label: string;
}

  return <input ref={ref} aria-label={label} {...rest} />;
}

A plain function with a typed props parameter has none of these problems, infers the return type correctly, and is what the React team recommends. Declare children: React.ReactNode explicitly when you want it.

// A generic wrapper that validates params, query and body, then hands you typed data.
function validated<
  P extends z.ZodTypeAny,
  Q extends z.ZodTypeAny,
  B extends z.ZodTypeAny,
  R,
>(
  schemas: { params?: P; query?: Q; body?: B },
  handler: (
    input: { params: z.infer<P>; query: z.infer<Q>; body: z.infer<B> },
    req: Request,
    res: Response,
  ) => Promise<R>,
) {
  return async (req: Request, res: Response, next: NextFunction) => {
    try {
      const params = schemas.params ? schemas.params.parse(req.params) : undefined;
      const query  = schemas.query  ? schemas.query.parse(req.query)   : undefined;
      const body   = schemas.body   ? schemas.body.parse(req.body)     : undefined;
      const result = await handler({ params, query, body } as never, req, res);
      if (!res.headersSent) res.json(result);
    } catch (e) {
      next(e);                                 // one error handler, defined once
    }
  };
}

  constructor(
    private readonly repo: OrderRepository,
    private readonly payments: PaymentGateway,
  ) {}

  async markPaid(id: string, paymentId: string): Promise<Order> {
    const order = await this.repo.findById(id);
    if (!order) throw new NotFoundError("Order", id);
    if (order.status !== "draft") {
      throw new ConflictError(`Order ${id} is ${order.status}, cannot be paid`);
    }
    await this.payments.capture(paymentId, order.totalMinor);
    return this.repo.updateStatus(id, "paid");
  }

Errors You Will Hit and How to Read Them

TypeScript error messages are famously long, and the skill is knowing which part to read. This section covers the half-dozen errors that account for most of the confusion, plus a method for decoding a forty-line message in under a minute.

Reading a long error

Read the LAST line first, then the firstTypeScript errors are structured as a chain: "A is not assignable to B" at the top, then progressively more specific "because X is not assignable to Y" lines, ending with the actual mismatch. The final line names the concrete incompatibility — Type 'string' is not assignable to type 'number'. Read that, then look at the first line to find which argument or property it was about, and ignore the middle entirely. In the editor, hovering the squiggle and collapsing the message gives the same effect.

Excess property checking

TYPESCRIPT
interface Options { width: number; height?: number }

function render(o: Options) {}

render({ width: 10, heigth: 20 });
// ERROR: Object literal may only specify known properties,
//        and 'heigth' does not exist in type 'Options'. Did you mean 'height'?

// But this compiles:
const opts = { width: 10, heigth: 20 };
render(opts);                               // no error - structurally compatible

// Why: excess property checking applies ONLY to FRESH object literals assigned
// directly. Once the literal is in a variable, its "freshness" is gone and
// normal structural compatibility applies (extra props are allowed).

// If you want the check on a variable, use satisfies:
const opts2 = { width: 10, heigth: 20 } satisfies Options;   // ERROR - good

Variance: why callbacks behave oddly

TYPESCRIPT
// Arrays are covariant in TypeScript, which is UNSOUND but pragmatic.
class Animal { name = "" }
class Dog extends Animal { breed = "" }

const dogs: Dog[] = [new Dog()];
const animals: Animal[] = dogs;             // allowed
animals.push(new Animal());                 // compiles - but dogs now contains a non-Dog!
// dogs[1].breed;                           // undefined at runtime. TypeScript chose
//                                          // convenience over soundness here.

// readonly arrays avoid the problem
const safe: readonly Animal[] = dogs;       // cannot push

// Function PARAMETERS are bivariant for method syntax, contravariant for
// property syntax under strictFunctionTypes. This is the real-world difference:
interface Handler1 { handle(e: Animal): void }      // method - bivariant (lenient)
interface Handler2 { handle: (e: Animal) => void }  // property - contravariant (strict)

const h1: Handler1 = { handle: (d: Dog) => {} };    // allowed (bivariance)
// const h2: Handler2 = { handle: (d: Dog) => {} }; // ERROR under strictFunctionTypes

// Rule of thumb: declare callbacks as properties, not methods, if you want
// the compiler to catch a handler that demands more than it will receive.

Escape hatches, ranked by how much they should worry you

TYPESCRIPT

brokenThing.doStuff();

// 8. @ts-expect-error - better than ts-ignore: it ERRORS if the line stops failing,

// @ts-expect-error library types are wrong, see https://github.com/x/y/issues/123
legacy.doStuff();
Use @ts-expect-error, never @ts-ignoreThey look equivalent but behave oppositely when the underlying problem is fixed. @ts-ignore keeps suppressing forever and nobody ever removes it. @ts-expect-error becomes an error itself once the line compiles cleanly — so when the library ships correct types, your build tells you to delete the comment. Enforce it with the ESLint rule @typescript-eslint/ban-ts-comment configured to allow expect-error with a description and ban the rest.

Migrating a JavaScript Codebase

You will be asked to do this at a customer, often with a team that is nervous about it. The project fails when it is attempted as a big-bang rewrite with strict on from day one, and succeeds when it is incremental, reversible and visibly delivering value within the first week.

Five stages, each independently valuable, each shippable within days.

Stage by stage

  1. Add TypeScript without converting anything. Install typescript, add a tsconfig.json with allowJs: true, checkJs: false, strict: false, noEmit: true. Wire tsc --noEmit into CI. At this point it passes trivially — that is the point. The build is proven and nobody's workflow changed.
  2. Turn on checkJs for one directory using a second tsconfig or // @ts-check pragmas. Fix what it finds — usually real bugs: typos in property names, functions called with the wrong arity, unhandled undefined. Ship those fixes as bug fixes, because that is what they are, and the team sees value before any migration cost.
  3. Install @types for every dependency that has them. This alone transforms the editor experience and costs nothing.
  4. Rename leaf files first. Start with modules nothing imports from — constants, pure utilities, type definitions. Renaming .js to .ts there cannot break anything above it. Work up the dependency graph. Use madge or dependency-cruiser to find the leaves.
  5. Define the domain types once and reuse them. This is where the real benefit appears: a single Order type that every module agrees on, derived from a Zod schema at the API boundary.
  6. Enable strict flags one at a time, in this order: noImplicitAny, strictNullChecks (the big one — budget real time), strictFunctionTypes, strictBindCallApply, noImplicitThis, then the rest. Each flag is a separate pull request.
  7. Add the ratchet. A CI script that counts remaining anys, @ts-expect-errors and unchecked files and fails if the count increases. This is what makes the migration irreversible without requiring it to be finished.

#!/usr/bin/env bash
# scripts/type-ratchet.sh - fail CI if type debt increases
set -euo pipefail

BASELINE_FILE=".type-baseline.json"

ANY_COUNT=$(grep -rE ':\s*any\b|<any>|as any' src --include='*.ts' --include='*.tsx' | wc -l)
IGNORE_COUNT=$(grep -rE '@ts-(ignore|expect-error|nocheck)' src | wc -l)
JS_COUNT=$(find src -name '*.js' -o -name '*.jsx' | wc -l)

BASE_ANY=$(jq -r '.any' "$BASELINE_FILE")
BASE_IGNORE=$(jq -r '.ignores' "$BASELINE_FILE")
BASE_JS=$(jq -r '.jsFiles' "$BASELINE_FILE")

fail=0
[ "$ANY_COUNT"    -gt "$BASE_ANY" ]    && { echo "any:    $ANY_COUNT > $BASE_ANY";       fail=1; }
[ "$IGNORE_COUNT" -gt "$BASE_IGNORE" ] && { echo "ignore: $IGNORE_COUNT > $BASE_IGNORE"; fail=1; }
[ "$JS_COUNT"     -gt "$BASE_JS" ]     && { echo "js:     $JS_COUNT > $BASE_JS";         fail=1; }

if [ "$fail" -eq 1 ]; then
  echo "Type debt increased. Fix it, or update $BASELINE_FILE with a justification."
  exit 1
fi

# Ratchet DOWN automatically when the numbers improve
jq -n --argjson a "$ANY_COUNT" --argjson i "$IGNORE_COUNT" --argjson j "$JS_COUNT" \
   '{any:$a, ignores:$i, jsFiles:$j}' > "$BASELINE_FILE"
echo "Type debt: any=$ANY_COUNT ignores=$IGNORE_COUNT js=$JS_COUNT"

What project references buy youEach package is type-checked once and its .d.ts output is consumed by dependents, so changing a leaf package does not re-check the entire monorepo. On a large repo this routinely turns a 90-second check into 8 seconds. It also enforces the dependency graph — package A cannot secretly import from package B unless the reference exists, which is a genuine architectural benefit beyond speed. The cost is more configuration and the need to build before some editor features work across package boundaries.

Keeping types fast as the codebase grows

  • skipLibCheck: true and incremental: true from day one.
  • Prefer interface X extends Y over type X = Y & Z for object composition.
  • Give intermediate type computations names; the compiler caches named types.
  • Annotate exported function return types explicitly — it stops the compiler re-inferring them at every call site and improves .d.ts emit.
  • Avoid barrel index.ts files in large packages; import from the concrete module.
  • Cap template-literal unions; do not generate thousands of members.
  • Put a depth guard on every recursive type.
  • Run --generateTrace when a check gets slow rather than guessing.
  • Split into project references once a single tsc --noEmit exceeds ~30 seconds.

Interview Questions

What is the difference between any and unknown, and when would you use each?
Both can hold any value, but they differ in what you are allowed to do with them. With any, the compiler stops checking entirely: you can access any property, call it, and assign it to anything, and the any spreads to every expression it touches, which is why one any can silently disable checking across a whole module. With unknown, you can assign anything into it but you cannot do anything with it until you narrow it — no property access, and it is not assignable to any other type. That makes unknown the correct type for data crossing a trust boundary: the result of JSON.parse, a fetch response body, a caught exception, or process.env values. You then prove the shape with a type guard or, better, a schema parse. I use any only as a deliberate temporary escape hatch during a migration, with a comment explaining why, and I configure the no-explicit-any lint rule so each one is a conscious decision rather than a habit.
TypeScript types do not exist at runtime. What are the practical consequences?
The main one is that no data entering your program is actually validated by the type system — it is validated by your assertion, which may be wrong. Writing const user = await res.json() as User tells the compiler to trust you, and if the API returns a number where you declared a string, or omits a field, nothing fails at that line. The failure surfaces much later, somewhere unrelated, as "cannot read properties of undefined", and the stack trace points at the victim rather than the cause. The consequence for design is that you need runtime validation at every boundary: HTTP responses, request bodies, environment variables, localStorage, message queue payloads, and database rows, since drivers return loosely typed objects. The pattern I use is to define a Zod schema and derive the type with z.infer, so there is exactly one definition and the check and the type cannot drift. Secondary consequences: you cannot do if (x instanceof MyInterface), you cannot reflect over types to generate a form or an ORM mapping without a build step, and generics are erased so you cannot branch on T at runtime.
Explain discriminated unions and why they are better than optional properties.
A discriminated union is a union of object types that all share a literal-typed field — kind, type, status — with a different value in each member. TypeScript uses that field to narrow: inside if (state.status === "success") the compiler knows exactly which member you have and gives you its specific fields with no cast. The alternative people reach for is one interface with everything optional — loading?, data?, error? — and that is worse for two reasons. First, it permits nonsense states like loading and error being simultaneously true, which means every consumer has to write defensive logic and they will not all agree on the precedence. Second, every access needs a null check even in branches where the value is logically guaranteed, so the code is noisier and the compiler helps less. The phrase I use is "make illegal states unrepresentable". The additional payoff is exhaustiveness: with a default branch that assigns the value to never, adding a new member to the union causes every switch that does not handle it to fail compilation, which turns a scary refactor into a to-do list from the compiler.
What does strict actually turn on, and which flag matters most?
strict is an umbrella for about eight flags: noImplicitAny, strictNullChecks, strictFunctionTypes, strictBindCallApply, strictPropertyInitialization, noImplicitThis, useUnknownInCatchVariables and alwaysStrict. By far the most important is strictNullChecks. Without it, null and undefined are assignable to every type, which means the single largest category of JavaScript runtime errors — reading a property of undefined — is completely invisible to the type system. With it on, a value that might be absent has type T | null and the compiler forces you to handle it before use. The others matter too: noImplicitAny stops untyped parameters silently becoming any; useUnknownInCatchVariables types caught errors as unknown, which is correct since JavaScript can throw anything. Beyond strict I also enable noUncheckedIndexedAccess, which makes array and record access return T | undefined — initially noisy, but it catches a real class of off-by-one and missing-key bugs. On a legacy codebase I would enable these one flag at a time, each as its own pull request, rather than all at once.
When would you use interface versus type?
They overlap for object shapes, so the honest answer is that consistency matters more than the choice, but there are two real differences. Only type can express unions, intersections of non-objects, tuples, primitives, mapped types, conditional types and template literal types — so anything derived or computed must be a type. Only interface supports declaration merging, where you reopen it in another file and add members; that is essential for augmenting third-party or global types, such as adding a user property to Express's Request or a field to Window. There are also minor practical differences: interfaces tend to produce better error messages because the name is preserved rather than the structure expanded, and they are marginally faster for the compiler on very large shapes because the resolved members are cached. My convention is interface for object shapes that form a public API or might need augmenting, and type for everything else. I would not re-litigate an existing codebase's convention over this.
How do generics work and when should you reach for one?
A generic introduces a type parameter that is filled in at the call site, letting you express a relationship between types rather than fixing them. The classic example is function first<T>(arr: T[]): T | undefined, where the return type is tied to the element type of the input, so calling it with a User[] gives you User | undefined with no cast. Constraints restrict what the parameter can be — T extends { length: number } lets you access .length inside — and K extends keyof T is the pattern behind typed property access and Pick. The test I apply before adding a type parameter is whether it appears at least twice, typically once in the parameters and once in the return type, or twice in the parameters to force two arguments to agree. If T appears exactly once, the generic is doing nothing that unknown or a constraint would not do, and it just makes the signature harder to read. Beyond that there is a second tier — conditional types, infer, mapped types — which you rarely need to write but constantly need to read, because that is what library types are made of.
How would you migrate a large JavaScript codebase to TypeScript?
Incrementally, with every stage merged to main within days, because the long-lived migration branch is the way these projects die. First I add TypeScript with allowJs, checkJs: false, strict: false and noEmit, and wire tsc --noEmit into CI — it passes trivially, which proves the pipeline works and changes nobody's workflow. Then I install @types packages for dependencies, which immediately improves the editor for the whole team at zero cost. Then I enable checkJs on one directory, or add // @ts-check pragmas with JSDoc types, and fix what it finds — which is usually genuine bugs like misspelled properties and wrong arity, shipped as bug fixes so the team sees value before paying migration cost. Only then do I start renaming files, beginning with leaves that nothing imports from and working up the dependency graph. Finally I enable strict flags one at a time, noImplicitAny first and strictNullChecks as its own substantial piece of work. Throughout, I add a CI ratchet that counts remaining anys, ts-expect-errors and .js files and fails if any count increases, because you do not need to finish the migration — you need to guarantee it cannot go backwards.
What is satisfies and what problem does it solve?
It checks a value against a type without widening the value to that type. Before satisfies, you had two bad options. Annotating — const config: Config = {...} — validates the shape but throws away the specific literal types, so config.port becomes string | number | boolean and you cannot call a number method on it. Using as const keeps the literal types but performs no validation at all, so a typo in a key or a disallowed value type goes unnoticed. satisfies gives you both: the expression is checked against the type and any excess or wrong property is an error at the declaration, but the inferred type remains the specific literal shape. The most common real use is a lookup table — a route map, a theme, a config object — where you want keyof typeof routes to be the exact union of keys and the values to be the exact literal strings, while still guaranteeing every value matches a constraint like `/${string}`. You can also combine it with as const for a deeply readonly, checked, literal-typed object.
A colleague writes const user = await res.json() as User. What is wrong with it?
It is an unverified assertion dressed up as a type. res.json() returns Promise<any>, and the cast tells the compiler to stop asking questions — no check happens at runtime. If the API returns {"id": 1} where id is declared as a string, or renames name to fullName, or returns null for a field declared non-nullable, this line succeeds and the program continues with a value that violates its own type. The failure then appears somewhere else entirely, often in a UI component, as "cannot read properties of undefined", and debugging starts at the wrong end of the call chain. The fix is to type the parsed JSON as unknown and run it through a schema: const user = UserSchema.parse(await res.json()), with type User = z.infer<typeof UserSchema> so the schema is the single source of truth. That throws immediately, at the boundary, with a message naming the exact field and the exact problem. The broader principle is that every as on data from outside your program is a bug you have not encountered yet, and the whole point of validating at the edge is that everything inside can then trust its types completely.
How do you type errors in TypeScript?
You cannot type what a function throws — there is no throws clause and the language deliberately does not track it, because JavaScript's throw is unconstrained. Under strict, catch (e) gives you unknown, which is correct since any value can be thrown, so the first thing in any catch block is narrowing: if (e instanceof Error), or a normaliser function that converts anything into an Error. Beyond that I use two complementary approaches. For unexpected failures — programmer errors, infrastructure problems — I use a class hierarchy with a literal code field on each subclass, which makes them a discriminated union so a single top-level handler can switch on the code and map to an HTTP status exhaustively. For expected, domain-level failures — not found, validation failed, a business rule violated — I prefer returning a Result type, a union of { ok: true, value } and { ok: false, error }, because that puts the failure in the signature where the compiler forces the caller to handle it. The trade-off is verbosity and friction with libraries that throw, so I draw the line at "is this part of the domain or is it exceptional".
Your team's tsc --noEmit takes four minutes and the editor lags. How do you diagnose it?
I start with tsc --noEmit --diagnostics to see the basic shape: file count, type count, and especially instantiation count, since instantiations in the millions point at heavy generic or conditional type work rather than simply having a lot of code. Then --generateTrace with @typescript/analyze-trace, which names the specific files and type instantiations consuming the time. The usual findings, in rough order of frequency: skipLibCheck is off so the compiler is checking every .d.ts in node_modules; a recursive or deeply conditional utility type with no depth guard; large intersections of big object types, which are recomputed rather than cached — switching to interface extends often helps measurably; enormous union types, sometimes generated accidentally by a template literal type; and barrel index.ts files that drag the entire module graph into every import. Structural fixes are enabling incremental and splitting the repo into project references, which type-checks each package once and reuses its declaration output, commonly taking a ninety-second check down to under ten seconds. I would measure before and after each change rather than applying all of them blind.
What are the downsides of TypeScript, honestly?
Several, and being able to name them is a sign you actually use it. Build complexity: you now have a compile step, a tsconfig with options that interact in non-obvious ways, and module resolution that can produce errors that look like type errors but are configuration problems. Error messages: a mismatch deep inside a generic produces a forty-line message that is genuinely hard to read until you learn to read the last line first. The false sense of safety is the most dangerous one — a fully typed codebase that casts at every boundary has all the ceremony and none of the protection, and teams routinely believe they are safe when they are not. There is a real learning curve past the basics; conditional types and infer are a second language. Type-level code can get clever to the point of being unmaintainable, and a sufficiently baroque utility type is worse than an any with a comment. Compile times on large repos need active management. And some patterns are genuinely more awkward than in plain JavaScript, particularly highly dynamic code and some metaprogramming. On balance I think it is clearly worth it for anything multi-person and long-lived, but I would not use it for a sixty-line script, and I would not pretend the costs are zero.

Checklist and Practice Plan

TypeScript is learned by hitting errors and understanding why, not by reading about types. The exercises below are ordered so each one forces a specific concept, and the checklists are what to apply on a real codebase.

Practice plan — eight focused exercises

  1. Model a state machine. Take a request lifecycle — idle, loading, success, error, retrying — and model it as a discriminated union. Write a render function with an exhaustive switch and a never default. Then add a sixth state and watch exactly which code fails to compile. This is the single most important exercise.
  2. Build a typed API client. Pick any public API. Write Zod schemas for three endpoints, derive the types with z.infer, and build a generic request<T>(path, schema) function. Then deliberately change a schema to the wrong type and confirm you get a precise error naming the field.
  3. Write five utility types from scratch without looking them up: MyPartial, MyPick, MyOmit, MyReturnType, MyAwaited. Then write DeepPartial and Paths with a depth guard. This is the fastest way to internalise mapped and conditional types.
  4. Brand your identifiers. In an existing project, convert userId, orderId and one more identifier to branded types. Count how many places the compiler finds where the wrong one was being passed. There is usually at least one.
  5. Type a generic React component. Build a <DataTable> where column accessors are constrained to keyof T or a render function, and prove that a typo in a column key is a compile error.
  6. Fix a real error chain. Find a forty-line "not assignable" error in a codebase and work out the mismatch from the last line alone, without reading the middle. Repeat until it takes under a minute.
  7. Migrate a small JS project. Take a 20-file JavaScript project through all five migration stages in one sitting. Note which stage produced the most real bugs — it is almost always checkJs with JSDoc, before any renaming.
  8. Profile a slow build. Run --generateTrace on any non-trivial project, read the analysis, and find the single most expensive type. Then make it cheaper and measure the difference.

Checklist: starting a new TypeScript project

  • strict: true, plus noUncheckedIndexedAccess and exactOptionalPropertyTypes.
  • skipLibCheck: true, incremental: true, isolatedModules: true, verbatimModuleSyntax: true.
  • module/moduleResolution matched to the runtime or bundler, and verified by actually running the output.
  • tsc --noEmit as a separate CI step, because your bundler does not type-check.
  • ESLint with @typescript-eslint: no-explicit-any, no-floating-promises, no-misused-promises, ban-ts-comment allowing only expect-error with a description.
  • A validation library at every boundary, with types derived from schemas.
  • Environment variables validated at startup; the process exits with a readable message if they are wrong.
  • A Prettify helper in the shared types file.
  • Path aliases wired in both tsconfig and the bundler/runtime, with the output verified.

Checklist: code review

  • Any as on data from outside the program — should be a schema parse.
  • Any any without a comment explaining why and a plan to remove it.
  • @ts-ignore anywhere — should be @ts-expect-error with a reason and a link.
  • Non-null assertions (!) where a guard would be clearer and safer.
  • A union being handled without an exhaustive never default.
  • Optional properties used where a discriminated union expresses the real invariants.
  • A type parameter that appears only once — it wants to be a constraint or unknown.
  • Object literals typed by annotation where satisfies would preserve the literals.
  • Database rows or API responses cast rather than parsed.
  • A recursive type without a depth guard.
  • Exported functions without explicit return types in a large codebase.

Checklist: handing a TypeScript codebase to a customer's team

  • Domain types defined once, derived from schemas, in a single shared module.
  • Every external boundary validated; no casts on untrusted data anywhere.
  • tsc --noEmit and lint both green, enforced in CI, with no skipped checks.
  • A type ratchet in place so the debt cannot grow after you leave.
  • A README that states the module resolution setup and how to run the type check locally.
  • No any in the public surface of any shared package.
  • attw clean if you are publishing a package.
  • Build time measured and documented, with project references in place if it exceeds about thirty seconds.
